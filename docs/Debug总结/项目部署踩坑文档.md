# Docker 部署指南

## 架构概览

```
用户 → xg-2.frp.one:31431 (frp 内网穿透)
  ↓
127.0.0.1:5645 (宿主机 frpc 映射)
  ↓
Nginx (docker, 5645端口)
  ├── /api/*                  → backend-1:8000 / backend-2:8000 (least_conn 负载均衡)
  ├── /api/v1/ws              → WebSocket 升级代理（私信聊天）
  ├── /api/v1/messages/stream → SSE 长连接（消息推送）
  └── /*                      → 前端静态文件 (frontend volume)
```

## 服务列表

| 服务 | 实例数 | 说明 |
|------|--------|------|
| `backend-1` | 1 | FastAPI 实例 1，端口 8000 |
| `backend-2` | 1 | FastAPI 实例 2，端口 8000 |
| `mq-consumer` | 1 | MQ 消费者进程 |
| `nginx` | 1 | 负载均衡 + 前端静态文件服务，端口 5645 |
| `frontend` | 1 | 前端构建（一次性，构建后退出） |

### 基础设施

MySQL、Redis、RabbitMQ 已单独部署在宿主机上，容器通过 `host.docker.internal` 连接。

## 启动

```bash
# 首次启动（构建镜像 + 启动所有服务）
docker-compose up -d --build

# 查看状态
docker-compose ps

# 查看日志
docker-compose logs -f backend-1
docker-compose logs -f nginx
```

## 常见部署问题

### 1. `alembic: not found`

**现象**：`backend-1` / `backend-2` 不断重启，日志显示 `sh: 1: alembic: not found`

**原因**：`requirements.txt` 中缺少 `alembic` 依赖，或 Docker 构建缓存了旧层未重新安装。

**解决方案**：
1. 确保 `requirements.txt` 包含 `alembic>=1.13.0`
2. 启动命令中已加入 `pip install alembic -q` 作为兜底
3. 若仍无效，强制重建：
```bash
docker-compose build --no-cache backend-1 backend-2
docker-compose up -d
```

### 2. `Table 'xxx' already exists`

**现象**：alembic 迁移失败，日志显示 `Table 'comment' already exists`

**原因**：MySQL 数据库已存在旧表，alembic 尝试 `CREATE TABLE` 时报错。

**解决方案**：启动命令已做容错处理：
```bash
alembic upgrade head 2>/dev/null || alembic stamp head 2>/dev/null
```
先尝试升级，失败则仅标记当前版本。如果数据库结构与迁移文件不一致，需要手动处理：
```bash
# 进入容器执行
docker exec -it interview-backend-1 sh
# 手动标记所有迁移已应用
alembic stamp head
```

### 3. `host not found in upstream "backend-1:8000"`

**现象**：nginx 不断重启，日志显示 `host not found in upstream "backend-1:8000"`

**原因**：nginx 在 backend 容器尚未就绪时尝试解析其主机名，Docker DNS 解析失败。

**解决方案**：`depends_on` 配置了 `condition: service_healthy`，nginx 会等待 backend 健康检查通过后才启动。如果 backend 健康检查失败，nginx 也会启动失败。可检查 backend 健康检查状态：
```bash
docker inspect --format='{{json .State.Health}}' interview-backend-1
```

### 4. `frontend` 容器 `exec: "true": executable file not found in $PATH`

**现象**：`frontend` 容器创建失败，报错 `exec: "true": executable file not found in $PATH`

**原因**：`FROM scratch` 或 `FROM alpine:latest` 镜像中缺少 `true` 命令，或 Docker 版本兼容性问题。

**解决方案**：Dockerfile 中使用 `CMD ["/bin/true"]`，docker-compose 中不覆盖 `command`。如果 `/bin/true` 仍不可用，改为 `CMD ["sh", "-c", "exit 0"]`。

### 5. `frontend` 容器 `no command specified`

**现象**：`frontend` 容器创建失败，报错 `no command specified`

**原因**：`FROM scratch` 没有默认命令，且 docker-compose 中未指定 `command`。

**解决方案**：改用 `FROM alpine:latest` 作为最终阶段，并设置 `CMD`。

### 6. 前端加载慢，70+ 个 JS 请求

**现象**：打开页面时浏览器发起大量小 JS 文件请求（每个 antd 图标单独一个 chunk）。

**原因**：Vite 默认将 `@ant-design/icons` 的每个图标拆分为独立 chunk，导致大量 HTTP 请求。

**解决方案**：在 `vite.config.ts` 中配置 `manualChunks` 合并：
```typescript
manualChunks: {
  'antd-vendor': ['antd', '@ant-design/icons', 'react-is'],
  'react-vendor': ['react', 'react-dom', 'react-dom/client', 'react/jsx-runtime', 'react-router-dom'],
  'utils-vendor': ['axios', 'zustand', 'dayjs', 'cos-js-sdk-v5'],
},
```
合并后 chunk 数从 70+ 减少到 34 个。

### 7. API 请求到 `localhost:8000` 而不是 nginx 代理

**现象**：前端页面 API 请求直接到 `http://localhost:8000/api/v1/...`，返回 `ERR_CONNECTION_REFUSED`

**原因**：仍在访问 Vite 开发服务器（未停止），而非 nginx 容器。开发服务器使用默认 API URL，未使用 `VITE_API_BASE_URL=/api/v1`。

**解决方案**：
1. 停止 Vite 开发服务器
2. 通过 `http://localhost:5645` 访问 nginx 服务
3. 前端 Dockerfile 中已设置 `ENV VITE_API_BASE_URL=/api/v1`，生产构建的 API 请求会走同域 nginx 代理

### 8. 容器名冲突

**现象**：`docker-compose up -d` 报错 `Conflict. The container name "/interview-xxx" is already in use`

**原因**：旧容器未清理。

**解决方案**：
```bash
docker-compose rm -f
docker-compose up -d
```

### 9. GitHub/Gitee 登录 `oauth_failed`：容器内 DNS 解析 `EAI_AGAIN`

**现象**：GitHub/Gitee 登录在 `oauth_failed` 时报错，后端日志：
```
[auth] OAuth callback failed (gitee): TypeError: fetch failed
  [cause]: Error: getaddrinfo EAI_AGAIN gitee.com
```

**原因**：`EAI_AGAIN` 是**间歇性 DNS 解析失败**。Docker 容器默认通过内嵌 resolver `127.0.0.11` 解析，外部域名（`github.com`/`gitee.com`/`api.github.com`）由它转发给宿主机 DNS（Docker Desktop 上一般是 `192.168.65.7`），这条转发链路**不稳定**，偶发超时/失败。宿主机本机访问这些域名是通的，问题只出在"Docker 转发 DNS 查询"这一段。

> 为什么本后端（Python/httpx）并不总是报错？Python 走系统 glibc `getaddrinfo`，受 `resolv.conf` 的 `timeout`/`attempts` 保护，瞬时抖动会自动重试扛过；而 Node.js 全局 `fetch`（undici）对瞬时 `EAI_AGAIN` 会直接冒泡报错。两者都依赖同一根因，只是暴露概率不同。

**检测**（进入容器实测解析）：
```bash
docker exec interview-backend-1 cat /etc/resolv.conf
# 应看到 nameserver 127.0.0.11，ExtServers 转发宿主机 DNS

docker exec interview-backend-1 python -c "import socket; print(socket.gethostbyname_ex('github.com'))"
```

**解决方案**（已固化到 `docker-compose.yml` backend-1/backend-2）：
```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
dns:
  - 223.5.5.5        # 阿里公共 DNS
  - 119.29.29.29     # 腾讯公共 DNS
```
显式指定公共 DNS，绕开"内嵌 resolver → 宿主机 DNS"的不稳定转发链路；容器名互访仍走 `127.0.0.11`，不受影响。生效需重启 backend：
```bash
docker-compose up -d --force-recreate backend-1 backend-2
```

## 更新前端

```bash
# 1. 修改前端代码后，重新构建镜像
docker-compose build frontend

# 2. 停止 nginx，删除旧容器和卷
docker-compose stop nginx
docker rm interview-nginx
docker-compose rm -f frontend
docker volume rm interview_tool_frontend_dist

# 3. 重新创建容器
docker-compose up -d frontend nginx
```

## 更新后端

```bash
# 修改代码后重新构建并滚动更新
docker-compose build backend-1 backend-2
docker-compose up -d backend-1 backend-2 --force-recreate
```

## 连接方式

容器通过 `host.docker.internal` 连接宿主机服务（需要 Docker Desktop 支持，Windows/Mac 默认可用）：
- MySQL: `host.docker.internal:3306`
- Redis: `host.docker.internal:6379`
- RabbitMQ: `host.docker.internal:5672`
- Ollama: `host.docker.internal:11434`
