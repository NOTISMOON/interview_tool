# 数据库设计文档

> 项目：AI 面试教练（interview_tool）
> 更新日期：2026-08-17
> 修订：v1.3 — 面试模块对齐前端 v2 原型：语音回答（audio_url/时长）、追问题（is_follow_up/parent_question_id）、题目维度（category）、设备检测（device_check_passed）、时长统计（total_duration/follow_up_count）
> 数据库：MySQL 8.0+ / InnoDB
> 字符集：utf8mb4 / utf8mb4_unicode_ci

---

## 一、架构概览

### 1.1 技术栈

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   web_front   │────▶│  api_server  │────▶│    MySQL     │
│  (React SPA)  │     │  (FastAPI)   │     │  (持久化存储)  │
└──────────────┘     └──────┬───────┘     └──────────────┘
                            │
                     ┌──────▼───────┐
                     │    Redis     │
                     │ (刷新令牌缓存) │
                     └──────────────┘
```

### 1.2 认证流程

```
登录（邮箱/密码）:
  POST /auth/login  →  验证密码  →  签发 JWT(30min) + RefreshToken  →  RefreshToken 存 Redis
  
登录（GitHub OAuth）:
  GET /auth/github/callback?code=xxx  →  换 token  →  拉取用户信息  →  查 user_auth 映射
  →  签发 JWT(30min) + RefreshToken  →  RefreshToken 存 Redis

令牌刷新:
  POST /auth/refresh  →  用 RefreshToken 换新的 JWT  →  RefreshToken 轮转（旧 token 失效）

JWT 存储位置:
  前端 localStorage（短期，默认 30 分钟过期）

RefreshToken 存储位置:
  Redis（Key: refresh_token:{token_hash}，设置 TTL，如 7 天）
```

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| 无外键约束 | 所有关联由应用层保证一致性，避免外键带来的性能开销和死锁 |
| 冗余计数 | `likes_count`、`comments_count`、`following_count` 等避免频繁 COUNT |
| 联合索引 | 覆盖高频查询的筛选+排序组合，减少回表 |
| 冗余索引 | 允许冗余索引存在以提升查询性能（如 `idx_following_id` 与 `idx_following_created` 并存），以写放大换取查询速度 |
| JSON 字段 | 技能列表、教育经历、标签缓存、报告中的优势/不足等半结构化数据用 JSON 存储 |
| 软删除 | 帖子/评论使用 `status` 字段，不物理删除 |

### 2.2 `user_auth` — 用户认证方式表

```sql
CREATE TABLE `user_auth` (
  `id`               BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `user_id`          BIGINT UNSIGNED  NOT NULL COMMENT '关联 user 表',
  `provider`         TINYINT UNSIGNED NOT NULL COMMENT '1-邮箱 2-GitHub 3-QQ(预留) 4-微信(预留)',
  `provider_user_id` VARCHAR(255)     NOT NULL COMMENT '第三方平台用户唯一标识',
  `created_at`       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '绑定时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_provider_user` (`provider`, `provider_user_id`),
  KEY `idx_user_id` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='用户认证方式映射表';
```

**provider 枚举约定**：

| 值 | 含义 | `provider_user_id` 示例 |
|----|------|------------------------|
| 1 | 邮箱注册 | `user@example.com` |
| 2 | GitHub | GitHub 数字 ID，如 `12345678` |
| 3 | QQ（预留） | QQ OpenID |
| 4 | 微信（预留） | 微信 UnionID |

**索引说明**：

| 索引名 | 类型 | 字段 | 用途 |
|--------|------|------|------|
| `PRIMARY` | 主键 | `id` | 自增 ID |
| `uk_provider_user` | 唯一索引 | `(provider, provider_user_id)` | **OAuth 回调核心查询**：同平台同标识唯一 |
| `idx_user_id` | 二级索引 | `user_id` | 查某用户绑定了哪些登录方式 |

**认证流程**：

```
邮箱注册:
  ① 创建 user → ② INSERT user_auth(provider=1, provider_user_id=email)

GitHub 登录:
  ① 后端用 code 换 access_token（仅内存使用，用完即弃）
  ② 用 token 调 GitHub API 拿到 github_id / login / avatar
  ③ SELECT * FROM user_auth WHERE provider=2 AND provider_user_id='{github_id}'
  ④ 找到 → 返回该 user + 签发 JWT
  ⑤ 找不到 → 新建 user(nickname, avatar) → INSERT user_auth → 签发 JWT

已登录用户绑定第三方:
  ① INSERT user_auth(user_id, provider=3, provider_user_id) → 一个 user 可绑定多种登录方式
```

### 2.7 `interview_question` — 面试题目表

```sql
CREATE TABLE `interview_question` (
  `id`                 BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `interview_id`       BIGINT UNSIGNED  NOT NULL,
  `question_no`        INT UNSIGNED     NOT NULL COMMENT '题号（追问题与父题目同号，靠 is_follow_up 区分）',
  `question_type`      TINYINT UNSIGNED NOT NULL COMMENT '1-技术题 2-项目题 3-行为题',
  `category`           TINYINT UNSIGNED DEFAULT NULL COMMENT '题目维度 1-技术基础 2-项目经验 3-综合素质 4-架构设计（与 question_type 正交）',
  `is_follow_up`       TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '是否追问题 0-否 1-是',
  `parent_question_id` BIGINT UNSIGNED  DEFAULT NULL COMMENT '父题目ID（追问关联，指向本表 id；非追问题为 NULL）',
  `question_text`      TEXT             NOT NULL,
  `user_answer`        TEXT             DEFAULT NULL COMMENT '用户回答（语音转写文本或占位说明）',
  `audio_url`          VARCHAR(512)     DEFAULT NULL COMMENT '语音回答文件地址（前端录音上传后的存储路径）',
  `answer_duration`    INT UNSIGNED     DEFAULT NULL COMMENT '回答时长（秒，录音计时）',
  `thinking_duration`  INT UNSIGNED     DEFAULT NULL COMMENT '思考时长（秒，思考倒计时实际用时）',
  `ai_score`           TINYINT UNSIGNED DEFAULT NULL COMMENT 'AI评分 1-5',
  `ai_comment`         TEXT             DEFAULT NULL COMMENT 'AI评价',
  `created_at`         DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`         DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_interview_id` (`interview_id`),
  KEY `idx_interview_no` (`interview_id`, `question_no`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='面试题目表';
```

**`category` 枚举约定**（题目维度，与 `question_type` 题型正交）：

| 值 | 维度 | 典型 `question_type` |
|----|------|---------------------|
| 1 | 技术基础 | 技术题 |
| 2 | 项目经验 | 项目题 |
| 3 | 综合素质 | 行为题 |
| 4 | 架构设计 | 技术题 |

> 同一维度可包含不同题型，例如「架构设计」维度下既有技术题（微前端原理）也可能有项目题（系统设计案例）。`category` 可空，未分类时按 `question_type` 推断。

**追问关联说明**：
- `is_follow_up=1` 表示该题为追问题，`parent_question_id` 指向被追问的父题目（同表 `id`）。
- 追问题与父题目共享 `question_no`（如第 4 题的追问也为 `question_no=4`），展示时靠 `is_follow_up` 与 `created_at` 顺序区分。
- 应用层保证一致性，不建外键；删除父题目时需级联处理其追问（当前业务不删除题目）。

**索引说明**：

| 索引名 | 类型 | 字段 | 用途 |
|--------|------|------|------|
| `PRIMARY` | 主键 | `id` | 题目 ID |
| `idx_interview_id` | 二级索引 | `interview_id` | 按面试会话查所有题目 |
| `idx_interview_no` | 联合索引 | `(interview_id, question_no)` | 按题号排序获取当前题目 |

> `category`、`is_follow_up`、`parent_question_id` 通常随会话批量读取（已由 `idx_interview_id` 覆盖），无独立查询需求，故不新增索引。

### 2.9 `post` — 帖子表

```sql
CREATE TABLE `post` (
  `id`             BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `author_id`      BIGINT UNSIGNED  NOT NULL COMMENT '作者 ID',
  `title`          VARCHAR(255)     NOT NULL,
```

**索引说明**：

| 索引名 | 类型 | 字段 | 用途 |

## 五、Redis 键设计

| 键格式 | 类型 | TTL | 说明 |
|--------|------|-----|------|
| `refresh_token:{token_hash}` | String | 7天 | 存储刷新令牌，值包含 user_id |

## 六、开发注意事项

1. **user_auth 查询**：OAuth 回调时使用 `uk_provider_user` 唯一索引，时间复杂度 O(1)
2. **帖子计数**：`likes_count` / `comments_count` 等冗余字段，插入/删除点赞时需同步更新帖子表
3. **关注计数**：`following_count` / `followers_count` 在 user_follow 表变更时同步更新
4. **dm_conversation 约定**：插入时保证 `user1_id < user2_id`，查询某用户会话时需同时查 `user1_id` 和 `user2_id` 两个方向（此约定属于 `dm_conversation` 表，与 `user_auth` 无关）
5. **标签存储（冗余缓存）**：`post_tag` 关联表为标签筛选的唯一数据源（按标签查帖子走 `idx_tag`）；`post.tags` JSON 为展示用冗余缓存（避免列表查询 JOIN）。两者在应用层事务内双写保证一致，冗余以换取列表查询性能
6. **简历教育经历**：`resume.parsed_education` 以 JSON 数组存储，支持多段教育经历（本科/硕士/博士）；前端如仅需展示首条可取数组首元素
7. **JSON 字段**：`parsed_skills`、`parsed_education`、`strengths` 等 JSON 字段，如果查询频繁可考虑使用 MySQL 8.0 的虚拟列+索引
8. **消息派生字段**：前端 `Message` 的 `link`、`actionLabel`、`actionLink` 为 UI 派生字段，由前端根据 `type` 与 `related_type` 映射生成，不入库；`relatedContent` 由 `related_id` + `related_type` JOIN 派生
9. **浏览量去重**：`views_count` 通过 Redis `post:view:dedupe:{post_id}:{user_id}` 做用户级去重，未命中才累加，防止刷量
10. **在线状态**：用户在线状态由 Redis `online:user:{user_id}` 维护（60 秒心跳续期），不入 MySQL
11. **分页**：所有按时间排序的列表查询建议使用游标分页（`WHERE created_at < ?`）而非 OFFSET，避免深分页性能问题
12. **面试语音回答**（v1.3）：`interview_question.audio_url` 为录音文件存储地址，`user_answer` 存语音转写文本（或前端占位说明）；`answer_duration` 为录音计时，`thinking_duration` 为思考倒计时实际用时。录音文件建议存对象存储（OSS/MinIO），DB 仅存地址。
13. **追问关联**（v1.3）：追问题 `is_follow_up=1`，`parent_question_id` 指向父题目（同表 `id`，应用层保证，不建外键）；追问题与父题目共享 `question_no`，展示靠 `is_follow_up` + `created_at` 排序区分。
14. **面试统计冗余**（v1.3）：`interview.follow_up_count` / `total_duration` 与 `interview_report.follow_up_count` / `total_duration` 为冗余字段，面试完成时由面试会话汇总写入报告，列表展示免聚合。
