## 一、模块概述

提供关注列表与粉丝列表的游标分页查询，读路径采用 **ZSET 分页 + SET 关系判断 + DB 批量详情** 的组合方案，目标为极致读性能（缓存命中时 3 次网络往返，约 2~4ms）。

### 1.1 接口清单

| 接口 | 路径 | 认证 | 说明 |
|------|------|------|------|
| 我的关注列表 | `GET /api/v1/users/me/following` | 必须登录 | 游标分页 + 互关标记 |
| 我的粉丝列表 | `GET /api/v1/users/me/followers` | 必须登录 | 游标分页 + 互关标记 |
| 他人关注列表 | `GET /api/v1/users/{user_id}/following` | 可选（游客可访问） | 受属主资料可见性限制 |
| 他人粉丝列表 | `GET /api/v1/users/{user_id}/followers` | 可选（游客可访问） | 受属主资料可见性限制 |

**查询参数**（4 个接口一致）：

| 参数 | 类型 | 约束 | 说明 |
|------|------|------|------|
| `cursor` | int | ≥ 0，可选 | 上一页 `next_cursor`（followed_at 毫秒时间戳），首页不传 |
| `page_size` | int | 1~100，默认 20 | 页大小 |

**响应结构**（`FollowListResponse`）：

```json
{
  "items": [
    {
      "id": 2,
      "nickname": "张三",
      "avatar": "https://...",
      "bio": "...",
      "location": "上海",
      "followed_at": "2026-08-18T10:30:00",
      "is_following": true,
      "is_mutual": false
    }
  ],
  "next_cursor": 1755508200000,
  "following_count": 42,
  "followers_count": 17,
  "restricted": false
}
```

## 二、Redis 键设计

| 键 | 类型 | 内容 | 用途 |
|----|------|------|------|
| `follow:z:following:{user_id}` | ZSET | score=关注时间毫秒时间戳，member=被关注者ID | 关注列表游标分页 |
| `follow:z:followers:{user_id}` | ZSET | score=关注时间毫秒时间戳，member=粉丝ID | 粉丝列表游标分页 |
| `follow:s:following:{user_id}` | SET | 全部被关注者ID | 批量判断"访问者是否关注TA" |
| `follow:s:followers:{user_id}` | SET | 全部粉丝ID | 批量判断"TA是否关注访问者" |
| `follow:empty:{direction}:{user_id}` | STRING | `"1"` | 空列表防穿透标记（TTL 60s） |
| `user:profile:{user_id}` | STRING | 资料JSON | 可见性校验与计数来源（已有） |

**ZSET 与 SET 双存的理由**：ZSET 管有序分页（`ZREVRANGEBYSCORE`），SET 管批量关系判断（`SMISMEMBER` 仅 SET 支持）。冗余一份数据换取读路径极致性能。

**配置项**：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `FOLLOW_CACHE_TTL` | 86400（1天） | ZSET/SET 有效期 |
| `FOLLOW_ZSET_REBUILD_LIMIT` | 1000 | ZSET 回源条数（超出部分读时降级DB） |
| `FOLLOW_EMPTY_MARK_TTL` | 60 | 空标记有效期 |

## 三、读路径流程

```
GET /users/{user_id}/following?cursor=...&page_size=20
              │ viewer_id 来自Cookie（游客为None）
              ▼
┌────────────────────────────────────────────────────────────┐
│ Step 1  可见性校验（复用 user_service.get_public_profile，  │
│         走 user:profile:{id} 资料缓存）                     │
│   - 用户不存在/已注销/visibility=2        → 404            │
│   - visibility=1 且访问者未关注           → restricted响应  │
│     （items为空，仅返回计数）                                │
│   - visibility=0 / 本人 / 关注者           → 放行           │
└────────────────────────────────────────────────────────────┘
              ▼
┌────────────────────────────────────────────────────────────┐
│ Step 2  ZSET 游标分页（1次Redis往返）                       │
│   ZREVRANGEBYSCORE follow:z:following:{uid}                │
│       ({cursor} | +inf)  -inf  LIMIT 0 (size+1)            │
│   - ZSET不存在 → 检查空标记：                               │
│       * 有标记 → 直接返回空页（防穿透）                      │
│       * 无标记 → 回源重建（见第四节）后重查                  │
│   - 多取1条判定 has_more                                    │
└────────────────────────────────────────────────────────────┘
              ▼
┌────────────────────────────────────────────────────────────┐
│ Step 2b ZSET尽头判定（仅ZSET返回不足时，追加1次ZCARD）       │
│   has_more = (返回条数 > size)                             │
│              or (zcard < user冗余计数 → DB还有更老数据)      │
│   - ZSET本页为空 且 cursor非空 且 zcard<计数                │
│     → 降级DB补页（老数据低频访问，性能不敏感）               │
└────────────────────────────────────────────────────────────┘
              ▼
┌────────────────────────────────────────────────────────────┐
│ Step 3  DB批量详情（1次往返，主键IN）                        │
│   SELECT ... FROM user WHERE id IN (...)                   │
│   AND status IN (0,1)          ← 过滤注销用户               │
└────────────────────────────────────────────────────────────┘
              ▼
┌────────────────────────────────────────────────────────────┐
│ Step 4  SET批量互关判断（1次Redis pipeline）                 │
│   SMISMEMBER follow:s:following:{viewer} id1..id20         │
│   SMISMEMBER follow:s:followers:{viewer}  id1..id20        │
│   is_following[i] = 结果1[i]                               │
│   is_mutual[i]    = 结果1[i] AND 结果2[i]                  │
└────────────────────────────────────────────────────────────┘
              ▼
       组装 items + next_cursor（基于ZSET原始行，
       而非过滤注销用户后的items，防止游标回退死循环）
```

**性能**：缓存命中时 1 Redis（分页）+ 1 DB（批量）+ 1 Redis pipeline（互关）≈ 2~4ms。

## 四、回源重建策略

ZSET 不存在时（冷启动 / TTL 过期 / Redis 清空），从 DB 回源：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | double-check ZSET 是否存在 | 并发请求可能已重建 |
| 2 | 进程内 per-key 锁（singleflight） | 防缓存击穿 |
| 3 | `fetch_recent_following/followers(limit=1000)` | ZSET 部分回源（走覆盖索引） |
| 4 | `fetch_all_following/follower_ids()` | SET 全量回源（保证关系判断准确） |
| 5 | pipeline：ZADD + EXPIRE + SADD + EXPIRE | 原子批量写入 |
| 6 | 无任何记录时 SETEX 空标记（60s） | 防空列表穿透 |

**为什么 ZSET 部分回源、SET 全量回源**：
- ZSET 只服务分页，最近 1000 条覆盖绝大多数访问；更老数据走 DB 降级，避免大 V 全量回源阻塞。
- SET 服务关系判断，漏一个成员就漏报（"已关注却显示未关注"），必须全量。

**自愈性**：回源以 DB 为准，任何 Redis 侧的脏数据在 TTL 过期后自然修正；Outbox/MQ 上线前，短期不一致靠该机制兜底。

## 五、降级策略（ZSET 部分回源的尽头）

ZSET 只缓存最近 `FOLLOW_ZSET_REBUILD_LIMIT`（1000）条。关注数超过该值的用户翻页到 ZSET 尽头后：

1. 判定条件：本页 ZSET 返回空 且 `cursor` 非空 且 `zcard < user.following_count`（冗余计数）
2. 降级执行：`fetch_following_page_from_db(user_id, before=cursor时间, limit=size+1)`
   - JOIN user 表过滤注销用户，命中 `idx_follower_created` 覆盖索引
3. 下一页游标从 DB 行的 `created_at` 计算，继续走 DB 路径直到翻完

## 六、可见性规则

| 属主可见性 | 本人 | 关注者 | 其他人/游客 |
|-----------|------|--------|-------------|
| 公开(0) | 完整列表 | 完整列表 | 完整列表 |
| 仅关注者(1) | 完整列表 | 完整列表 | `restricted=true`，items为空，仅返回计数 |
| 仅自己(2) | 完整列表 | 404 | 404 |

- 判断"访问者是否关注属主"复用 `user_service.get_public_profile`（DB 唯一索引查询，仅对 visibility=1 用户触发，频率低）。
- 游客（无Cookie或token无效）：`viewer_id=None`，`is_following`/`is_mutual` 全为 `false`。

## 七、边界情况检查清单（重点）

> 对 ZSET+SET 方案实现前的设计评审结论逐项复核。状态：✅ 已处理 / ⚠️ 已知限制（有缓解） / 📋 遗留项（Outbox 上线时处理）

### 7.1 缓存生命周期类

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-1 | ZSET 不存在（冷启动/TTL过期/Redis清空） | 每次请求都打DB | 回源重建（DB为准，自愈） | ✅ |
| B-2 | 并发请求同时发现 ZSET 缺失 | 缓存击穿，重复回源 | 进程内 per-key 锁 + double-check 单飞 | ✅ |
| B-3 | 多进程/多实例部署 | 进程内锁失效，各进程各回源一次 | 语义仍正确（幂等ZADD），仅浪费少量DB查询；需严格防护时升级 Redis 分布式锁 | ⚠️ |
| B-4 | 用户关注数为 0 | 每次请求回源DB空查询 | 空标记 `follow:empty:*`（TTL 60s）防穿透 | ✅ |
| B-5 | 空标记有效期内发生新关注 | 60秒内列表显示为空 | 业务可接受的最终一致（Outbox 上线后可在写路径 DEL 空标记） | ⚠️ |
| B-6 | TTL 期间 ZSET 与 DB 新增数据不一致（无写路径维护时） | 列表缺最新关注 | 回源以 DB 为准 + TTL 1天自然过期；Outbox 上线后写路径实时维护 | ⚠️ |

### 7.2 游标分页类

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-7 | 同一秒内多条关注记录（`created_at` 为 DATETIME 秒级精度，score 同值） | 翻页时 `(score` 排他区间可能丢失同秒内后续记录 | 概率低（单用户同一秒关注多人）；演进方案：`created_at` 升级 `DATETIME(3)` 或游标改 `(score, member)` 双元组 | ⚠️ |
| B-8 | 本页含已注销用户（ZSET 残留 member） | 过滤后 items 少于 page_size | 正常过滤；`next_cursor` 基于 ZSET **原始行**计算而非过滤后 items，防止游标回退死循环 | ✅ |
| B-9 | ZSET 部分回源（1000条）后翻页到尽头 | 第 1001 条之后数据不可见 | 尽头判定（zcard < 冗余计数）→ 自动降级 DB 补页 | ✅ |
| B-10 | 注销用户残留使 zcard 虚高 | 降级判定偏保守（少触发），深页可能缺数据 | 影响极小（需同时满足：注销残留 + 关注数>1000 + 翻到深页）；Outbox 注销事件清理后消除 | ⚠️ |
| B-11 | 游标/页大小参数非法 | 异常查询 | `cursor ≥ 0`、`page_size` 1~100 由 Query 约束 | ✅ |

### 7.3 用户状态类

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-12 | 列表成员已注销（status=2） | 展示失效账号 | 批量详情查询过滤 `status IN (0,1)`，DB 降级路径 JOIN 过滤 | ✅ |
| B-13 | 列表属主已注销 | 数据泄露 | 可见性校验第一步即 404 | ✅ |
| B-14 | 注销账号只清了 DB 与资料缓存，**未清 follow ZSET/SET** | SET 关系判断误报"已关注注销用户"（如私信前置校验场景） | 读路径已过滤展示；Outbox 上线后注销事件需发 MQ 清理该用户 4 个键 + 所有关联用户的键 | 📋 |
| B-15 | 访问者 token 残留（注销后 30 分钟内） | 已注销用户读公开数据 | 危害极小（仅读），不做拦截 | ⚠️ |

### 7.4 关系判断类（SET）

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-16 | 访问者的 SET 从未回源（未访问过自己的关注/粉丝列表） | `SMISMEMBER` 对不存在的键返回全 false → `is_following` 漏报 | **已修复（实测发现）**：rebuild 时当前方向与对方向 SET 均全量回源，首次访问即互关判断正确；Outbox 上线后由写路径常驻维护 | ✅ |
| B-17 | SMISMEMBER 成员类型 | Redis member 恒为字符串，int 不匹配恒 false | 入参与回源统一 `str(id)` | ✅ |
| B-18 | DB 批量 IN 查询结果乱序 | 列表项顺序错乱 | 查询结果转 `{id: User}` 字典，按 ZSET 顺序重排 | ✅ |
| B-19 | 游客访问 | 无身份可判 | `viewer_id=None` 时 flags 直接全 false，不发起 Redis 调用 | ✅ |

### 7.5 一致性类（Outbox + MQ 规划）

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-20 | DB 事务提交 → MQ 消费完成之间存在窗口 | 刚关注的人列表里暂时看不到 | 最终一致（秒级延迟），社交列表场景业务可接受 | ⚠️ |
| B-21 | MQ 消费失败 / 消息丢失 | ZSET/SET 永久缺数据 | Outbox 表重试投递；TTL 过期回源 DB 自愈兜底 | 📋 |
| B-22 | 回源重建与 MQ 消费并发（同 member 同 score） | 数据重复或覆盖错乱 | ZADD 幂等（同 member 同 score 覆盖为相同值），EXPIRE 仅刷新TTL，安全 | ✅ |

### 7.6 其他

| 编号 | 边界场景 | 风险 | 处理方式 | 状态 |
|------|---------|------|---------|------|
| B-23 | 时区：`created_at` naive datetime ↔ 毫秒时间戳往返 | 时间偏移 | 存取均按应用服务器本地时区（`timestamp()` / `fromtimestamp()` 对称），单机部署一致；多时区部署需统一 UTC | ⚠️ |
| B-24 | 关注自己 / 重复关注 | 脏数据 | 读路径不涉及；后续关注/取关写接口由业务校验 + `uk_follower_following` 唯一索引兜底 | 📋 |
| B-25 | 冗余计数与真实行数偏差（历史脏数据） | B-9 降级判定误差 | 计数仅用于降级启发式判定，不影响正确性主路径 | ⚠️ |
| B-26 | FastAPI 路由注册顺序：`/users/me/following` 若注册在 `/users/{user_id}/following` 之后 | 路径 "me" 被 `{user_id}` 捕获 → int 解析失败返回 422（**实测发现**） | `/me/*` 路由全部注册在 `/{user_id}/*` 之前，并在代码注释中标注约束 | ✅ |

## 八、一致性保证规划（Outbox + MQ，写路径）

读路径已就绪，写路径（关注/取关接口）按以下模式实现，届时 B-5/B-6/B-14/B-16/B-21 自然闭环：

```
follow 请求:
  DB 单事务内:
    1. INSERT user_follow
    2. INSERT outbox_event(type=follow_created, follower_id, following_id, created_at)
    3. UPDATE user.following_count+1 / user.followers_count+1
    4. INSERT user_activity(type=3)
  事务提交 → 返回 200

MQ Consumer（异步）:
  读 outbox → pipeline 同步 Redis:
    ZADD follow:z:following:{A} {ts_ms} {B}
    ZADD follow:z:followers:{B} {ts_ms} {A}
    SADD  follow:s:following:{A} {B}
    SADD  follow:s:followers:{B} {A}
    DEL   follow:empty:following:{A} / follow:empty:followers:{B}
  成功后删除/标记 outbox 事件

unfollow 对称：ZREM/SREM + 计数-1（注意 INT UNSIGNED 溢出，需 CAST，参见
user_repository.decrement_followers_count 的既有实现）

注销（delete_account）追加：
  发 outbox_event(type=user_deactivated) → Consumer 批量清理：
    - 该用户自身 4 个键
    - 其关注者的 followers SET 中的该用户、其粉丝的 following SET 中的该用户
    - 对应 ZSET 成员（ZREM）
```

## 九、量级边界与演进路线

| 量级 | 表现 | 演进方案 |
|------|------|---------|
| 关注数 ≤ 1万（当前） | 全链路毫秒级 | 无需演进 |
| 关注数 > 10万 | SET 全量回源变慢（秒级） | 分批 SADD（pipeline 每 1万 一批）；或 SET 只存近期+活跃，长尾走 DB 唯一索引判断 |
| 粉丝数 > 100万 | ZSET 部分回源仍可控，但 DB 降级深页变慢 | ZSET 分层（热区 Redis + 冷区 DB）；`created_at` 升级毫秒精度消除 B-7 |
| QPS > 1万 | 单 Redis 成为瓶颈 | Redis Cluster 按 user_id 分片；读副本 |
