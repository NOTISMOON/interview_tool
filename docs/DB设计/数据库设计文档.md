## 一、架构概览

### 1.1 技术栈

```
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│   web_front   │────▶│  api_server  │────▶│    MySQL     │
│  (React SPA)  │     │  (FastAPI)   │     │  (持久化存储)  │
└──────────────┘     └──────┬───────┘     └──────────────┘
                            │
                     ┌──────▼───────┐
                     │    Redis     │
                     │ (刷新令牌缓存) │
                     └──────────────┘
```

### 1.2 认证流程

```
登录（GitHub OAuth，目前唯一登录方式）:
  GET /api/v1/auth/github/login  →  返回 GitHub 授权 URL
  授权完成后 POST /api/v1/auth/github/callback {code}  →  换 token → 拉取用户信息
  → 查 user_auth 映射（provider=2）→ 未命中则创建 user + user_auth（即自动注册）
  → 签发 access_token(JWT,30min) + refresh_token(7天) → 写入 HttpOnly Cookie

令牌刷新:
  POST /api/v1/auth/refresh（浏览器自动携带 refresh_token Cookie）
  → Redis 校验（refresh_token:{sha256}，值内含 jti）→ 轮转签发新 Token 对 → 写回 Cookie

退出登录:
  POST /api/v1/auth/logout  →  删除 Redis 中的 refresh_token + 清除 Cookie（幂等）

单设备登录（v1.7 新增）:
  ① 登录/刷新时在 Redis 维护 auth:active_jti:{user_id} = 当前会话 jti（TTL=access 有效期）
  ② 新设备登录发现已有旧 jti → 向 notify:push:{user_id} 推送 session_kicked 事件（SSE 顶号通知）
  ③ 中间件与 refresh 均校验 jti：旧设备的 access/refresh 一律 401，杜绝两设备互相顶号死循环

开发环境: GET /api/v1/auth/dev-login?user_id=22（仅 settings.DEBUG=True 时可用，生产返回 404）

JWT 存储位置:
  HttpOnly Cookie（JS 不可读，access_token Path=/；refresh_token Path=/api/v1/auth 缩小暴露面）

RefreshToken 存储位置:
  Redis（Key: refresh_token:{sha256(token)}，Value JSON 含 user_id/login/jti/created_at，TTL 7 天）
```

### 1.3 设计原则

| 原则      | 说明                                                                                                            |
| ------- | ------------------------------------------------------------------------------------------------------------- |
| 无外键约束   | 所有关联由应用层保证一致性，避免外键带来的性能开销和死锁                                                                                  |
| 冗余计数    | `likes_count`、`comments_count`、`following_count` 等避免频繁 COUNT                                                  |
| 联合索引    | 覆盖高频查询的筛选+排序组合，减少回表                                                                                           |
| 冗余索引    | 允许冗余索引存在以提升查询性能，以写放大换取查询速度；但被联合索引最左前缀完全覆盖的单字段索引除外（如 v1.4 删除的 `idx_following_id`，被 `idx_following_created` 覆盖） |
| JSON 字段 | 技能列表、教育经历、标签缓存、报告中的优势/不足等半结构化数据用 JSON 存储                                                                      |
| 软删除     | 帖子/评论使用 `status` 字段，不物理删除                                                                                     |

### 2.2 `user_auth` — 用户认证方式表

```sql
CREATE TABLE `user_auth` (
  `id`               BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `user_id`          BIGINT UNSIGNED  NOT NULL COMMENT '关联 user 表',
  `provider`         TINYINT UNSIGNED NOT NULL COMMENT '1-邮箱 2-GitHub 3-QQ(预留) 4-微信(预留)',
  `provider_user_id` VARCHAR(255)     NOT NULL COMMENT '第三方平台用户唯一标识',
  `created_at`       DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '绑定时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_provider_user` (`provider`, `provider_user_id`),
  KEY `idx_user_id` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='用户认证方式映射表';
```

**provider 枚举约定**：

| 值 | 含义     | `provider_user_id` 示例     |
| - | ------ | ------------------------- |
| 1 | 邮箱注册   | `user@example.com`        |
| 2 | GitHub | GitHub 数字 ID，如 `12345678` |
| 3 | QQ（预留） | QQ OpenID                 |
| 4 | 微信（预留） | 微信 UnionID                |

**索引说明**：

| 索引名                | 类型   | 字段                             | 用途                        |
| ------------------ | ---- | ------------------------------ | ------------------------- |
| `PRIMARY`          | 主键   | `id`                           | 自增 ID                     |
| `uk_provider_user` | 唯一索引 | `(provider, provider_user_id)` | **OAuth 回调核心查询**：同平台同标识唯一 |
| `idx_user_id`      | 二级索引 | `user_id`                      | 查某用户绑定了哪些登录方式             |

**认证流程**：

```
邮箱注册:
  ① 创建 user → ② INSERT user_auth(provider=1, provider_user_id=email)

GitHub 登录:
  ① 后端用 code 换 access_token（仅内存使用，用完即弃）
  ② 用 token 调 GitHub API 拿到 github_id / login / avatar
  ③ SELECT * FROM user_auth WHERE provider=2 AND provider_user_id='{github_id}'
  ④ 找到 → 返回该 user + 签发 JWT
  ⑤ 找不到 → 新建 user(nickname, avatar) → INSERT user_auth → 签发 JWT

已登录用户绑定第三方:
  ① INSERT user_auth(user_id, provider=3, provider_user_id) → 一个 user 可绑定多种登录方式
```

### 2.4 `resume` — 简历表

```sql
CREATE TABLE `resume` (
  `id`                      BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `user_id`                 BIGINT UNSIGNED  NOT NULL,
  `file_name`               VARCHAR(255)     NOT NULL COMMENT '原始文件名',

  `is_deleted`              TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '软删除标记 0-否 1-是',
  `deleted_at`              DATETIME         DEFAULT NULL COMMENT '软删除时间',
```

**索引说明**：

| 索引名                 | 类型   | 字段                     | 用途                                             |

| 3 | 综合素质 | 行为题                |
| 4 | 架构设计 | 技术题                |

> 同一维度可包含不同题型，例如「架构设计」维度下既有技术题（微前端原理）也可能有项目题（系统设计案例）。`category` 可空，未分类时按 `question_type` 推断。

**追问关联说明**：

- `is_follow_up=1` 表示该题为追问题，`parent_question_id` 指向被追问的父题目（同表 `id`）。

- 追问题与父题目共享 `question_no`（如第 4 题的追问也为 `question_no=4`），展示时靠 `is_follow_up` 与 `created_at` 顺序区分。

- 应用层保证一致性，不建外键；删除父题目时需级联处理其追问（当前业务不删除题目）。

**索引说明**：

| 索引名                | 类型   | 字段                            | 用途          |
| ------------------ | ---- | ----------------------------- | ----------- |
| `PRIMARY`          | 主键   | `id`                          | 题目 ID       |
| `idx_interview_id` | 二级索引 | `interview_id`                | 按面试会话查所有题目  |
| `idx_interview_no` | 联合索引 | `(interview_id, question_no)` | 按题号排序获取当前题目 |

> `category`、`is_follow_up`、`parent_question_id` 通常随会话批量读取（已由 `idx_interview_id` 覆盖），无独立查询需求，故不新增索引。

#### 2.10.1 设计思路：数据库层面不区分"评论"和"回复"

**核心原则**：数据库层面不区分"评论"和"回复"，它们都是 `comment` 记录。区别只在于 `root_id` 和 `reply_user_id`。

**示例数据**：

用户 A 评论帖子：

| id | post\_id | root\_id | author\_id | reply\_user\_id | content |
| -- | -------- | -------- | ---------- | --------------- | ------- |
| 1  | 100      | NULL     | A          | NULL            | 这个视频不错  |

B 回复 A：

| id | post\_id | root\_id | author\_id | reply\_user\_id | content |
| -- | -------- | -------- | ---------- | --------------- | ------- |
| 2  | 100      | 1        | B          | A               | 确实不错    |

C 回复 B（**注意：`root_id=1`，而非** **`root_id=2`**）：

| id | post\_id | root\_id | author\_id | reply\_user\_id | content |
| -- | -------- | -------- | ---------- | --------------- | ------- |
| 3  | 100      | 1        | C          | B               | 我也觉得    |

**逻辑树结构**：

```text
A (id=1, root_id=NULL)
├── B (id=2, root_id=1, reply_user_id=A)
└── C (id=3, root_id=1, reply_user_id=B)
```

**前端展示**：

```text
A:
这个视频不错

B:
确实不错

C 回复 @B:
我也觉得
```

#### 2.10.2 查询逻辑

**查询帖子的一级评论**（`comments_count` 统计对象）：

```sql
SELECT * FROM comment
WHERE post_id = 100
  AND root_id IS NULL
  AND status = 1
ORDER BY created_at DESC;
```

**查询某条一级评论的所有回复**：

```sql
SELECT * FROM comment
WHERE root_id = 1
  AND status = 1
ORDER BY created_at ASC;
```

**整体结构**：

```text
帖子

一级评论 A
    ├── B
    ├── C 回复 B
    └── D 回复 C

一级评论 E
    ├── F
```

> `root_id` 决定属于哪个评论线程，`reply_user_id` 决定回复显示对象。这是抖音、微博、小红书等评论系统常见的设计方式——牺牲无限树结构，换来了简单查询、容易分页、容易缓存。

#### 2.10.3 后端创建回复的逻辑

**前端请求**（只传被回复的评论 ID）：

```json
{
  "reply_comment_id": 2,
  "content": "我也觉得"
}
```

**后端处理**（不要让前端传 `root_id` 和 `reply_user_id`，防止用户乱传）：

```python
# 1. 查询被回复的评论
comment = db.query(Comment).filter(Comment.id == reply_comment_id).first()

# 2. 创建回复记录
new_reply = Comment(
    post_id=comment.post_id,
    author_id=current_user_id,

    # 永远找到最顶部评论（一级评论）
    root_id=comment.root_id or comment.id,

    # 回复谁 → 前端展示 "回复 @xxx"
    reply_user_id=comment.author_id,

    content=content,
)

# 3. 更新一级评论的 reply_count
if root_comment := db.query(Comment).filter(Comment.id == new_reply.root_id).first():
    root_comment.reply_count += 1

# 4. 更新帖子的 comments_count
post.comments_count += 1
```

**索引说明**：

| `uk_follower_following` | 唯一索引 | `(follower_id, following_id)`     | 防止重复关注 + 判断关注关系（互关校验） |
| `idx_follower_created`  | 联合索引 | `(follower_id, created_at DESC)`  | 关注列表：查"我关注了谁"并按关注时间倒序 |
| `idx_following_created` | 联合索引 | `(following_id, created_at DESC)` | 粉丝列表：查"谁关注了我"并按关注时间倒序 |

> v1.4 变更：原 `idx_following_id`（单字段）被 `idx_following_created` 最左前缀完全覆盖，属纯冗余索引已删除；新增 `idx_follower_created` 补齐关注列表的排序索引，两个方向的列表查询至此完全对称且均走索引。

**设计说明：不存储"相互关注"（`is_mutual`）字段**

互关是双向派生状态，若落库需在每次 follow/unfollow 时双写两条记录并维护一致性（写放大2\~3倍、事务复杂度翻倍）。本设计将互关判断下放至 Redis SET：

- 判断方式：`SMISMEMBER follow:s:following:{A} B`（A是否关注B）与 `SMISMEMBER follow:s:followers:{A} B`（B是否关注A，即A的粉丝中是否有B）组合，O(1)。

- 列表场景批量判断：1 次 pipeline 内 2 次 `SMISMEMBER` 覆盖整页 20 条。

- 兜底：Redis 不可用时按 `uk_follower_following` 唯一索引查库判断。

**关联 Redis 缓存键**（关注/粉丝列表读路径，详见 `docs/功能模块流程.md`）：

| 键                                    | 类型                                  | 说明                     |
| ------------------------------------ | ----------------------------------- | ---------------------- |
| `follow:z:following:{user_id}`       | ZSET（score=关注时间毫秒时间戳，member=被关注者ID） | 关注列表游标分页，部分回源（最近1000条） |
| `follow:z:followers:{user_id}`       | ZSET（同上，member=粉丝ID）                | 粉丝列表游标分页，部分回源          |
| `follow:s:following:{user_id}`       | SET（全部被关注者ID）                       | "我是否关注TA"批量判断，全量回源     |
| `follow:s:followers:{user_id}`       | SET（全部粉丝ID）                         | "TA是否关注我"批量判断，全量回源     |
| `follow:empty:{direction}:{user_id}` | STRING                              | 空列表防穿透标记（短TTL）         |

### 2.20 `outbox_event` — Transactional Outbox 事件表

```sql
CREATE TABLE `outbox_event` (
  `id`              BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `event_type`      VARCHAR(50)      NOT NULL COMMENT '事件类型：follow_created/follow_deleted/user_deactivated',
  `aggregate_type`  VARCHAR(50)      NOT NULL COMMENT '聚合根类型：user_follow/user',
  `aggregate_id`    VARCHAR(64)      NOT NULL COMMENT '聚合根标识（user_follow为follower_id:following_id，user为user_id）',
  `payload`         JSON             NOT NULL COMMENT '事件负载（含实体字段快照，消费端免回查）',
  `status`          TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0-待发布 1-已发布 2-死信（重试超限）',
  `retry_count`     INT UNSIGNED     NOT NULL DEFAULT 0 COMMENT '投递重试次数',
  `next_retry_at`   DATETIME         DEFAULT NULL COMMENT '下次允许重试时间（指数退避），NULL表示立即可投',
  `created_at`      DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `published_at`    DATETIME         DEFAULT NULL COMMENT '成功发布到MQ的时间',
  PRIMARY KEY (`id`),
  KEY `idx_status_retry` (`status`, `next_retry_at`, `id`),
  KEY `idx_published` (`status`, `published_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='Transactional Outbox事件表（业务变更与事件写入同一事务，Relay轮询投递到MQ）';
```

**设计要点**：

- **事务一致性**：业务变更与事件写入同一个本地事务，事务提交即保证事件不丢。

- **全局有序**：`id` 自增 = 全局事件序号，Relay 按 `id ASC` 批量投递保证顺序。

- **通用基础设施**：不与 `user_follow` 耦合字段，业务字段全部在 `payload` JSON 中，后续帖子点赞、评论等事件直接复用该表。

- **指数退避**：`next_retry_at` 为下次允许重试时间，投递失败后按 `2^retry_count` 秒退避。

**索引说明**：

| 索引名                | 类型   | 字段                            | 用途                  |
| ------------------ | ---- | ----------------------------- | ------------------- |
| `PRIMARY`          | 主键   | `id`                          | 全局事件序号，Relay 按此顺序投递 |
| `idx_status_retry` | 联合索引 | `(status, next_retry_at, id)` | Relay 轮询扫描待发布事件     |
| `idx_published`    | 联合索引 | `(status, published_at)`      | 清理任务删除超期已发布事件       |

## 五、Redis 键设计

> v1.7 按当前实现全面补全。所有键均在 `app/redis/`、`app/cache/`、`app/services/` 中定义，键分隔符统一使用 `:`（注意：关注缓存曾用 `/`，现统一为 `:`）。

### 5.1 认证与会话

| 键格式                             | 类型           | TTL               | 说明                                                  |
| ------------------------------- | ------------ | ----------------- | --------------------------------------------------- |
| `refresh_token:{sha256(token)}` | String(JSON) | 7天                | 刷新令牌，值含 `{user_id, login, jti, created_at}`，轮转即删旧写新 |
| `auth:active_jti:{user_id}`     | String       | access 有效期(30min) | 单设备登录：当前活跃会话 jti；新登录覆盖旧值并触发 `session_kicked` 推送     |
| `user:deactivated:{user_id}`    | String       | 7天                | 注销吊销标记，refresh 续签时校验，存在则拒绝并删除 refresh\_token        |
| `user:profile:{user_id}`        | String(JSON) | 30分钟              | 用户完整资料缓存（Cache-Aside）                               |

| `follow:z:followers:{user_id}`       | ZSET               | 持续             | 粉丝列表游标分页            |

### 5.3 Feed / 帖子 / 互动 / 评论

| 键格式                                               | 类型                 | TTL     | 说明                                                                     |
| ------------------------------------------------- | ------------------ | ------- | ---------------------------------------------------------------------- |

| ---------------------------------------------------------- | ------------ | ------- | --------------------------------------- |

| `post:hot`                                                 | ZSET         | 与重算周期一致 | 定时重算后的热门帖 Top100（`GET /posts/hot` 直接读取） |
| `post:views:{post_id}`                                     | String       | 短       | 浏览数累加暂存，定时同步 MySQL `views_count`        |
| `lock:views:sync` / `lock:hot:calc` / `lock:hot:reconcile` | String(Lock) | 短       | 定时任务分布式锁（防多实例重复执行）                      |

> 热度分公式（`hot_post_service`）：`score = 点赞×3 + 评论×5 + 浏览×0.1`，按 `DECAY_FACTOR=1.5/小时` 时间衰减；重算仅取近 7 天且 `json_length(tags)>0` 的帖子（无标签帖子不进热榜）。

## 六、开发注意事项

1. **user\_auth 查询**：OAuth 回调时使用 `uk_provider_user` 唯一索引，时间复杂度 O(1)
2. **帖子计数**：`likes_count` / `comments_count` 等冗余字段，插入/删除点赞时需同步更新帖子表
3. **关注计数**：`following_count` / `followers_count` 在 user\_follow 表变更时同步更新
4. **dm\_conversation 约定**：插入时保证 `user1_id < user2_id`，查询某用户会话时需同时查 `user1_id` 和 `user2_id` 两个方向（此约定属于 `dm_conversation` 表，与 `user_auth` 无关）
5. **标签存储（冗余缓存）**：`post_tag` 关联表为标签筛选的唯一数据源（按标签查帖子走 `idx_tag`）；`post.tags` JSON 为展示用冗余缓存（避免列表查询 JOIN）。两者在应用层事务内双写保证一致，冗余以换取列表查询性能
6. **简历教育经历**：`resume.parsed_education` 以 JSON 数组存储，支持多段教育经历（本科/硕士/博士）；前端如仅需展示首条可取数组首元素
7. **JSON 字段**：`parsed_skills`、`parsed_education`、`strengths` 等 JSON 字段，如果查询频繁可考虑使用 MySQL 8.0 的虚拟列+索引
8. **消息派生字段**：前端 `Message` 的 `link`、`actionLabel`、`actionLink` 为 UI 派生字段，由前端根据 `type` 与 `related_type` 映射生成，不入库；`relatedContent` 由 `related_id` + `related_type` JOIN 派生。**v1.7**：`type=7`（关注动态）按 `related_id`=帖子跳转；`related_type=4` 按消息来源跳转（简历分析→简历列表；面试就绪→设备检测页）
9. **浏览量去重**：`views_count` 通过 Redis `post:view:dedupe:{post_id}:{user_id}` 做用户级去重，未命中才累加，防止刷量
10. **在线状态**：用户在线状态由 Redis `online:user:{user_id}` 维护（60 秒心跳续期），不入 MySQL
11. **分页**：所有按时间排序的列表查询建议使用游标分页（`WHERE created_at < ?`）而非 OFFSET，避免深分页性能问题
12. **面试语音回答**（v1.3）：`interview_question.audio_url` 为录音文件存储地址，`user_answer` 存语音转写文本（或前端占位说明）；`answer_duration` 为录音计时，`thinking_duration` 为思考倒计时实际用时。录音文件建议存对象存储（OSS/MinIO），DB 仅存地址。
13. **追问关联**（v1.3）：追问题 `is_follow_up=1`，`parent_question_id` 指向父题目（同表 `id`，应用层保证，不建外键）；追问题与父题目共享 `question_no`，展示靠 `is_follow_up` + `created_at` 排序区分。
14. **面试统计冗余**（v1.3）：`interview.follow_up_count` / `total_duration` 与 `interview_report.follow_up_count` / `total_duration` 为冗余字段，面试完成时由面试会话汇总写入报告，列表展示免聚合。
15. **用户资料缓存**（v1.4）：`user:profile:{user_id}` 采用 Cache-Aside——读路径先查 Redis 未命中查库回填；写路径（更新资料/可见性/注销）先更新数据库事务提交，再删缓存，下次查询回填最新数据。缓存存完整资料 JSON，公开资料的敏感字段过滤（email/phone 不外泄）在 Service 层按访问者身份进行。
16. **注销语义**（v1.4）：注销为软删除（`user.status=2`），单事务内同步清理双向关注关系并修正关联用户计数（`GREATEST(x-1,0)` 防负数）；事务提交后删资料缓存并写 `user:deactivated:{user_id}` 吊销标记（TTL 7天覆盖 refresh\_token 最长寿命），auth 续签流程校验该标记拒绝已注销用户，防止旧 refresh\_token 复活账号。
17. **可见性规则**（v1.4）：`user.profile_visibility` — 0-公开返回完整公开资料；1-仅关注者，非关注者仅返回昵称/头像卡片（关注关系校验走 `uk_follower_following`）；2-仅自己，非本人一律 404（等同不存在）。
18. **评论扁平化模型**（v1.6）：`comment` 表统一存储评论和回复，通过 `root_id` 区分层级（NULL=一级评论，非NULL=属于该根评论的回复）。`reply_user_id` 决定前端展示"回复 @xxx"。后端创建回复时从 `reply_comment_id` 反查 `root_id` 和 `reply_user_id`，禁止前端直接传这两个字段，防止用户乱传。
19. **评论计数**（v1.6）：`post.comments_count` 统计该帖子下所有评论+回复总数；`comment.reply_count` 仅在一级评论（`root_id IS NULL`）上维护，统计该一级评论下的回复数。创建回复时需同步更新 `root_comment.reply_count` 和 `post.comments_count`。
20. **Transactional Outbox**（v1.6）：`outbox_event` 表为通用基础设施表，业务变更与事件写入同一个本地事务，事务提交后由 Relay 轮询 `idx_status_retry` 索引批量投递到 MQ。`payload` JSON 含实体字段快照，消费端无需回查数据库。后续帖子点赞、评论等事件可直接复用该表，新增 `event_type` 即可。
21. **文件上传**（v1.6）：`upload_records` 表记录文件上传到 COS 的元数据，`cos_key` 为对象存储 Key，`cos_url` 为访问 URL。`status` 字段支持异步处理流程：`pending` → 处理中 → `completed`/`failed`。**v1.7**：`file_type` 实际存储值为 `resume` / `image`（STS 申请时支持 `resume`/`avatar`/`post_image`，目录统一映射 `resumes/` 与 `images/`）；扩展名白名单为 `.pdf,.docx,.png,.jpg,.jpeg`（**简历仅支持 .pdf/.docx，.doc 已移除**）。
22. **评论点赞**（v1.7）：`comment_like` 表承接 `POST /comments/{comment_id}/like`，唯一约束 `uk_comment_user` 防重复；写路径同步维护 `comment.likes_count`。不产生动态/通知/热度分。
23. **单设备登录**（v1.7）：`auth:active_jti:{user_id}` 记录当前活跃会话 jti；新登录/刷新覆盖旧 jti 并向 `notify:push:{user_id}` 推送 `session_kicked`（SSE）；中间件与 refresh 双重校验 jti，被顶设备 access/refresh 均失效，防互相顶号死循环。
24. **面试软删除**（v1.7）：`DELETE /interviews/{id}` 置 `is_deleted=1` + `deleted_at`（不物理删），题目/报告/总分保留；删除时清理 Redis `interview:checkpoint:*` 与相关通知。
25. **报告 JSON 扩展**（v1.7）：`interview_report.dimension_scores`（六维：技术能力/问题理解/准确性/深度/工程经验/表达能力）与 `capability_profile`（能力画像雷达图）在 LLM 报告生成时一并落库，前端报告页直接读取。
26. **私信幂等与软删**（v1.7）：`dm_message.client_msg_id` 唯一索引是 at-least-once 消费 + 幂等落库的兜底；会话/消息的"删除"是 `hidden_by_userX` / `deleted_by_userX` 侧写语义，各自对一侧隐藏，不物理删除。
27. **签到打卡**：Redis Bitmap `checkin:user:{user_id}:{YYYYMM}` 按位记录当月签到，不入 MySQL；接口 `GET /checkin/status`、`POST /checkin`（每日一次）。
28. **热榜过滤**：定时重算（每 10 分钟）仅处理近 7 天且 `json_length(tags)>0` 的帖子——**无标签帖子不进热榜**；同时维护 `post.is_hot` 冗余标记与 `post:hot` ZSET 供读接口。
29. **面试就绪通知**：`POST /interviews` 创建成功（题目预生成完成）后投递 `MESSAGE_TYPE_INTERVIEW`(5) 条通知，`related_id`=interview\_id、`related_type=4`，前端据此路由到设备检测页。
