# BUG5：面试提交频繁 409 冲突 —— 分析报告与改造任务清单

> 版本：v1.1
> 更新日期：2026-09-03
> 项目：AI 面试教练（interview\_tool）
> 状态：阶段三方案已细化定稿（问题队列 + 异步落库决策，见 §4.1/§4.2），待实施
> 决策方向：回答数据落库**走 MQ 异步化**：提交接口收敛为"毫秒级受理"，判题/推进由
> MQ Consumer 串行编排，所有数据（追问行/回答/分析/报告）在消费端异步落库。

***

## 一、Bug 现象

面试进行中（尤其"提交后判题/生成追问"环节），出现以下循环：

1. 提交回答 → 进入判题 → 报 **409** 并回退让用户重新提交（用户感知"可能是超时？还是锁未释放？"）
2. 再次点击 → 提示 **"操作过于频繁，请稍候重试"**（409 的 busy 分支）
3. 多次失败后再次点击 → **成功**，且直接使用了**第一次提交的结果**（跳过重新判题）

用户补充：该现象在"判定下一题（含追问）"时高发；成功后明显是复用了第一次请求已落库的结果。

***

## 二、根因分析

### 2.1 结论：不是"锁泄漏"，是"锁持有时间 > 前端超时"的结构性错配

一次提交协同三处超时/锁配置：

| 项             | 位置                                                | 默认值      |
| ------------- | ------------------------------------------------- | -------- |
| 前端提交超时        | `web_front/src/lib/api/interview.ts` submitAnswer | **30s**  |
| 后端单次 LLM 调用超时 | `api_server/app/core/config.py` → `LLM_TIMEOUT`   | **120s** |
| 后端操作锁 TTL     | `api_server/app/redis/interview_session.py` 锁实现   | **150s** |

### 2.2 完整时序还原

```
t0       用户点提交 → 请求A 进入操作锁（submit_answer 内 acquire_lock）
t0+0s    锁内执行 run_fast_decision()（判题 LLM，最长可到 120s；生成追问时更重）
t0+30s   前端 axios 超时 → 报"分析服务异常，请重试提交"→ 回退作答态
         （后端同步线程不被客户端断连取消，请求A 继续跑、继续持锁）
t0+40s   用户重试 → 请求B 撞锁 → 409 busy → "操作过于频繁，请稍候重试"
t0+50s   再次点击 → 仍 busy（请求A 未结束）
t0+60s   请求A 落库完成并释放锁 →
         用户重试命中幂等预检（(interview_id, question_index) 已有 user_answer）
         → 200 duplicated=true，直接返回第一次的分析结果与 next_question → 成功进入下一题
```

三段现象 ↔ 三段机制：

| 现象            | 机制                             | 代码位置                                                |
| ------------- | ------------------------------ | --------------------------------------------------- |
| 提交后 409 回退重提交 | 前端 30s 超时（非 409，但被用户感知为失败回退）   | `InterviewSessionPage.tsx` 非冲突 catch：`分析服务异常，请重试提交` |
| 后续点击"操作繁忙"    | 后端锁被请求A 持有 → 409 `busy`        | `interview_service.py` submit\_answer 锁分支           |
| 最后"复用第一次结果"   | 幂等预检命中 → 200 `duplicated=true` | `_advance_with_lock` / `_idempotent_response`       |

### 2.3 追问为什么高发

- 答完基础题的那次 `run_fast_decision` 需额外**生成追问文本**（输出更长 → 调用更久），且生成后要插行 + 重查题目快照 + 推进 checkpoint（`_advance_with_lock` 内）。

- 故"提交后判题 → 生成追问"的那一步最容易超过前端 30s。

- 已核对追问的 `question_index` 用 `_ordinal_of` 重算、幂等重试从 checkpoint 取当前题，**无索引错位**——409 非追问索引 bug，是锁+超时问题。

### 2.4 锁不会真泄漏的依据

- `submit_answer` 的 `try/finally` 保证 `release_lock_sync` 必执行；

- 进程崩溃时锁 TTL（150s）兜底自动过期；

- 因此"锁未释放感"= 上一个请求仍在服务端运行，前端已放弃等待。

## 四、改造任务清单

### 阶段一：短期止血（不改架构，优先级 P0）

> 目标：不重构即可让 409 循环基本消失，先保证线上体验。

- [ ] **T1.1 前端提交超时对齐**：`submitAnswer` timeout 由 30s 提升至 90s（与后端 LLM\_TIMEOUT=120s 留足缓冲）

- [ ] **T1.2 busy 自动退避重试**：`busy` 分支改为自动重试（2s/4s/8s，最多 3 次），失败再提示用户；
  期间保持"提交中"态，不再回退作答态让用户重复点按钮

- [ ] **T1.3 超时文案区分**：axios 超时（ECONNABORTED）与业务异常分开提示，
  文案："网络较慢，答案正在后台处理，请稍候点击重试"（避免误认为失败丢数据）

- [ ] **T1.4 验证**：连续提交/快速重试均不再出现 409 弹窗；成功仍能进入下一题且不重复计数

### 阶段二：后端最小治理（不改提交链路，P1）

> 目标：在正式 MQ 化之前，把"锁内跑 LLM"的窗口压回毫秒级。

- [ ] **T2.1 Fast Decision 移出操作锁**：先无锁落库 `user_answer`（幂等兜底），判题后持锁仅做 checkpoint 版本校验与推进（毫秒级写）

- [ ] **T2.2 同题并发"排队复用"**：同 `question_index` 撞锁时不再 409，改为等待首个请求完成并复用其结果（回归 `duplicated=true` 语义）

- [ ] **T2.3 回归测试**：覆盖"同题双提交""提交超时重试""追问推进"用例

### 阶段三：回答落库 MQ 化（大改，按既定方向 P2）

> 方向（已确认）：**回答数据与判题推进不直接在请求线程内落库/计算，改走 MQ**。

现状参考：项目已有 Transactional Outbox + RabbitMQ 基建（`interview.analysis` 异步分析、`interview.report.generate` 报告生成均已走 outbox + Consumer），可复用同一套模式。

#### 目标架构（v1.1 细化：受理 / 串行编排 / 异步数据 三层）

```
前端提交答案
   │ POST /interviews/{id}/answers —— 毫秒级受理（不调 LLM、不写业务表）
   ▼
受理接口（请求线程）
   ① epoch 租约校验 → ② 幂等预检（已答直接返回既有结果）→ ③ 状态校验
   → checkpoint 置 phase=analyzing（暂存 answer、刷新 last_activity_at）
   → 同一事务投递 outbox 事件 interview.answer.submitted
   → 立即返回 {"phase":"analyzing","accepted":true}
   ※ 同题已在判题中（analyzing 且题序一致）再次提交 → 返回"已受理"继续轮询
     （409 busy 在提交链路消失；仅保留 epoch/version/finished 真冲突）
   ▼
Answer Consumer（单实例，保同面试题目 FIFO）
   ① 幂等预检（该题 user_answer 已写 → 跳过）
   ② 串行编排（判题→追问→推进强顺序，严禁与落库并行乱序）：
      图 invoke（speech_correct → fast_decision → route）→ next_action
      follow_up → 生成追问文本 → 追问题"生成即异步落库"（T3.10）
      更新问题队列（追问 lpush 队首 / 完成一题取队首）
   ③ 推进 checkpoint（answering + 新 current_question_id / summarizing）
   ④ 异步数据侧：
      user_answer 落库（消费端异步，幂等键防重）
      投递 interview.analysis（沿用现有链路）
      （结束时）投递 interview.report.generate（沿用现有链路）
   ⑤ SSE 推送 interview:judged
   ▼
前端：SSE / 3s 轮询（复用 recovering 基建）→ 进入下一题 / 报告轮询
```

#### 阶段三关键决策（v1.1 确认）

1. **判题→追问生成→推进为强串行**：必须先出 `next_action` 才有追问文本、才知道推进到哪；
   "判题/落库/推进"不得拆成各自独立的异步任务（修正早期"三段并列"的理解）。
2. **问题队列挂 LangGraph 状态**：`InterviewState` 增加 `question_queue` 字段，input 与全局状态均携带；
   基础题在面试正式启动时入队；追问 `lpush` 插队首；每完成一题取队首为下一题。
3. **Redis List 仅作备份/恢复**：`interview:q:{id}` 镜像图内队列，防异常（崩溃/重启）漏题；
   图 checkpointer 与 List 双写，任一丢失互恢复，两处全失按 MySQL 重建。
4. **追问文本"生成即异步落库"**：不延后到用户作答后再落，避免放弃/超时中断丢题。
5. **受理去重替代 409 busy**：同题处于 analyzing 再提交 → 返回已受理，前端继续轮询。
6. **Answer Consumer 单实例**：保同面试题目严格按题序处理；不复刻 ANALYSIS 的竞争多实例。

#### 任务细分（v1.1 细化）

- [ ] **T3.1 事件定义**：新增 `interview.answer.submitted`（payload：interview\_id/question\_index/question\_id/question\_text/answer/answer\_duration/epoch/tab\_id/priority\_ref）

- [ ] **T3.2 受理接口瘦身**：`submit_answer` 改为"epoch 校验 → 幂等预检 → 状态校验 → checkpoint 置 analyzing → 同事务投事件 → 秒回已受理"；不再调 LLM、不再写业务表

- [ ] **T3.3 串行编排语义（修正）**：判题→追问生成→推进为强顺序依赖，在同一消息处理内按序完成；不得拆成独立异步任务

- [ ] **T3.8 问题队列（LangGraph 状态）**：`InterviewState` 新增 `question_queue`（input 与全局状态均携带）；
  基础题在 `start_interview` 时按序入队；追问产出 → `lpush` 队首；完成一题 → 取队首为下一题；队空且无追问 → summarizing

- [ ] **T3.9 队列镜像与恢复**：`interview:q:{id}` Redis List 与图状态双写；任一丢失互恢复；两处全失 →
  MySQL 按"未答题 + 追问父子关系"重建（复用 `_load_or_rebuild_checkpoint` 思路，防漏题）

- [ ] **T3.10 追问题生成即异步落库**：追问文本由判题产出后，在消费端立即异步落库追问题行（user\_answer 暂空），
  避免放弃/超时中断丢题；用户作答后由回答落库流程补写 answer

- [ ] **T3.4 进度感知**：前端 `submitting` 态改为 3s 轮询 / SSE `interview:judged` 接收"判题完成 + next\_question"；
  失败路径（连续失败跳题、重试上限）沿用现有 `analysis_fail_count` 逻辑

- [ ] **T3.5 幂等与恢复**：Consumer 幂等键 = (interview\_id, question\_index)；checkpoint 丢失按 MySQL 重建（现有 `_load_or_rebuild_checkpoint` 继续兜底）

- [ ] **T3.6 超时语义重构**：前端无需长超时（受理毫秒级返回），改由轮询控制等待窗口

- [ ] **T3.7 兼容清理**：移除锁内 LLM、同步落库路径（含 `_advance_with_lock` 判题段）；409 仅保留真冲突（epoch/version/finished）

## 五、风险与注意点

| 风险        | 说明                                               | 应对                                                          |
| --------- | ------------------------------------------------ | ----------------------------------------------------------- |
| 消息延迟      | MQ 判题延迟会让"下一题"出现等待                               | 轮询 + SSE 双通道；等待超时提示"生成中"                                    |
| 顺序性       | 追问与下一基础题的推进必须有序                                  | Consumer 按 (interview\_id) 分片/串行消费 + checkpoint 版本校验        |
| 幂等边界      | Consumer 重复投递不能双写/重复判题                           | 唯一键 + `_idempotent_response` 复用                             |
| 与 BUG3 联动 | 提交链路改造涉及 checkpoint（`started_at` 起算点），需一并修复 BUG3 | 阶段三时同步修正 `start_interview` 重置 `started_at`                  |
| 前端兼容      | 老的"同步返回 next\_question"契约变化                      | 接口返回值兼容（仍返回"已受理+处理中"），前端按新契约适配                              |
| 队列一致性     | 图 checkpointer 与 Redis List 双写可能不一致              | 任一丢失互恢复；两处全失按 MySQL"未答题+追问父子关系"重建队列（防漏题）                    |
| 编排吞吐      | 判题在单消费者内串行，多面试同时答题存在排队等待                         | 判题主流 1\~5s，当前量级足够；量级上升后按 interview\_id 分片 + checkpoint 版本校验 |

***

## 六、结论

- 根因 = **锁持有时间（LLM ≤120s）> 前端超时（30s）**，叠加幂等复用，形成"超时 → busy → 复用第一次结果"的三段式体验。

- 短期（阶段一）即可消除绝大部分 409；阶段三是符合预期方向的**回答落库 MQ 化大改**，将提交接口收敛为"受理 + 事件投递"，判题/落库/进度推进全部异步化。

- v1.1 已细化阶段三落地形态：**受理 / 串行编排 / 异步数据 三层** + **问题队列**（LangGraph
  `InterviewState` 承载发问顺序，Redis List 镜像备份恢复）；判题→追问生成→推进保持强串行，
  数据（含追问行）统一在消费端异步落库。
