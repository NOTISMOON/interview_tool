# 简历上传分析功能流程文档

> 本文档描述简历上传、AI 分析、面试消费分析结果的完整功能流程与数据设计。

---

## 1. 系统概述

简历模块是 AI 面试系统的前置基础模块，入口位于个人主页的「我的简历」区域，核心职责：

1. **简历上传**：支持个人主页（我的简历模块）、AI 面试页面两个入口，统一走 COS 直传 + 回调落库。
2. **简历删除**：用户可在个人主页删除已上传的简历。
3. **简历去重**：基于文件 SHA256 哈希值，同一用户同一文件只保留一份简历记录。
4. **AI 分析**：上传完成后通过 MQ 异步触发 AI 解析，提取技能、项目经历、教育经历、工作经历等结构化信息。
5. **结果消费**：AI 面试模块加载简历分析结果，作为 LangGraph Agent 生成面试题目的上下文。

整体架构：

```
                         用户
                          |
          ┌───────────────┴───────────────┐
          ↓                               ↓
     简历管理模块                    AI 面试模块
     上传简历                        上传简历（复用）
     简历管理                        创建面试
     查看分析结果                     获取分析结果
          |                               |
          └───────────────┬───────────────┘
                          ↓
                   Resume Service
                 （FastAPI 同步业务）
                          |
              ┌───────────┼───────────┐
              ↓           ↓           ↓
           MySQL      COS 存储      MQ（RabbitMQ）
           Resume     文件存储     interview.resume
                                   .parse.queue
                          ↓
              InterviewResumeParseConsumer
                   （同进程异步消费者）
                          ↓
                       LLM 分析
                          |
              ┌───────────┴───────────┐
              ↓                       ↓
         resume 表更新           resume_work_experience 表写入
         (parsed_skills,         (company, role, duration,
          parsed_projects,        description)
          parsed_education,
          parsed_name)
                          ↓
                   通知服务（SSE/WebSocket）
                          ↓
                   AI 面试模块消费
```

## 2. 简历上传流程

用户可以通过以下入口上传简历：

- **个人主页（我的简历模1块）**：上传新简历、删除已有简历、查看分析结果
- **AI 面试页面**：上传简历（复用已有或新增），创建面试

两个入口最终进入统一的简历服务。

流程：

```
用户上传简历（前端直传 COS）
        ↓
获取 STS 临时密钥（限定用户目录）
        ↓
前端直传 COS 对象存储
        ↓
回调 FastAPI 校验落库（upload_records 表）
        ↓
计算文件 SHA256 → file_hash
        ↓
查询 resume 表是否已有相同文件
  (user_id, file_hash) 唯一约束
        ↓
   ┌── 存在 ──→ 复用已有 Resume
   │
   └── 不存在 → 创建新 Resume（status=0 解析中）
        ↓
检查是否已有分析结果（status=1 就绪）
        ↓
   ┌── 已有 → 直接返回分析结果
   │
   └── 无 ──→ 尝试获取 Redis 分析锁
              ↓
         ┌── 获取失败 → 不创建 MQ 任务（已有任务在执行）
         │
         └── 获取成功 → 发送 MQ 消息 → 异步分析
        ↓
前端展示「AI 分析中…」等待状态
```

## 3. 简历表设计

### 3.1 `resume` 表

```sql
CREATE TABLE `resume` (
  `id`                BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `user_id`           BIGINT UNSIGNED  NOT NULL              COMMENT '用户ID',
  `file_name`         VARCHAR(255)     NOT NULL              COMMENT '原始文件名',
  `file_url`          VARCHAR(512)     DEFAULT NULL          COMMENT '文件存储地址（COS URL）',
  `file_size`         BIGINT UNSIGNED  DEFAULT NULL          COMMENT '文件大小(字节)',
  `file_hash`         VARCHAR(64)      DEFAULT NULL          COMMENT '文件SHA256哈希值，用于去重',
  `status`            TINYINT UNSIGNED NOT NULL DEFAULT 0    COMMENT '0-解析中 1-就绪 2-错误',
  `parsed_name`       VARCHAR(128)     DEFAULT NULL          COMMENT 'AI解析出的姓名',
  `parsed_skills`     JSON             DEFAULT NULL          COMMENT 'AI解析出的技能列表',
  `parsed_projects`   JSON             DEFAULT NULL          COMMENT 'AI解析出的项目经历',
  `parsed_education`  JSON             DEFAULT NULL          COMMENT 'AI解析出的教育经历',
  `created_at`        DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `updated_at`        DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_file_hash` (`user_id`, `file_hash`),
  KEY `idx_user_id` (`user_id`),
  KEY `idx_user_status` (`user_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='简历表';
```

**字段说明**：

| 字段 | 说明 |
|------|------|
| `file_hash` | 文件内容 SHA256，与 `user_id` 组成唯一约束，实现去重 |
| `status` | 0=解析中、1=就绪、2=错误 |
| `parsed_skills` | JSON 数组，如 `["Python", "FastAPI", "Redis"]` |
| `parsed_projects` | JSON 数组，每项含 `name`、`description`、`tech_stack` 等 |
| `parsed_education` | JSON 数组，每项含 `school`、`degree`、`major`、`year` |

**唯一约束 `uk_user_file_hash`**：保证同一用户同一文件只有一份简历记录，避免个人主页和面试模块重复上传同一文件。

### 3.2 `resume_work_experience` 表

工作经历独立成表，与简历是一对多关系：

```sql
CREATE TABLE `resume_work_experience` (
  `id`          BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `resume_id`   BIGINT UNSIGNED  NOT NULL              COMMENT '关联简历ID',
  `company`     VARCHAR(128)     NOT NULL              COMMENT '公司名称',
  `role`        VARCHAR(128)     NOT NULL              COMMENT '职位',
  `duration`    VARCHAR(64)      NOT NULL              COMMENT '任职时间',
  `description` TEXT             DEFAULT NULL          COMMENT '工作描述',
  `sort_order`  INT UNSIGNED     NOT NULL DEFAULT 0    COMMENT '排序',
  `created_at`  DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_resume_id` (`resume_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='简历工作经历表';
```

### 3.3 分析结果存储说明

> **设计决策**：不创建独立的 `ResumeAnalysis` 表。分析结果直接存入 `resume` 表的 JSON 字段（`parsed_skills`、`parsed_projects`、`parsed_education`、`parsed_name`），工作经历存入 `resume_work_experience` 表。这样避免了 1:1 关系表的额外 JOIN，且工作经历独立成表比 JSON 大字段更规范、更易查询。

## 4. 简历 AI 分析流程

### 4.1 分析任务创建

简历上传完成后：

```
Resume Service（同步）
        ↓
检查 resume.status 是否已为 1（就绪）
        ↓
   ┌── 已就绪 → 跳过分析，直接返回
   │
   └── 非就绪 → 尝试获取 Redis 分析锁
                 ↓
            ┌── 获取失败 → 不创建 MQ 任务（已有分析在执行）
            │
            └── 获取成功 → 发送 MQ 消息 → 后台异步分析
```

MQ 消息：

```json
{
    "resume_id": 10001,
    "user_id": 1001
}
```

队列：`interview.resume.parse.queue`

交换机：`interview`（topic 类型），routing_key：`interview.resume.parse`

### 4.2 分析 Worker（MQ 消费者）

消费者：`InterviewResumeParseConsumer`（在 FastAPI 服务进程内运行）

流程：

```
消费 MQ 消息
        ↓
获取简历文件（从 COS 下载）
        ↓
PDF/Word 文档解析
        ↓
文本提取
        ↓
LLM 分析（调用 AI 服务）
        ↓
生成结构化信息：
  - parsed_name（姓名）
  - parsed_skills（技能列表）
  - parsed_projects（项目经历）
  - parsed_education（教育经历）
  - resume_work_experience（工作经历记录）
        ↓
保存到 MySQL（同一事务）
        ↓
更新 resume.status = 1（就绪）
        ↓
释放 Redis 分析锁
        ↓
发送完成通知（MQ → Notification Service）
```

## 5. 简历分析互斥锁

### 5.1 为什么需要锁

场景：用户上传简历后，分析任务正在执行。此时用户进入面试页面，再次上传同一份简历。由于 `(user_id, file_hash)` 唯一约束，系统复用已有 Resume 记录。但如果不加锁，可能会创建第二个分析任务，导致：

- 重复消耗 LLM Token
- 分析结果覆盖

### 5.2 Redis 分析锁

| 项目 | 值 |
|------|-----|
| Key | `resume:analysis:lock:{resume_id}` |
| Value | `task_uuid`（任务唯一标识） |
| 获取命令 | `SET key value NX EX 600` |
| TTL | 600 秒（10 分钟） |
| 获取成功 | 当前任务负责分析 |
| 获取失败 | 已有分析任务执行中，不创建新任务 |

**注意**：锁竞争对用户无感知，前端统一展示「AI 分析中…」等待状态。

## 6. 用户体验流程

### 场景一：首次上传

```
用户上传简历
        ↓
resume.status = 0（解析中）
        ↓
前端展示「AI 分析中…」等待动画
        ↓
后台：MQ → Worker → LLM 分析
        ↓
分析完成 → status = 1（就绪）
        ↓
前端收到通知 → 展示分析结果
```

### 场景二：重复上传（分析进行中）

```
用户再次上传同一份简历
        ↓
发现 file_hash 已存在 → 复用已有 Resume
        ↓
发现 status = 0（解析中）
        ↓
发现 Redis 分析锁存在
        ↓
不创建新的 MQ 任务
        ↓
前端仍展示「AI 分析中…」等待动画
```

> 用户不会感知到底层的锁、MQ、去重逻辑。

## 7. 简历分析完成通知

分析完成后：

```
Worker 保存分析结果
        ↓
更新 resume.status = 1（就绪）
        ↓
删除 Redis 分析锁
        ↓
发送完成通知（MQ）
```

通知消息：

```json
{
    "resume_id": 10001,
    "user_id": 1001,
    "status": 1
}
```

### 通知消费

Notification Service 消费通知后：

- 写入 `message` 表（站内消息）
- 通过 SSE / WebSocket 实时推送给前端

用户收到：「你的简历 AI 分析已完成」

## 8. AI 面试模块消费分析结果

### 8.1 面试创建

简历分析完成后，用户可以创建面试：

```
创建 Interview Session
        ↓
绑定 resume_id
        ↓
获取简历分析结果
        ↓
初始化 LangGraph Agent
        ↓
开始面试
```

### 8.2 分析结果加载策略

```
Interview 请求简历分析数据
        ↓
优先读 Redis 缓存
  resume:analysis:{resume_id}
        ↓
   ┌── 命中 → 直接使用
   │
   └── 未命中 → 查询 MySQL
                 ↓
            ┌── 存在（status=1）→ 回写 Redis 缓存
            │
            └── 不存在/解析中 → 等待分析完成或返回错误
```

### 8.3 面试数据表

面试相关表已在数据库中完整定义：

| 表 | 说明 |
|----|------|
| `interview` | 面试会话（绑定 `resume_id`，含类型、状态、当前题号、总分、时长） |
| `interview_question` | 面试题目（题号、题型、维度、追问、AI 评分/评语、语音回答） |
| `interview_report` | 面试报告（总分、总结、优势/不足/建议 JSON、题目数、追问数） |

## 9. Redis 职责划分

### 简历模块

| Key | 用途 |
|-----|------|
| `resume:analysis:{resume_id}` | 分析结果缓存（JSON，含 skills/projects/education/work_experience） |
| `resume:analysis:lock:{resume_id}` | 分析互斥锁（NX EX 600，防重复分析） |
| `resume:analysis:status:{resume_id}` | 分析状态缓存（减少数据库查询） |

### 面试模块

| Key | 用途 |
|-----|------|
| `interview:lock:{session_id}` | 面试执行锁（防多浏览器同时操作） |
| `interview:checkpoint:{session_id}` | LangGraph 状态检查点（异常恢复） |

## 10. 核心设计原则

| 组件 | 职责 |
|------|------|
| **Resume Service** | 简历资产管理（上传/删除）、文件去重判断、分析任务调度 |
| **InterviewResumeParseConsumer** | MQ 异步消费者，负责 PDF/Word 解析 + LLM 分析 + 结果持久化 |
| **Redis** | 高频缓存（分析结果、状态）、分布式锁（分析互斥、面试互斥）、状态恢复 |
| **MQ（RabbitMQ）** | 异步分析解耦、完成通知投递 |
| **MySQL** | 最终数据存储，保证数据一致性 |

**核心流程总结**：

> 个人主页/AI面试页上传简历 → 统一 Resume Service（上传/删除/去重） → SHA256 去重 → MQ 异步分析 → Redis 锁保证唯一分析 → 分析结果存 MySQL + 缓存 Redis → 完成通知推送前端 → Interview Agent 消费分析结果 → LangGraph 执行智能面试。
