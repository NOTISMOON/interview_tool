# 简历上传与 AI 分析功能（设计蓝图 / 现状实现）

> 状态：**已实现 M1（基础闭环）+ 部分担保项** · 建设中文档，随实现持续修订 · v0.6
> 更新日期：2026-08-22
> 项目：AI 面试教练（interview_tool）
>
> 本文档描述「简历上传 → 去重 → AI 解析分析 → 结果落库 → 通知 → 面试模块消费」的完整链路。
> 简历上传复用已实现的《文件上传功能文档》（COS 前端直传 + 回调校验），本文档聚焦其下游的
> **去重、异步分析、结果存储与消费**，并预留面试功能对接契约。
> 标注说明：`[已实现]` 表示已按本文档落地并通过端到端验证；`[待建设]` 表示尚未完成，随实现推进更新。

## 一、背景与目标

### 1.1 背景

简历是 AI 面试系统的前置基础。用户上传简历后，系统需自动提取姓名、技能、项目经历、教育经历、
工作经历等结构化信息，作为面试环节生成题目的上下文。简历模块入口：

- **个人主页 → 我的简历**：上传、删除（分析结果**不展示给用户**，仅下游消费）
- **AI 面试页面**：上传（复用已有或新增）后创建面试

### 1.2 范围

| 属于本蓝图 | 不属于本蓝图（仅定义契约） |
|------------|---------------------------|
| 简历上传与去重 | 面试会话执行（LangGraph Agent） |
| AI 解析分析（LLM 结构化提取） | 面试题目生成、评分报告 |
| 分析结果存储与缓存 | 面试过程语音/交互 |
| 完成/失败通知 | |
| 简历删除（软删除） | |
| 与面试模块的读取契约 | |

### 1.3 目标

1. 用户上传简历后 **10 分钟内** 完成 AI 分析并落库（结果**不展示给用户**，仅供下游面试模块消费）。
2. 同一用户重复上传同一文件 **只保留一份** 分析结果，不重复消耗 LLM Token。
3. 分析全程异步，**不阻塞** 上传/浏览请求。
4. 分析结果稳定可消费，为面试模块提供可靠上下文。
5. 进度与结果仅面向**面试模块**暴露；个人主页只通知完成/失败，不展示分析进度。

### 1.4 非目标（防范围蔓延）

- 不做简历 OCR 服务端闭环（扫描版 PDF 仅提示不支持，见 §7.2）。
- 不做简历在线编辑/模板。
- **不做分析结果对用户的展示页**：分析结果属用户画像/上下文数据，仅通知「分析完毕」，页面只展示上传状态。
- 不在此蓝图实现面试 Agent，仅保证「面试能取到分析结果」。

## 三、核心流程设计

### 3.1 简历上传（复用已具备链路）

```
前端直传 COS → 回调 POST /cos/callback 校验落库（upload_records）
        ↓
【新增】创建/复用 Resume 记录
```

回调校验完成后进入简历模块，见 §3.2。上传本身的参数（file_type=resume、10MB 限制、
每日次数限制、STS 策略）均复用《文件上传功能文档》，本蓝图不重复设计。

### 3.2 文件去重与记录创建

> 设计决策：**SHA256 在回调内服务端计算**（一次 COS GET，≤10MB，同地域耗时可控），
> 使得「创建即去重」、唯一约束 `uk_user_file_hash` 立即可用，避免 `file_hash=NULL` 去重空窗。
> 备选方案（Worker 内计算，回调零开销）及其代价见 §5.10。

```
回调校验落库（upload_records）成功后（同步路径）：
1. 下载 COS 文件（一次 GET）计算 SHA256 → file_hash
2. 查询 (user_id, file_hash) 是否已有【未删除】Resume
        ↓
   ┌── 命中 → 复用已有 Resume（不新增记录）
   │          ├── status=1（就绪）→ 直接返回，不重新调度
   │          └── status=0/2（解析中/错误）→ 尝试重新调度（自愈，见 §3.3）
   │
   └── 未命中 → 校验当前未删除简历数 < 6（份数上限）
       │         达到上限 → 返回 409「简历数量已达上限（6），请删除后再上传」
       └── 未达上限 → 插入新 Resume（status=0，file_hash 必填非空）
        ↓
3. 触发分析调度（§3.3）
```

> **份数上限（=6，已定）**：每用户最多保留 6 份**未删除**简历；去重命中的复用不占新名额，
> 新增插入前校验，超限返回 409。
> **软删除联动（已定）**：删除为软删（§3.6），删除时 `is_deleted=1` 且 `file_hash` 置空，
> 使 `uk_user_file_hash` 唯一约束不阻塞「删除后重新上传同一文件」；去重查询必须过滤 `is_deleted=1`。

**并发竞态规避（必做）**：两个请求同时上传同一文件时，「查→插」会产生唯一约束冲突。
实现必须在 `try/except IntegrityError` 中执行插入，冲突后**回查并复用**已有记录
（项目在用户创建上已有同款经验），而不是让 500 返回给用户。

### 3.3 分析任务调度（Redis 锁 + MQ）

```
检查 resume.status
   ├── 已就绪（status=1）→ 直接返回，跳过分析
   └── 非就绪（status=0 解析中 / status=2 错误）→ 尝试获取分析锁
       SET resume:analysis:lock:{resume_id} <task_uuid> NX EX <TTL>
            ├── 获取失败 → 已有任务在执行，不创建 MQ 任务
            └── 获取成功 → 投递 MQ 消息 → 返回「分析中」
```

调度为同步快速路径，只做「查状态 + 抢锁 + 投递」，不做重 IO。
该逻辑天然支持**自愈**：重复上传命中 status=0/2 的旧记录时，只要锁未被持有即可重新投递分析
（§3.2 的「自愈」即指此路径）；status=2 的记录重传后锁释放即重新分析。
**锁要点**：`finally` 必释放；分析超时前 `PEXPIRE` 续期；删除前校验锁 value == 自己 task_uuid。

### 3.4 分析 Worker 执行（独立进程 + LangChain）

```
消费 MQ 消息 {resume_id, user_id}
        ↓
定位文件（用落库的完整 `file_url` 直连公开链接，供 `PyPDFLoader`/`Docx2txtLoader` 加载；SHA256 已在回调算好）
        ↓
LangChain/LangGraph 文件加载与文本提取
  （PyPDFLoader / Docx 等加载插件，不手写下载/解析逻辑）
        ↓
LLM 结构化提取（姓名/技能/项目/教育/工作经历）
        ↓
【持有锁校验】锁 value == 自己 task_uuid？（防锁过期后重复任务）
        ↓
   ┌── 成功 → 同一事务写入：
   │           resume.parsed_* 更新 + resume_work_experience 写入
   │           resume.status = 1（就绪）
   │           释放锁 → 失效缓存 → 发「分析完成」通知
   │
   └── 失败 → 记录 error_message → resume.status = 2（错误）
              释放锁 → 失效缓存 → 发「分析失败」通知（提示可重试）
```

### 3.5 完成/失败通知与前端状态

- **通知模式（对齐项目现状）**：Worker 落库成功/失败后，按
  `follow_post_consumer` 的既有模式——`asyncio.to_thread(notification_service.create_notification)` 写
  `message` 表（新开同步会话提交）→ `notification_service.publish_to_user()` 经 Redis Pub/Sub 广播 SSE。
  **无需再投递一层通知 MQ**（`notification.deliver.queue` 保留给走 Outbox 的跨系统事件）。
- **消息类型（已定）**：采用 `MESSAGE_TYPE_SYSTEM(1)`（系统消息）；`related_id=resume_id`。
  `related_type` 现有枚举（1-帖子 2-报告 3-用户）不含简历；若系统消息点击需要跳转简历实体页，
  实现时新增 `RELATED_TYPE_RESUME=4`（默认可不填 related_type）。
- **通知内容（已定）**：
  - 成功：仅提示「简历 AI 分析已完成」，**不携带、不展示分析结果**。
  - 失败：提示「简历 AI 分析失败，请重新上传或重试」。
  - 分析结果属内部数据，仅供下游面试模块消费；前端只展示上传状态（解析中/就绪/失败）。
- **进度展示（已定）**：
  - **个人主页**：不展示分析进度，仅收到完成/失败通知。
  - **面试模块**：上传后展示「AI 分析中…」进度（按 3s 轮询 `resume.status`），就绪后进入面试。
  - SSE 断线兜底：轮询 status；通知丢失时刷新仍可见 status=1（可降级）。
- **失败重新分析（后期迭代）**：status=2 的记录提供「重新分析」入口（一键重试接口），
  或用户重新上传同一文件触发自愈（§3.3）；重新分析受 Redis 锁保护，成功后补发完成通知。

### 3.6 简历删除（软删除 + 联动一致性）

> **已定决策：软删除**。保留 `resume` 行用于审计与面试上下文追溯，物理清理其下游资源。

```
删除 Resume（软删除）
  ├── 前置检查：是否存在进行中/未结束的 Interview 绑定该 resume_id
  │      有 → 仍可软删除（进行中面试不受影响，上下文可追溯）
  ├── 更新 is_deleted=1 + deleted_at；file_hash 置空（释放唯一约束）
  ├── 删除 resume_work_experience（或一并保留，视面试追溯粒度）
  ├── 物理删除关联 upload_records 记录
  ├── 删除 COS 对象（复用 cos.delete_object；简历已不可访问，物理清理）
  ├── 清理缓存 resume:analysis:* / resume:analysis:status:*
  └── 释放分析锁（若存在）
```

**唯一约束与去重联动**：
- `resume` 表新增 `is_deleted` / `deleted_at`（见 §4.1）。
- 删除时将 `file_hash` 置 NULL → `uk_user_file_hash` 不冲突，允许「删除后重新上传同一文件」。
- 去重查询与份数统计（上限 6）仅看未删除记录（`is_deleted=0`）。

## 四、数据设计

### 4.1 `resume` 表（已具备 + 待迁移）

```
现有列：id / user_id / file_name / file_url / file_size / status /
        parsed_name / parsed_skills / parsed_education / created_at / updated_at
```

**待新增字段/索引（迁移项）**：

```sql
ALTER TABLE `resume`
  ADD COLUMN `file_hash` VARCHAR(64) DEFAULT NULL COMMENT '文件SHA256哈希，用于去重' AFTER `file_size`,
  ADD COLUMN `parsed_projects` JSON DEFAULT NULL COMMENT 'AI解析出的项目经历数组（含 name/description/tech_stack）' AFTER `parsed_education`,
  ADD COLUMN `error_message` VARCHAR(512) DEFAULT NULL COMMENT '解析失败原因' AFTER `parsed_projects`,
  ADD COLUMN `is_deleted` TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '软删除标记 0-否 1-是' AFTER `error_message`,
  ADD COLUMN `deleted_at` DATETIME DEFAULT NULL COMMENT '软删除时间' AFTER `is_deleted`,
  ADD UNIQUE KEY `uk_user_file_hash` (`user_id`, `file_hash`);
```

> 说明：
> - `idx_user_id` / `idx_user_status` **已存在**（ORM 与库表均有），无需重复添加。
> - 注意：MySQL 唯一索引对 `NULL` 不互斥（多个 NULL 可共存）。应用层创建记录时 `file_hash`
>   **必须非空**（§3.2 在回调内算好再插入），否则去重失效。
> - **软删除联动**：删除时 `is_deleted=1` 且 `file_hash` 置空，`uk_user_file_hash` 因此不阻塞
>   重新上传同一文件（见 §3.6）。
> - `parsed_projects` / `file_hash` / `error_message` / `is_deleted` / `deleted_at` 未在
>   `docs/DB设计/数据库设计文档.md` 出现，实现 M1 时需一并同步更新该文档与 ORM 模型。

### 4.2 `resume_work_experience` 表（已具备）

```
id / resume_id(普通索引 idx_resume_id，无外键/唯一约束) / company / role / duration / description / sort_order / created_at
```

工作经历独立成表而非 JSON，便于查询与规范（沿用现有设计）。
注意：`resume_id` 仅建了二级索引 `idx_resume_id`，**没有外键与唯一约束**；
同一简历不应有重复工作经历行，靠 Worker 写入逻辑保证（每次解析先清空该简历旧行再插入），
删除简历时需显式联动删除（见 §3.6）。

### 4.3 分析结果存储约定

- `parsed_*` 直接存 `resume` 表 JSON 字段（不建 1:1 分析结果表，避免额外 JOIN）。
- `resume_work_experience` 存工作经历行（一对多）。
- `parsed_projects` 每项：`name` / `description` / `tech_stack`。
- `parsed_education` 每项：`school` / `degree` / `major` / `year`。

### 4.4 Redis Key 设计

| Key | 用途 | 说明 |
|-----|------|------|
| `resume:analysis:lock:{resume_id}` | 分析互斥锁 | SET NX EX 600，value=task_uuid |
| `resume:analysis:{resume_id}` | 分析结果缓存 | JSON 全量结果，面试模块读取 |
| `resume:analysis:status:{resume_id}` | 分析状态缓存 | 减少 DB 查询（面试模块进度） |

### 4.5 MQ 拓扑

| 项 | 值 |
|----|-----|
| 交换机 | `interview.exchange`（topic，已存在） |
| 队列 | `interview.resume.parse.queue`（**持久化 + 手动 ack**，已存在） |
| routing key | `interview.resume.parse` |
| 消息体 | `{"resume_id": 10001, "user_id": 1001}` |

> 队列/交换机/routing key 与 `app/mq/queues.py`、`app/mq/exchanges.py` 现状一致，
> `InterviewResumeParseConsumer` 骨架已注册，实现时直接填充其 `handle_message` 即可。

## 五、关键设计决策与隐患规避

### 5.1 去重并发竞态（高）

- 唯一约束 + `IntegrityError` 回查复用（§3.2）。
- `file_hash` 创建即非空，避免 NULL 空窗。

### 5.2 分析锁超时与失败释放（高）

- `finally` 释放；`PEXPIRE` 续期；删除前校验 value==task_uuid。
- 锁 TTL=600s；异常路径必须释放，避免死锁阻塞后续重试。

### 5.3 简历 PII 访问控制（高）[已实现，技术方案以实际为准]

> **方案已定（2026-08-22，M1 落地依据）**：当前实现采用「**COS Bucket 对 `resumes/*` 公读 + 落库完整 `file_url`**」，
> **而非**蓝图初稿的「私有读 + 预签名」。原因是简历解析 Worker 的 `PyPDFLoader` / `Docx2txtLoader`
> 需要**匿名 GET 线上公开链接**做文档加载，私有读会让 Worker 加载器无法访问，故 M1 选择了公读直连。
> `cos_client.generate_presigned_url()` 接口仍保留，作为未来切回「私有读 + 预签名」的备选（见下方切换指引）。

- **风险提示（保留）**：`build_cos_url()` 生成**永久公网 URL** 并落库到 `upload_records.cos_url` /
  `resume.file_url`；bucket 对 `resumes/*` 公有读时，链接一旦泄露即可被任何人下载简历全文，且该 URL 永久有效。
- **当前约束（公读方案）**：
  1. COS 对象 key 采用**不可猜测**结构 `resumes/{user_id}/{uuid}.pdf`（UUID 随机），降低被枚举扫描的风险。
  2. 分析结果读取接口**强制归属校验**（仅简历归属者可读，`get_current_user` + user_id 比对）。
  3. 分析结果**不对用户展示**，仅供下游面试模块消费；个人主页仅提示完成/失败。
  4. 日志脱敏，不打印文件内容/完整链接。
  5. 上传回调三重校验（STS 路径归属、Redis 上传状态、COS HEAD 元数据）确保只有本人能登记对象。
- **切回私有化（可选，非当前实现）**：若未来收紧安全，将 bucket 改为私有读，并把 Worker 加载改为
  先调 `cos.generate_presigned_url()` 取短时 URL 供加载器使用（PDF 可直连，DOCX 仍先下临时文件），
  `file_url` 语义回归「仅标识」。切换涉及 §6.3 与 Worker 加载逻辑，暂列为可选演进。

### 5.4 删除联动一致性（高）

- 见 §3.6：**软删除**保留 `resume` 行（面试上下文可追溯），物理清理 upload_records / COS / 缓存 / 锁。
- 删除时 `file_hash` 置空以释放唯一约束；去重与份数统计仅看未删除记录（`is_deleted=0`）。
- 新增字段与迁移需与 `docs/DB设计/数据库设计文档.md` 同步更新。

### 5.5 LLM 输出结构校验（中）

- LLM 输出 JSON 直接落库风险大：需 Pydantic schema 校验 + 解析失败降级
  （整段失败置 status=2 并通知；单字段缺失置空并记录警告）。

### 5.6 消费者进程隔离（中）

- **问题**：文件加载 + 文本提取 + LLM 为长耗时重 IO，若跑在 FastAPI 进程内会拖慢 API。
- **约束**：Worker 独立进程运行（沿用项目 MQ runner 模式）；**API 进程不承载解析逻辑**。
- Worker 内文件读取与文本提取交由 **LangChain/LangGraph 的文档加载插件**处理，不手写下载/解析。

### 5.7 重试与死信（中）

- 手动 ack；处理失败 `nack(requeue=false)` → 重试队列（指数退避，上限 3 次）→ 死信队列人工排查。
- 重试前先释放/校验锁，防止重试任务与续期任务并存。

### 5.8 缓存一致性（中）

- 缓存 key `resume:analysis:{resume_id}` / `resume:analysis:status:{resume_id}`。
- 写路径失效：Worker 落库成功后 DEL + 发布通知；读路径命中即返回。
- 面试模块读分析结果时：缓存优先 → 未命中回源 MySQL（status=1）→ 回写缓存。

### 5.9 关联：每日上传计数时机（低，属上传模块）

- 当前 `get_sts_token` 在 STS 前 `incr` 每日计数，STS 失败/未真正上传也扣次数。
- 建议：回调成功后扣，或发放时预扣 + 未回调自动退还（本蓝图不实现，仅标注关联项）。

### 5.10 哈希计算位置（设计决策，§3.2）

- **方案 A（采纳）**：回调内服务端计算 SHA256（一次 COS GET，≤10MB）。
  - 优点：创建即去重，`uk_user_file_hash` 唯一约束立即可用；无 `file_hash=NULL` 空窗；
    Worker 只下载一次用于文本提取，不重复下载。
  - 代价：回调请求增加一次 ≤10MB 下载（同地域毫秒~秒级），可接受。
- **方案 B（备选）**：Worker 内计算，回调零开销。
  - 代价：插入时 `file_hash` 为空 → 唯一约束失效 → 并发重复上传会建多条记录；
    需额外引入 Redis 锁按 `(user_id, file_hash)`「认领」，loser 复用 winner，复杂度明显更高。
  - 适用：若未来文件体积上限提升或对回调延迟敏感，再切换。

### 5.11 LLM 抽象层（供应商/预算待定）

- **决策**：LLM 供应商、模型、超时与 Token 预算**待定**（见 §9 开放问题）。
- **约束**：基于 LangChain 抽象 LLM 调用层（Provider 配置化切换），Worker 内不直接绑定单一供应商；
  结构化提取结果统一用 Pydantic schema 校验（见 §5.5），供应商差异不影响下游数据契约。

## 七、非功能需求

- **性能**：上传回调 <2s；分析 10 分钟内完成（LLM 超时设置）；缓存命中率目标 ≥90%。
- **可靠**：MQ 持久化 + 手动 ack + 重试/死信；Redis 锁超时自动释放（防死锁）。
- **安全**（当前实现，见 §5.3）：COS `resumes/*` 公读 + 完整 file_url 落库；分析结果归属校验；日志脱敏；
  对象 key 用 UUID 防枚举。（备注：切回「私有读 + 预签名」为可选演进，`generate_presigned_url` 已可用。）
- **可观测**：分析链路埋点（入队/下载/解析/LLM/落库/通知各阶段耗时、失败率）；日志含 request_id/task_uuid。
- **成本**：去重减少重复 LLM 消耗；LLM Token 预算上限（待定，§5.11）。
