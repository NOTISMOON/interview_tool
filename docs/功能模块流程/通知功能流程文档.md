# 通知功能流程文档（SSE + Nginx多实例 + MQ + Redis Pub/Sub 广播）

> 项目：AI 面试教练（interview_tool）
> 模块：通知功能基座（多实例部署友好）
> 更新日期：2026-08-19
> 版本：v1.1
> 部署模式：Nginx 负载均衡 → N 台 API Server 实例（每实例：API + Outbox Relay + MQ Consumer + SSE 连接维护）
> 关键变更v1.0→v1.1：取消SSE建立/重连时的全量拉取，统一改为**基于前端本地最后一条消息ID的增量拉取，最多10条**

## 二、完整流程（分 6 阶段）

### 阶段 1：客户端建立 SSE 长连接（浏览器 → Nginx → 某实例）**【增量拉取版】**

```
浏览器                                       Nginx                           API Server #k (随机分配)
   │                                          │                                   │
   │ 1. 读 localStorage.last_msg_id           │                                   │
   │    (空 → 首次访问，走 since_id=NULL)      │                                   │
   │                                          │                                   │
   │ 2. EventSource('/api/v1/messages/stream')│                                   │
   │    withCredentials=true                  │                                   │
   │    + 请求头 Last-Event-ID: <last_msg_id> │                                   │
   │    (或 EventSource 自动携带上次的ID)       │                                   │
   │─────────────────────────────────────────▶│                                   │
   │       (GET /api/v1/messages/stream)      │   负载均衡                          │
   │                                          │──────────────────────────────────▶│
   │                                          │   A. 鉴权：Cookie.access_token     │
   │                                          │      → 解析出 user_id=U            │
   │                                          │   B. 解析增量起点：                  │
   │                                          │      since_id = req.query["since_id"]          │
   │                                          │              || req.headers["last-event-id"]    │
   │                                          │              || NULL(首次)          │
   │                                          │   C. 增量补偿查询：                    │
   │                                          │      SELECT * FROM message          │
   │                                          │      WHERE user_id=U                │
   │                                          │        AND (:since_id IS NULL OR id > :since_id)│
   │                                          │      ORDER BY id DESC LIMIT 10     │
   │                                          │      → 取"之后"最多10条（非全量！） │
   │                                          │   D. 未读计数：COUNT WHERE is_read=0│
   │                                          │   E. SSEManager.connect(U)          │
   │                                          │      → 生成本地 Queue，存入内存     │
   │                                          │   F. 先推送补偿消息（按id升序）       │
   │                                          │      再推送 unread_count 事件       │
   │                                          │  HTTP 200 (text/event-stream)       │
   │◀─────────────────────────────────────────│◀──────────────────────────────────│
   │ 3. 接收补偿消息 (最多10条)                 │                                   │
   │    写入本地列表 + 内存渲染                 │                                   │
   │    更新 localStorage.last_msg_id          │                                   │
   │        = MAX(补偿消息里的最大id)           │                                   │
   │ 4. 进入实时监听（Redis Pub/Sub 消息）      │                                   │
   │                                          │                                   │
   │◀──── 每 15s 发送 : keep-alive 注释帧 ──── │◀──────────────────────────────────│
   │  (防 Nginx / CDN 空闲超时断连)             │                                   │
```

**关键点（增量版新增）**：
- 浏览器 `localStorage` 持久化 `last_msg_id` → 关闭页面重开也能从上次位置继续增量
- SSE 连接的 `Last-Event-ID` 头和 `localStorage.last_msg_id` 双保险，取最大值做 `since_id`
- **补偿查询严格 `id > since_id ORDER BY id DESC LIMIT 10`** — 无论用户离线 1 天还是 1 个月，只拉最新 10 条，不会全量扫描
- 需要更多历史的用户主动进入消息中心，使用 `cursor` 游标准分页翻页（与补偿查询解耦）

### 阶段 2：用户发起业务操作（关注 / 提交面试 / 发布内容…）

**以"关注用户"为例**（简单业务，同步事务完成）：

```
浏览器 A (user_99 关注 user_100)
   │  POST /api/v1/users/100/follow
   │───────────────────────▶ Nginx ──────────────────────▶ API Server #m (任意实例)
                                                                        │
                                                                        ▼
                                                          【单 MySQL 本地事务 BEGIN】
                                                            ① INSERT user_follow(99,100)
                                                            ② UPDATE user.following_count+1 (id=99)
                                                            ③ UPDATE user.followers_count+1 (id=100)
                                                            ④ INSERT user_activity(type=3, 关注动态)
                                                            ⑤ INSERT outbox_event(follow_created, …)
                                                                   ← 用于后续缓存同步
                                                            ⑥ INSERT outbox_event(notification.created,
                                                                 recipient=100, type=FOLLOW,
                                                                 title="新关注",
                                                                 content="user_99关注了你",
                                                                 from_user_id=99)
                                                                   ← 用于产生通知消息
                                                          【COMMIT】
                                                                        │
                                                                        ▼
                                                               返回 204 No Content
```

**以"简历解析 / 面试报告生成"为例**（耗时长，先进 MQ 异步）：

```
浏览器 B (提交简历解析)
   │  POST /api/v1/interviews/resumes/parse
   │──────────────▶ Nginx ──────────────▶ API Server #k
                                                   │
                                                   ▼
                                    【单 MySQL 本地事务 BEGIN】
                                      ① UPDATE resume.status=解析中
                                      ② INSERT outbox_event(notification.created,
                                           recipient=user_id, type=INTERVIEW,
                                           title="简历解析中",
                                           content="你的简历正在AI解析中，请稍候")
                                           ← 第一条：进度型通知，立即发给用户
                                      ③ INSERT MQ 消息（或直接发 RabbitMQ）
                                           → interview.resume.parse.queue
                                    【COMMIT】
                                                   │
                                                   ▼
                                              返回 202 Accepted
```

### 阶段 4：NotificationConsumer 消费通知 → 写 MySQL + Redis Pub/Sub 广播

```
RabbitMQ notification.deliver.queue
           │
           ▼
NotificationConsumer（抢到任何一个实例都行，比如实例#2）
   │
   ├─ payload.recipient_user_id = U100（被关注者）
   │
   ▼
1. 同步 Session: message_repository.create(message)
   → 落 MySQL message 表，拿到 message_id（自增BIGINT，全局有序）
2. message_repository.unread_count(U100)
   → 查得未读总数（如 3+1=4）
3. 封装 SSE 事件：
     {"kind":"message",
      "message":{"id":M_id, "type":4, "title":"新关注",
                 "content":"user_99 关注了你",
                 "from_user_id":99, "created_at":"..."},
      "unread_total":4}
4. Redis PUBLISH notify:push:100 <JSON事件>
   → 广播，不管 U100 连接在哪个实例
5. ACK MQ 消息
```

**Redis Pub/Sub 广播示意（跨实例扇出）：**

```
Redis Pub/Sub 通道 notify:push:100
    │
    ├───────────────────订阅───────────────────────┐
    │                                              │
    ▼                                              ▼
实例#1 订阅回调 on_message()                  实例#2 订阅回调 on_message()
  channel=notify:push:100 → user_id=100          channel=notify:push:100 → user_id=100
  查本地 SSEManager._queues[100]                  查本地 SSEManager._queues[100]
    → [Queue_A] 存在！push 进去 ✅                  → [] 不存在，跳过 ❌
       │
       ▼
  本地Queue出队 → SSE 写入 EventSource 响应流
```

**为什么要广播到所有实例？**
因为 NotificationConsumer 无法预知"U100 的 SSE 连在哪个实例上"。所有实例都收到，**只有真正持有连接的那个实例会实际推 SSE**，其余实例只是空判断一下（微秒级）。

### 阶段 5：SSE 推送 + 浏览器侧处理（**增量 last_id 更新**）

```
实例#1（U100 连接所在）
   │ 从本地 Queue 拿到事件
   ▼
SSE 流式响应写：
   event: message
   id: <message_id （= message表自增主键，前端同步用作last_msg_id）>
   data: {"id":M_id,"type":4,"title":"新关注","content":"user_99 关注了你",
          "from_user_id":99,"from_user_nickname":"...","from_user_avatar":"...",
          "created_at":"2026-08-19 12:00:00","unread_total":4}

浏览器 EventSource.onmessage
   │
   ├─ 0. 更新本地游标：
   │    if (msg.id > (Number(localStorage.getItem("notify:last_msg_id")) || 0)) {
   │        localStorage.setItem("notify:last_msg_id", String(msg.id));
   │    }
   │
   ├─ 1. Toast 弹窗（轻通知，1~3s自动消失）
   │    "user_99 关注了你 → [查看主页]"
   │
   ├─ 2. 顶部导航小红点：未读数 = event.data.unread_total
   │
   └─ 3. 若用户正停留在消息页面：
        新消息 prepend 到列表顶部（不刷新页面）
```

### 阶段 6：断线 / 重连 / 实例宕机（增量自愈闭环）**【增量拉取版】**

浏览器原生 `EventSource` **自带自动重连**（默认 3 秒，服务端可通过 `retry:` 帧调整）。

```
场景 A：网络波动断连（3秒内自愈）
   浏览器 ──断线── 实例#1
     → 断连期间产生的消息：id=200, 201
   （3秒后 EventSource 自动重连）
   浏览器 ──GET /stream ──▶ Nginx ──▶ 可能分配到实例#5
     请求头：Last-Event-ID: 199
     + localStorage.last_msg_id = 199 (取最大=199)
       │
       ▼
   since_id = 199
   SELECT * FROM message WHERE id > 199 ORDER BY id DESC LIMIT 10
     → 返回 [201, 200]（正好补上断线期间的 2 条）
   先推补偿 → 再进入实时 Pub/Sub 监听
   localStorage.last_msg_id 更新到 201
```

```
场景 B：用户离线 1 个月后重新访问（关键：绝不全量拉）
   localStorage.last_msg_id = 88 (一个月前的)
   浏览器 GET /stream
       │
       ▼
   since_id = 88
   SELECT * FROM message WHERE id > 88 AND user_id=U ORDER BY id DESC LIMIT 10
     → 只返回最新 10 条（id=9950~9941），其余 9940 条不推
   localStorage.last_msg_id 更新到 9950
   用户想要更多历史 → 主动点消息中心翻页（GET /messages?cursor=&size=20）
```

```
场景 C：实例#1 宕机，连接集体掉线
   所有挂在实例#1 的用户SSE断连 → 各自浏览器 3s 自动重连
   Nginx 健康检查发现实例#1 下线 → 从池中摘除
   重连请求全部分流到其他实例 → 各自携带自己的 last_msg_id
   → MySQL 按 id > last_msg_id 补偿最多10条（仅该实例宕机期间漏掉的）
   → Redis Pub/Sub 新连接已在新实例注册，后续实时消息无缝接收
```

```
场景 D：用户清了浏览器缓存（localStorage 丢失）
   localStorage.last_msg_id = 空
   GET /stream，since_id=NULL
     → 补偿拉最新 10 条（等价于"只看最近的"，不是全量）
   后续每条消息正常更新 last_msg_id
```

## 三、通知类型与触发源清单

| type | 名称 | 触发点 | 产生方式 | 接收方 |
|------|------|--------|---------|--------|
| 1 | SYSTEM 系统公告 | 运营后台发布 | 后台API → 批量message + Redis PUBLISH notify:broadcast | 全体用户 |
| 2 | COMMENT 评论 | 他人在我的内容下评论 | 评论写事务 → notification.created Outbox | 内容作者 |
| 3 | LIKE 点赞 | 他人点赞我的内容 | 点赞写事务 → notification.created Outbox | 内容作者（可合并：24h同一人多次点赞只发一次） |
| 4 | FOLLOW 关注 | 他人关注我 | follow_service.follow() 同事务追加 notification.created Outbox | 被关注者 |
| 5 | INTERVIEW 面试相关 | 简历解析完成 / 面试报告生成 / 面试邀请… | Consumer 处理完 MQ 任务 → notification.created Outbox 或直接写 message + publish | 任务提交者 / 被邀请者 |

> 注：数据库设计文档 type=5 原定义为"私信"，这里已将"私信"调整为 6、"面试"新增为 5，实施时同步对齐枚举。

## 四、API 接口清单 **【since_id 增量版】**

### 4.1 SSE 实时通道

| 方法 | 路径 | 认证 | 说明 |
|------|------|------|------|
| GET | `/api/v1/messages/stream` | Cookie自动鉴权 | text/event-stream 长连接，请求头 `Last-Event-ID` 或 query `?since_id=` 可选；补偿返回最多10条 |

**补偿查询参数（双路径兼容）**：

```
# 方式 A（推荐，EventSource 原生）
GET /api/v1/messages/stream
Header: Last-Event-ID: 199
Cookie: access_token=xxx

# 方式 B（某些环境自定义头受限，可通过 query 显式传）
GET /api/v1/messages/stream?since_id=199
Cookie: access_token=xxx
```

优先级：`query.since_id` > `header[Last-Event-ID]` > NULL（前端建议通过方式 B 显式传 since_id，避免部分环境 EventSource 头丢失）。

**SSE 事件格式规范**：

```
# 1. 单条新消息（含当前未读数，前端不用再请求）
event: message
id: 10234
data: {
  "id": 10234,
  "type": 4,
  "type_name": "follow",
  "title": "新关注",
  "content_text": "张三 关注了你",
  "from_user": {"id":888,"nickname":"张三","avatar":"https://..."},
  "related": {"id":888,"type":"user"},
  "created_at": "2026-08-19 12:00:00",
  "is_read": false,
  "unread_total": 4
}

# 2. 未读数变化（标记已读/全部已读后触发）
event: unread_count
data: {"total": 0, "by_type": {"follow":0,"interview":0,"system":0}}

# 3. 系统公告广播（type=1）
event: system_broadcast
id: 20001
data: {"id":20001,"title":"系统维护通知","content_text":"今晚23:00~24:00系统升级",...}

# 4. 心跳（15秒一次，不触发前端事件）
: keepalive

# 5. 断线重连间隔提示（服务端建议浏览器重连间隔）
retry: 3000
```

### 4.2 通知 REST 接口

| 方法 | 路径 | 说明 | 认证 |
|------|------|------|------|
| GET | `/api/v1/messages` | 消息列表：`?since_id=XXX&limit=10`（增量，最多10条） 或 `?cursor=&size=20&type=follow`（历史翻页） | 需登录 |
| GET | `/api/v1/messages/unread-count` | 未读计数（含分类汇总） | 需登录 |
| GET | `/api/v1/messages/{id}` | 消息详情（访问即标记已读） | 需登录 |
| PUT | `/api/v1/messages/{id}/read` | 单条标记已读 → 同步推 unread_count SSE | 需登录 |
| PUT | `/api/v1/messages/read-all` | 全部标记已读 → 同步推 unread_count=0 | 需登录 |
| DELETE | `/api/v1/messages/{id}` | 删除单条通知 | 需登录 |

**增量列表 GET /messages 参数规范**：

| 参数 | 类型 | 默认 | 说明 |
|------|------|------|------|
| `since_id` | bigint | NULL | 增量起点：返回 id > since_id 的消息；优先级高于 cursor |
| `limit` | int | 10 | 增量模式下返回条数上限，**服务端强制 clamp 到 [1, 10]** |
| `cursor` | bigint | 0 | 翻页游标（历史翻页模式，since_id 不传时生效） |
| `size` | int | 20 | 历史翻页每页数量，clamp 到 [1, 50] |
| `type` | string | 全部 | 按类型过滤：system/comment/like/follow/interview/dm |

校验规则：
- `since_id` 与 `cursor` 同时传入时，**since_id 优先**，cursor 忽略
- `limit > 10` → 服务端自动截断为 10

## 五、前端本地缓存策略（新增章节）

### 5.1 localStorage Key 约定

| key | 类型 | 说明 |
|-----|------|------|
| `notify:last_msg_id` | string | 最后一条已接收消息的 id，跨页面/跨重启共用 |
| `notify:unread_total` | string | 未读总数缓存（快速展示用，以实际接口/推送为准） |

### 5.2 生命周期钩子伪代码

```typescript
// App 启动钩子（Vue onMounted / React Root useEffect([])）
const NOTIFY_LAST_ID_KEY = "notify:last_msg_id";
const NOTIFY_UNREAD_KEY = "notify:unread_total";

async function initNotify() {
  // 1. 先增量拉一次（不等 SSE，保证首屏立即可见）
  const lastId = Number(localStorage.getItem(NOTIFY_LAST_ID_KEY) ?? 0);
  const resp = await fetch(
    `/api/v1/messages?since_id=${lastId}&limit=10`,
    { credentials: "include" }
  ).then(r => r.json());

  if (resp.items && resp.items.length) {
    // 按 id 去重合并，本地列表只保留最近 N 条（前端自管理）
    store.messages = mergePrependById(store.messages, resp.items);
    const newMax = Math.max(lastId, ...resp.items.map((m: any) => m.id));
    localStorage.setItem(NOTIFY_LAST_ID_KEY, String(newMax));
  }
  store.unreadTotal = resp.unread_total ?? store.unreadTotal;
  localStorage.setItem(NOTIFY_UNREAD_KEY, String(store.unreadTotal));

  // 2. 建立 SSE（显式传 since_id，避免某些环境 Last-Event-ID 头丢失）
  const currentLast = Number(localStorage.getItem(NOTIFY_LAST_ID_KEY) ?? 0);
  const es = new EventSource(
    `/api/v1/messages/stream?since_id=${currentLast}`,
    { withCredentials: true }
  );

  es.addEventListener("message", (e: any) => {
    const msg = JSON.parse(e.data);
    const prev = Number(localStorage.getItem(NOTIFY_LAST_ID_KEY) ?? 0);
    if (msg.id > prev) localStorage.setItem(NOTIFY_LAST_ID_KEY, String(msg.id));
    if (typeof msg.unread_total === "number") {
      store.unreadTotal = msg.unread_total;
      localStorage.setItem(NOTIFY_UNREAD_KEY, String(msg.unread_total));
    }
    store.messages = mergePrependById(store.messages, [msg]);
    Toast.show({ title: msg.title, content: msg.content_text, type: msg.type_name });
  });

  es.addEventListener("unread_count", (e: any) => {
    const { total } = JSON.parse(e.data);
    store.unreadTotal = total;
    localStorage.setItem(NOTIFY_UNREAD_KEY, String(total));
  });

  es.addEventListener("system_broadcast", (e: any) => {
    const msg = JSON.parse(e.data);
    Toast.show({ title: "系统公告", content: msg.content_text, sticky: true });
  });

  es.onerror = () => {
    // EventSource 会自动重连，不做额外处理；超过一定次数可以做降级轮询提示
  };
}
```

## 六、Nginx 关键配置（必配）

```nginx
upstream api_servers {
    server 127.0.0.1:8001;  # 实例#1
    server 127.0.0.1:8002;  # 实例#2
    server 127.0.0.1:8003;  # 实例#N
    keepalive 64;
}

server {
    listen 80;

    # ---- SSE 长连接专用配置（不缓存、不缓冲、保持chunked） ----
    location ~ ^/api/v1/messages/stream$ {
        proxy_pass http://api_servers;

        proxy_http_version 1.1;
        proxy_set_header Connection "";  # 不设 keep-alive/close，走默认chunked
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        # 透传浏览器 EventSource 自动携带的 Last-Event-ID（SSE增量必需）
        proxy_pass_header Last-Event-ID;

        proxy_buffering off;             # 关键：关闭响应缓冲，否则Nginx攒数据才推
        proxy_cache off;                 # 关闭缓存
        proxy_read_timeout 1h;           # SSE长连接读超时（1小时，超过会被Nginx切断）
        proxy_send_timeout 1h;
        proxy_request_buffering off;     # 请求体不缓冲

        chunked_transfer_encoding on;
    }

    # ---- 普通接口走默认 ----
    location / {
        proxy_pass http://api_servers;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

## 八、异常场景与降级策略

| 场景 | 现象 | 降级策略 |
|------|------|---------|
| **Redis 挂了** | Pub/Sub 不通 → SSE 在线推送失效 | ⭕ 功能降级：前端 30s 轮询 `/messages?since_id=<last>&limit=10` + `/messages/unread-count` 增量补偿（直到 Redis 恢复）；MySQL 永远可读，不丢消息 |
| **RabbitMQ 挂了** | NotificationConsumer 不消费 → Outbox 事件堆积 | ⭕ 功能降级：MQ 恢复后 Relay 继续投递积压 Outbox，最终一致；用户刷新页面时增量拉 since_id 能看到已落库的通知（业务主事务先写DB保证一致性） |
| **MySQL 挂了** | 业务主事务都失败 → 根本不会产生通知 | ❌ 服务不可用（属全局故障，由 HA/主从切换处理） |
| **单个 API 实例宕机** | 该实例上 SSE 连接断 | ⭕ 浏览器 3s 自动重连到其他实例；MySQL 按 since_id 补偿最多10条；一切恢复 |
| **N+1 实例扩容** | 新实例启动 → 自动 subscribe Pub/Sub | ⭕ 零配置接入，流量立即分摊 |
| **通知风暴（系统公告+大V上线）** | 瞬时百万级 Redis PUBLISH | ✅ Redis Pub/Sub 可扛百万级 QPS；SSE 是流式写入，不会阻塞；如瓶颈可进一步改为按实例分片 subscribe |
| **localStorage 被禁用/隐私模式** | last_msg_id 持久化失效 | ⭕ 降级：每次建连 since_id=NULL → 仍只拉最新10条（不是全量），只是无法精确断点续传；用户体验不变差 |
| **补偿查询返回 >10 条** | 恶意用户改 limit=1000 | ✅ 服务端强制 `LIMIT 10`，不接受更大值 |
| **SSE 连续失败 ≥ 3 次** | 推送受阻（通常意味着 Redis 或网关异常） | ⭕ 前端自动切换到 30s 轮询，并在用户进入消息中心时刷新 |

## 十、v1.0 → v1.1 增量拉取改动对照清单（实施时对齐）

| 位置 | v1.0（废弃） | v1.1（采用） |
|------|-------------|-------------|
| SSEManager.connect 补偿 | `SSE_INITIAL_RECENT_COUNT=20` 无条件拉最近20条 | `SSE_CATCHUP_LIMIT=10` + `WHERE id > :since_id ORDER BY id DESC LIMIT 10` |
| 端点 query/header | 无增量参数 | 新增 `?since_id=` query + 解析 `Last-Event-ID` header（query 优先） |
| GET /messages 参数 | 仅 cursor/size 翻页 | 新增 `?since_id=&limit=` 增量模式，limit>10 服务端强制截断 |
| 前端 EventSource | `new EventSource(url, {withCredentials:true})` | 拼接 `?since_id=` 显式传入，避免 Last-Event-ID 在某些环境下丢失 |
| 前端持久化 | 无 | `localStorage["notify:last_msg_id"]` 在每条消息/补偿时更新为 MAX(prev, msg.id) |
| Nginx SSE location | 未透传 Last-Event-ID | 新增 `proxy_pass_header Last-Event-ID;` |
| 降级轮询路径 | 全量 `?limit=5` | 增量 `?since_id=<last>&limit=10` |
