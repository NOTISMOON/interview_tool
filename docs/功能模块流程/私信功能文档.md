# 1. 功能概述

私信模块提供用户与用户之间的 **1:1 实时聊天**：WebSocket 长连接收发消息，消息先写入 **Redis Stream 写缓冲**（微秒级回执、按会话严格保序），由流消费者**批量异步落库 MySQL**；落库成功后通过 **Transactional Outbox → RabbitMQ** 扇出副作用（对端 WS 推送、未读数自增、通知）。会话列表与最近 N 条消息缓存于 Redis，全量历史回源 MySQL 分页。

核心目标：
- **不丢消息**：写缓冲（Redis + AOF）作为持久化兜底，`client_msg_id` 幂等重放。
- **同会话严格保序**：Redis Stream 按 `stream:conv:{id}` 做 key，天然分区保序。
- **发送端感知零延迟**：`XADD` 即回执，前端乐观渲染，不等 MySQL。
- **横向可扩展**：WS 网关每实例连接表 + Redis Pub/Sub 跨实例路由。

整体关系：

```text
┌──────────────┐        ┌─────────────────────┐
│  会话双方客户端 │  WS   │      WS 网关 (每实例)  │
└──────┬───────┘        └─────────┬───────────┘
       │                          │ Redis Pub/Sub 跨实例路由
       ▼                          ▼
┌─────────────────────────┐  ┌──────────────────┐
│  Redis Stream 写缓冲     │  │  热缓存 / 未读数   │
│  stream:conv:{convId}    │  └──────────────────┘
└─────────┬───────────────┘
          │ XGROUP 消费
          ▼
┌─────────────────────────┐
│  流消费者 (批量 flush)     │
└─────────┬───────────────┘
          ▼
┌─────────────────────────┐     ┌──────────────────────────┐
│       MySQL 落库         │ ──► │ Transactional Outbox → MQ │
└─────────────────────────┘     └───────────┬──────────────┘
                                            ▼
                             对端 WS 推送 / 未读数 / 通知
```

# 2. 技术选型与职责边界

私信模块同时使用 Redis Streams 与 RabbitMQ，二者**各司其职**：

| 环节 | 工具 | 为什么 |
|------|------|--------|
| 写缓冲（快速回执 + 备战批量入库） | **Redis Stream** | 内存级微秒写入、按会话 key 严格保序、append-only 可回读兜底、XGROUP 可靠消费 |
| 热数据（会话列表、最近消息、未读数） | **Redis**（zset / stream / hash） | 读加速，LRU 回源重建 |
| 跨实例在线路由 | **Redis Pub/Sub** | WS 连接钉在某实例，发消息给对端所在的其它实例需广播路由 |
| 入库后事件扇出（推 WS / 未读数 / 通知） | **RabbitMQ（Outbox）** | 一对多解耦、路由键、DLX 死信、失败拒收不重投；复用现成 outbox 链路 |

**同步/异步分界（遵循项目规范）**：
- **写路径**（WS 接收 → XADD → Stream 消费 → 落库）为高吞吐异步链路，使用**异步客户端**（`redis.asyncio` + `aiomysql`）。
- **读路径**（会话列表、历史分页、在线状态）为普通查询，使用**同步客户端**（`redis` + `pymysql`），配合 Redis 缓存。

# 3. 数据模型（MySQL）

## 3.1 `conversation` 会话表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK 自增 | 会话ID |
| user_a_id | INT | 会话发起方（较小 id，保证 (a,b) 唯一） |
| user_b_id | INT | 会话对方 |
| last_message_id | BIGINT | 最近一条消息ID（会话列表排序用） |
| last_message_preview | VARCHAR(255) | 最近一条消息预览 |
| last_message_at | DATETIME | 最近消息时间 |
| created_at / updated_at | DATETIME | 时间戳 |

`UNIQUE KEY uk_users (user_a_id, user_b_id)` —— 保证两人只有一个会话，会话 id 规范化：`(a, b) = (min, max)`。

## 3.2 `message` 消息表

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT PK 自增 | 消息ID（同会话内自增即 seq） |
| conversation_id | BIGINT | 所属会话 |
| sender_id | INT | 发送方 |
| receiver_id | INT | 接收方（冗余，便于未读数/消息中心查询） |
| client_msg_id | VARCHAR(64) UNIQUE | 客户端 UUID，**幂等键**（重复消费/重投靠它去重） |
| content_type | TINYINT | 1=文本 2=图片 3=文件 |
| content | TEXT | 消息内容（文本）或资源 key |
| seq | BIGINT | 同会话内自增序号（紧跟 conversation 内上一条 max(seq)+1） |
| created_at | DATETIME | 发送时间 |

`INDEX idx_conversation_seq (conversation_id, seq)` —— 分页查询走组合索引。
`INDEX idx_client_msg (client_msg_id)` —— 幂等唯一校验。

数据库变更走项目既有 `alembic`/迁移脚本，需与表结构同步（见规范第 5.1 节）。

# 4. Redis 数据结构设计

## 4.1 写缓冲 —— Stream

- 键：`stream:conv:{conversation_id}`
- 说明：消息 `XADD` 追加，Redis 自动生成递增 `id`（`*` 服务端序列，保序）。
- **不再单独存 seq**：Stream 的 auto-id 即有序序列，消费端落库时用 `seq = id 数值分` 存到 message.seq。
- 容量控制：Stream 用 `XTRIM ... MAXLEN ~ 1000` 近似裁剪，防止无界增长；全量历史在 MySQL，Stream 只保"未消费 + 近实时热窗"。
- 消费：`XGROUP CREATE stream:conv:{id} g:{conversation_id} $ MKSTREAM`，消费者 `XREADGROUP GROUP` 读取，`XACK` 确认，`XPENDING` 可靠重投。

## 4.2 热数据 —— 最近消息

- 键：`msg:recent:{conversation_id}`
- 类型：`LIST`（头部插入最近消息），`LPUSH` + `LTRIM` 保近 50 条。
- 读：`LRANGE` 取最近 N 条；未命中回源 MySQL 分页并回填。
- 注意（沿用 follow_cache 经验）：**写热缓存必须 EXISTS-guard + DB 兜底重建**，把缓存当"派生"而非"权威"。

## 4.3 未读数

- 键：`unread:{user_id}`，类型 `HASH`：`field = conversation_id, value = 未读数`。
- 发送：扇出消费者收到落库成功 → `HINCRBY unread:{receiver_id} {convId} 1`。
- 进会话/读消息：`HDEL unread:{user_id} {convId}` 清零。
- 会话列表首页：`HGETALL` 聚合各会话未读数。

## 4.4 在线路由（跨实例）

- 键：`ws:online:{user_id}`，类型 `SET`，`value = instance_id:conn_id`。
- 每 WS 连接握手时 `SADD`，断开时 `SREM`，TTL 心跳续期。
- 下线处理：Pub/Sub（`msg:route:*`）广播签名 `{target_user_id, conversation_id, instance_id}`，各实例先查自己身上有无该用户的在线连接，有则推送。

## 4.5 缓存键规范

| 键 | 类型 | TTL |
|----|------|-----|
| `stream:conv:{convId}` | Stream | 无（消费后裁剪） |
| `msg:recent:{convId}` | LIST | 24h |
| `unread:{userId}` | HASH | 30d（惰性失效） |
| `ws:online:{userId}` | SET | 心跳续期 |
| `conv:list:{userId}` | ZSET | 5min |

# 5. 写路径（核心含金量）

## 5.1 流程

```text
客户端 WS send(client_msg_id, convId, content)
        │
        ▼
WS 网关（async）
  ├─ 幂等校验：EXISTS client_msg_id 已存？→ 回执"重复"
  ├─ XADD stream:conv:{convId}  (client_msg_id, sender, content, ts)
  └─ 立即回执 {status:"sent", seq}   ← 发送端不等 DB
        │
        ▼
流消费者（异步，消费组 g:{convId}）
  ├─ 批量攒批：满 BATCH 或超时窗口
  ├─ 批量 INSERT message（带 client_msg_id 唯一键）
  ├─ 遇唯一冲突 → 视为幂等，跳过
  └─ XACK 确认
        │
        ▼
落库成功 → 写 Outbox 事件 outbox_event
        │
        ▼
OutboxRelay（复用现成模块）→ RabbitMQ 事件
        │
        ▼
私信扇出消费者
  ├─ 推对端 WS（Redis Pub/Sub 路由到对端实例）
  ├─ 未读数 HINCRBY unread:{receiver}
  └─ 通知中心（复用 notification 链路）
```

## 5.2 幂等设计

- **发送端侧**：客户端每次发送生成 `client_msg_id`（UUID）。即使 WS 断线重发，同一条消息 `client_msg_id` 不变。
- **服务端侧**：`message.client_msg_id` 唯一索引兜底；消费者批量 INSERT 遇唯一冲突即跳过（`INSERT IGNORE` 或捕获 `IntegrityError`），**不重复落库**。
- **消费组层面**：`XACK` 只在落库成功后执行，消费失败不 ACK，靠 `XPENDING` 重投 —— 保证 at-least-once + 幂等消化。

## 5.3 流消费者实现要点（已落地）

> 落库 Worker 见 `app/services/chat_flush.py`；数据访问见 `app/repositories/chat_repository.py`。

- **运行形态**：独立 asyncio task（`ChatFlushWorker`），由 `app.mq.runner` 挂载，与 OutboxRelay 同进程 —— 从 Redis Stream 读、写 MySQL，**不经过 RabbitMQ**（避免拿 MQ 当入库通道）。
- **活跃会话登记**：写缓冲 `chat_stream.append_message` 时 `SADD chat:convs:flush`，Worker 据此扫描待落库会话，避免遍历所有 stream key。
- **幂等落库**：`INSERT IGNORE` + `dm_message.client_msg_id` 唯一索引 —— 重复消费/重投冲突行自动跳过，at-least-once + 幂等消化。
- **攒批**：每会话 `XREADGROUP` 按批读取（`count=` 上限 + 会话粒度处理），落库后 `XACK`；失败不 ACK，靠 `XPENDING` 可靠重投。
- **一次性写事件**：消息批量落库与 `chat.message.sent` Outbox 事件在同一异步事务提交，保证「消息已存」与「扇出触发」原子。

# 6. 读路径

```text
打开会话列表 / 某会话
        │
        ▼
GET conv:list:{userId}（zset 会话列表 + 未读数 hash）
        │
  未命中/key 过期
        ▼
回源 MySQL：conversation JOIN message 取最近会话
        ▼
回填 zset + 设置 TTL
```

```text
读某会话消息
        │
        ▼
LRANGE msg:recent:{convId} 取最近 N 条
        │
   未命中
        ▼
回源 MySQL：message WHERE conversation_id=? ORDER BY seq (limit/offset 分页)
        ▼
回填 msg:recent + EXISTS-guard（避免覆盖已存在部分缓存）
```

同步读 + 缓存，遵循普通业务同步客户端规范。分页参数带默认值与上限（`page_size ≤ 50`）。

# 8. WebSocket 网关设计

## 8.1 连接管理

- **每实例**内存连接表 `{user_id: set[WebSocket]}`（多标签页同用户多连接）。
- **全局在线**：Redis `ws:online:{user_id}`（`instance_id:conn_id`）。
- **跨实例推送**：目标对端不在本实例 → 发 Redis Pub/Sub `msg:route:{target_user_id}`，各实例收到后查本地连接表推送。

## 8.2 心跳

- 服务端周期性 `ping`，超时未 `pong` 判定断线，清除连接表与 `ws:online`。
- 断线期间到达的消息由未读数 + 下次上线拉取兜底。

## 8.3 安全

- 握手走现有鉴权（JWT/当前用户），WS 携带 token 校验。
- 连接绑定 `user_id`，消息收发均以服务端解析的 user_id 为准，不信任客户端传入 id（规范 §6）。

# 9. 前端（web_front）

## 9.1 目录结构（沿项目 src/lib 约定）

```text
src/lib/
├── ws/
│   ├── wsClient.ts        # WebSocket 单例封装（重连、心跳、消息队列）
│   └── onlineBus.ts       # 在线/断线事件总线
├── api/
│   └── chat.ts            # 会话列表/历史分页/发送 的 REST 兜底
├── hooks/
│   └── useChat.ts         # 会话状态机：乐观渲染 + 发送队列 + 重连补偿
└── chatCache.ts           # 模块级内存缓存（会话列表 + 最近消息增量合并）
```

## 9.2 关键设计

- **乐观渲染**：发送即显示，`client_msg_id` 关联气泡状态（sending → sent → failed）。
- **发送队列 + 重连补偿**：断线时消息进本地队列，重连后按序重发（同 `client_msg_id`，服务端幂等去重）。
- **localStorage 边界收窄**：只做"最近会话 + 发送队列"的**轻量持久化**（崩溃恢复项），**不做聊天记录权威缓存**；历史以服务端为准分页拉取。
- **多标签页**（沿面试模块教训）：避免 localStorage 作为跨标签同步源；用 `BroadcastChannel` 或 WS 广播同步乐观状态，服务端为最终真相。
- **事件源单例**（沿 sseBus 教训）：WS 连接全局单例，禁止每组件独立建连，避免耗尽同源连接数。
- **未读数**：WS 收到扇出事件时即时自增，进会话清零。
