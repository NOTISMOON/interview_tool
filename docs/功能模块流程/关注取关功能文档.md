## 一、背景与目标

### 1.1 问题：双写一致性

读路径（关注/粉丝列表）已上线，依赖 Redis ZSET（分页）+ SET（关系判断）缓存，回源以 DB 为准。写路径（关注/取关）若采用"先写 DB 再写 Redis"的直接双写，存在两类不一致窗口：

| 顺序 | 崩溃点 | 后果 |
|------|--------|------|
| 先 DB 后 Redis | DB 提交成功、Redis 写入前宕机 | DB 有关注、缓存无 → 列表缺人、关系判断漏报（B-21） |
| 先 Redis 后 DB | Redis 写入成功、DB 提交失败 | 缓存有关注、DB 无 → 幽灵关注，需回滚 Redis（更差） |

### 1.2 方案：Transactional Outbox + RabbitMQ

业务变更与事件记录写入**同一个 MySQL 本地事务**，事务提交即保证事件不丢；独立的 Relay 轮询事件表投递到 RabbitMQ；Consumer 异步同步 Redis 缓存。最终一致（目标秒级），任何环节失败可重试，Redis 侧全部幂等。

```
┌─────────┐   ①单事务    ┌──────────┐   ②轮询投递   ┌──────────┐   ③消费    ┌────────┐
│  API    │────────────▶│  MySQL   │─────────────▶│ RabbitMQ │──────────▶│ Redis  │
│ (写接口) │ 业务表+outbox │ outbox表 │   Relay      │  Broker  │  Consumer │ ZSET/SET│
└─────────┘             └──────────┘              └──────────┘           └────────┘
```

### 1.3 目标与闭环

- 关注/取关接口幂等、低延迟（DB 事务 ≤ 3ms，不等待 MQ/Redis）。
- DB 与 Redis 最终一致，投递延迟 P99 < 1s。
- 闭环读路径文档遗留边界：**B-5**（空标记期新关注）、**B-6**（TTL 期间不一致）、**B-14**（注销未清缓存）、**B-16**（SET 常驻维护）、**B-21**（消费失败重试）。
- 复用现有 `app/mq/` 基础设施（aio-pika RobustConnection、统一信封、BaseConsumer、runner 进程），仅扩展拓扑。

## 二、功能流程

### 2.1 接口清单

| 接口 | 路径 | 方法 | 认证 | 成功响应 |
|------|------|------|------|---------|
| 关注用户 | `/api/v1/users/{user_id}/follow` | POST | 必须登录 | 204 No Content |
| 取消关注 | `/api/v1/users/{user_id}/follow` | DELETE | 必须登录 | 204 No Content |

**幂等语义**：重复关注、取关未关注的人均返回 204（不重复计数、不产生事件）。理由：前端按钮状态与网络重试场景下，409 会造成误报；DB 唯一索引与 DELETE rowcount 天然支撑幂等。

**校验规则（关注）**：

| 校验 | 顺序 | 失败响应 |
|------|------|---------|
| 登录态 | 依赖注入 | 401 |
| `user_id == 当前用户` | 1 | 400（不能关注自己） |
| 目标用户 `status=2`（注销） | 2 | 404（不可见） |
| 目标用户 `status=0`（禁用） | 3 | 403 |
| 重复关注（唯一索引冲突） | INSERT 时 | 捕获 IntegrityError → 回滚 → 幂等 204 |

取关无前置校验（DELETE rowcount 判定），仅 401 与 404（路径用户不存在）。

### 2.2 关注流程（时序）

```
Client          API Server                MySQL                    RabbitMQ           Consumer(runner进程)
  │ POST /users/2/follow     │                │                        │                    │
  │──────────────▶│          │                │                        │                    │
  │               │ BEGIN    │                │                        │                    │
  │               │ ① INSERT user_follow(1,2) ─────────────────────▶  │                    │
  │               │ ② INSERT outbox_event(follow_created) ─────────▶  │                    │
  │               │ ③ UPDATE user.following_count+1 (id=1) ────────▶  │                    │
  │               │ ④ UPDATE user.followers_count+1 (id=2) ────────▶  │                    │
  │               │ ⑤ INSERT user_activity(type=3) ─────────────────▶  │                    │
  │               │ COMMIT   │                │                        │                    │
  │◀────204───────│          │                │                        │                    │
  │                          │  Relay: SELECT status=0 LIMIT batch    │                    │
  │                          │──────────────▶│                        │                    │
  │                          │  Relay: publish(publisher confirm)     │                    │
  │                          │───────────────────────────────────────▶│                    │
  │                          │  Relay: UPDATE status=1, published_at  │                    │
  │                          │──────────────▶│                        │                    │
  │                          │                │      deliver           │                    │
  │                          │                │───────────────────────▶│ pipeline 写 Redis  │
  │                          │                │                        │─── ZADD/SADD ────▶│
  │                          │                │                        │◀── ack ───────────│
```

### 2.3 事务内容清单

**关注（单事务）**：

| # | 操作 | 说明 |
|---|------|------|
| 1 | `INSERT user_follow (follower_id, following_id)` | 唯一索引 `uk_follower_following` 兜底幂等 |
| 2 | `INSERT outbox_event (follow_created, payload)` | payload 见 2.4 |
| 3 | `UPDATE user SET following_count = following_count + 1 WHERE id = follower_id` | 冗余计数 |
| 4 | `UPDATE user SET followers_count = followers_count + 1 WHERE id = following_id` | 冗余计数 |
| 5 | `INSERT user_activity (type=3, related_id=following_id)` | "关注了 {nickname}" 动态 |

**取关（单事务）**：

| # | 操作 | 说明 |
|---|------|------|
| 1 | `DELETE user_follow WHERE follower_id AND following_id` | rowcount=0 → 直接 COMMIT，幂等返回，不发事件 |
| 2 | `INSERT outbox_event (follow_deleted, payload)` | 仅 rowcount=1 时 |
| 3 | `UPDATE ... following_count - 1 / followers_count - 1` | 沿用既有 `CAST + GREATEST(0)` 防无符号溢出模式 |

**注销联动（追加到既有注销事务）**：

既有注销流程（软删 status=2、`delete_follow_relations` 双向删关系、批量修正计数）已存在，本方案在其事务内**追加一条** `user_deactivated` 事件。注意：事件 payload 必须在删除关系**前**采集 ID 列表（删除后 Consumer 无法反查）：

| # | 操作 | 说明 |
|---|------|------|
| 1 | 采集 `following_ids`（TA关注的人）/ `follower_ids`（TA的粉丝） | 复用 `get_following_ids` / `get_follower_ids` |
| 2 | 既有注销逻辑（软删 + 删关系 + 计数修正） | 不变 |
| 3 | `INSERT outbox_event (user_deactivated, payload)` | payload 带两个 ID 列表，超上限截断（见 2.4） |

### 2.4 事件类型与 payload

| event_type | 触发场景 | aggregate_type | aggregate_id |
|------------|---------|----------------|--------------|
| `follow_created` | 关注事务提交 | `user_follow` | `{follower_id}:{following_id}` |
| `follow_deleted` | 取关事务提交 | `user_follow` | `{follower_id}:{following_id}` |
| `user_deactivated` | 注销事务提交 | `user` | `{user_id}` |

**payload 示例（follow_created）**：

```json
{
  "event_id": 123,
  "follower_id": 1,
  "following_id": 2,
  "created_at": "2026-08-18 10:30:00",
  "created_at_ms": 1755508200000
}
```

- `created_at_ms` 由**服务端**在写事件时计算并写入 payload，消费端直接用作 ZADD score——避免消费端做 naive datetime ↔ 时间戳换算引入时区偏差（读路径边界 B-23 的教训）。
- **user_deactivated payload**：`{"user_id": 5, "following_ids": [...], "follower_ids": [...], "truncated": false}`。列表截断上限 `OUTBOX_DEACTIVATED_PAYLOAD_LIMIT=50000`（当前量级 ≤1万，永不触发）；超限截断部分靠缓存 TTL（1天）自愈，事件内 `truncated=true` 便于告警观察。

### 2.5 取关后缓存语义细节

- 取关**不主动写**空标记：取关至列表为空时，ZSET 仍在（翻页返回空），下次回源重建时自然打空标记（读路径既有逻辑）。
- 取关**不 DEL 键**：只 ZREM/SREM 成员，保留剩余数据与 TTL。

## 三、Outbox 事件表设计

### 3.1 DDL

```sql
CREATE TABLE `outbox_event` (
  `id`             BIGINT UNSIGNED  NOT NULL AUTO_INCREMENT,
  `event_type`     VARCHAR(50)      NOT NULL COMMENT '事件类型 follow_created/follow_deleted/user_deactivated',
  `aggregate_type` VARCHAR(50)      NOT NULL COMMENT '聚合根类型 user_follow/user',
  `aggregate_id`   VARCHAR(64)      NOT NULL COMMENT '聚合根标识，user_follow为 follower_id:following_id，user为user_id',
  `payload`        JSON             NOT NULL COMMENT '事件负载（含实体字段快照，消费端免回查）',
  `status`         TINYINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0-待发布 1-已发布 2-死信(重试超限)',
  `retry_count`    INT UNSIGNED     NOT NULL DEFAULT 0 COMMENT '投递重试次数',
  `next_retry_at`  DATETIME         DEFAULT NULL COMMENT '下次允许重试时间（指数退避），NULL表示立即可投',
  `created_at`     DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `published_at`   DATETIME         DEFAULT NULL COMMENT '成功发布到MQ的时间',
  PRIMARY KEY (`id`),
  KEY `idx_status_retry` (`status`, `next_retry_at`, `id`),
  KEY `idx_published` (`status`, `published_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='事务性Outbox事件表（业务变更与事件同事务落库，异步投递MQ）';
```

### 3.2 字段与索引说明

| 索引 | 用途 |
|------|------|
| `PRIMARY (id)` | 自增主键 = 全局事件序号，**天然保证同一业务的事务内顺序**（Relay 按 id ASC 批量投递） |
| `idx_status_retry (status, next_retry_at, id)` | Relay 轮询扫描：`WHERE status=0 AND (next_retry_at IS NULL OR next_retry_at<=NOW()) ORDER BY id LIMIT batch` |
| `idx_published (status, published_at)` | 清理任务删除超期已发布事件 |

**设计要点**：

1. **事件表 = 通用基础设施**：不与 user_follow 耦合字段（不存 follower_id/following_id 独立列），业务字段全部在 `payload` JSON 中。后续帖子点赞、评论等事件直接复用该表。
2. **id 即顺序**：同事务内先写业务行再写事件行；跨事务按提交顺序获得 id。Relay 按 id 升序投递 + RabbitMQ 单队列 FIFO + 单消费者实例，保证同一关注关系的 created/deleted 事件**有序消费**（乱序风险见 6.3）。
3. **不做事件表与业务表的外键/关联约束**：沿用项目"无外键"原则。
4. **status 不设"发布中"态**：当前 Relay 单实例部署（挂 runner 进程），无抢占竞争；多实例演进见 6.4。
5. **`next_retry_at` 支持指数退避**：失败后 `retry_count+1`、`next_retry_at = NOW() + base * 2^retry_count`，防止毒消息打爆投递循环。

### 3.3 事件生命周期

```
写入(status=0) ──Relay投递成功──▶ status=1 (published_at=NOW())
      │                                   │
      │ 投递失败                            │ 清理任务（每日）
      ▼                                   ▼
  retry_count+1                    DELETE WHERE status=1
  next_retry_at=退避时间          AND published_at < NOW()-7天
      │                             (分批LIMIT 5000)
      ├─ retry_count < MAX ──▶ 回到待发布（到点重试）
      └─ retry_count ≥ MAX ──▶ status=2 死信（告警+人工排查）
```

## 四、MQ 配置

### 4.1 拓扑设计（扩展现有 exchanges.py / queues.py）

```
                                    ┌──────────────────────────────┐
              social.follow.created │                      social. │
  social.exchange ─────────────────▶│ social.follow.cache.queue    │──▶ FollowCacheSyncConsumer
  (topic, durable)                  │ (durable, DLX=dlx.social)    │
              social.follow.deleted │                              │
              social.user.deactivated                              │
                                    └──────────────┬───────────────┘
                                                   │ 消费失败 nack(requeue=False)
                                                   ▼
                                    ┌──────────────────────────────┐
                                    │ dlx.social (direct, durable) │
                                    │   └▶ social.follow.cache.dlq │──▶ 存档/告警/人工重放
                                    └──────────────────────────────┘
```

**新增配置项（代码层枚举，非环境变量）**：

| 项 | 值 | 说明 |
|----|-----|------|
| 交换机 `ExchangeName.SOCIAL` | `social.exchange` | topic，durable |
| 队列 `QueueName.SOCIAL_FOLLOW_CACHE` | `social.follow.cache.queue` | durable，绑定 DLX |
| 死信交换机 `ExchangeName.SOCIAL_DLX` | `dlx.social` | direct，durable |
| 死信队列 `QueueName.SOCIAL_FOLLOW_CACHE_DLQ` | `social.follow.cache.dlq` | durable，仅存档不消费 |

**routing_key 绑定（QUEUE_BINDINGS 追加）**：

| 队列 | 交换机 | routing_key | 触发事件 |
|------|--------|-------------|---------|
| `social.follow.cache.queue` | `social.exchange` | `social.follow.created` | follow_created |
| `social.follow.cache.queue` | `social.exchange` | `social.follow.deleted` | follow_deleted |
| `social.follow.cache.queue` | `social.exchange` | `social.user.deactivated` | user_deactivated |
| `social.follow.cache.dlq` | `dlx.social` | `social.follow.cache.dead` | 消费失败死信 |

routing_key 与 `event_type` 一一对应（`follow_created → social.follow.created`），Relay 投递时按 event_type 映射，消费端无需判断来源。

**队列声明改造**：`declare_queue` 需支持 `arguments` 参数，`social.follow.cache.queue` 声明时携带：

```python
arguments = {
    "x-dead-letter-exchange": ExchangeName.SOCIAL_DLX.value,
    "x-dead-letter-routing-key": "social.follow.cache.dead",
}
```

> 现有 `BaseConsumer` 对处理失败消息是 nack(requeue=False) 直接丢弃（原注释即标注"生产应配死信队列"）。本方案为该队列补齐 DLX 后，丢弃变为**进死信队列存档**，支撑人工重放与告警，消除静默丢失。

### 4.2 消息格式（复用现有信封）

复用 `MQProducer._build_body` 的统一信封：

```json
{
  "message_id": "123",
  "timestamp": "2026-08-18T10:30:00.123456+00:00",
  "payload": { "...": "outbox_event.payload 原样透传" }
}
```

- **`message_id = str(outbox_event.id)`**：链路追踪三段统一（DB 行 id → MQ message_id → Consumer 日志），也是消费幂等键。
- 消息 `delivery_mode=2`（持久化）+ 队列 durable + Broker 持久化，Broker 重启不丢。

### 4.3 可靠性配置

| 配置 | 值 | 说明 |
|------|-----|------|
| `RABBITMQ_PREFETCH_COUNT` | 8（现有值复用） | 缓存同步轻量，8 并发足够；乱序风险见 6.3 |
| publisher confirm | **Relay 通道必须开启** | `channel(publisher_confirms=True)`，收到 confirm 才标记 status=1；否则 Broker 落盘前宕机会"已标记未投递"，破坏 at-least-once |
| RobustConnection | 现有 | 断线自动重连，Relay/Consumer 均受益 |

> 现有 `MQProducer` 未开 confirm（面试业务可容忍极端丢失）。Relay 使用**独立通道**并开启 confirm，不改动现有 Producer 语义。

### 4.4 环境配置（config.py 追加）

```python
# ---- Outbox 事件投递配置 ----
OUTBOX_POLL_INTERVAL: float = 0.5        # Relay轮询间隔（秒）
OUTBOX_BATCH_SIZE: int = 100             # 单批扫描与投递条数
OUTBOX_MAX_RETRY: int = 5                # 投递最大重试次数，超限置死信
OUTBOX_RETRY_BASE_DELAY: int = 5         # 重试退避基数（秒），实际延迟=base*2^retry_count
OUTBOX_RETENTION_DAYS: int = 7           # 已发布事件保留天数，清理任务超期删除
OUTBOX_CLEANUP_BATCH: int = 5000         # 清理任务单批DELETE上限
OUTBOX_DEACTIVATED_PAYLOAD_LIMIT: int = 50000  # 注销事件payload中ID列表截断上限
```

## 六、Outbox Relay（投递器）设计

### 6.1 主循环（`app/mq/outbox_relay.py`，asyncio 任务）

```
每 OUTBOX_POLL_INTERVAL 秒:
  1. SELECT id, event_type, payload FROM outbox_event
     WHERE status = 0 AND (next_retry_at IS NULL OR next_retry_at <= NOW())
     ORDER BY id ASC LIMIT OUTBOX_BATCH_SIZE            ← 命中 idx_status_retry
  2. 无记录 → continue
  3. 逐条投递（独立 confirm 通道）:
     a. routing_key = event_type 映射（follow_created → social.follow.created）
     b. message_id = str(id)，await publish（等待 publisher confirm）
     c. 成功 → UPDATE status=1, published_at=NOW() WHERE id=? AND status=0
     d. 失败 → UPDATE retry_count=retry_count+1,
                next_retry_at = NOW() + INTERVAL (BASE * 2^retry_count) SECOND
              若 retry_count+1 >= OUTBOX_MAX_RETRY → status=2（死信，logger.error 告警）
```

- **逐条确认而非批量**：confirm 语义下逐条标记，单条失败不影响本批其余事件（批量事务标记会在部分成功时整体回滚造成重复投递——重复投递无害但浪费，逐条更精准）。
- 重复投递容忍：消费端全幂等（见 7.1），at-least-once 语义成立。

### 6.2 清理任务（低频，随 Relay 每 10 分钟执行一次）

```
DELETE FROM outbox_event WHERE status = 1
  AND published_at < NOW() - INTERVAL OUTBOX_RETENTION_DAYS DAY
LIMIT OUTBOX_CLEANUP_BATCH          ← 循环执行至 affected_rows=0，避免大事务长锁
```

### 6.3 顺序性分析

| 环节 | 保证 | 说明 |
|------|------|------|
| outbox 表内 | ✅ 自增 id | 同一事务/同一用户连续操作的 created→deleted 事件 id 严格递增 |
| Relay 投递 | ✅ 单实例按 id ASC | 批内顺序发布 |
| RabbitMQ 队列 | ✅ 单队列 FIFO | durable 队列 |
| 消费端 | ⚠️ prefetch=8 | **单消费者实例**下按投递顺序处理（aio-pika 逐条回调，回调内 await 完成才处理下一条） |

**残留乱序场景**：同一用户 A 对同一目标 B 在毫秒级内"关注→取关"连发两条事件，且未来扩展为多消费者实例（round-robin 分发）时可能乱序消费 → 缓存残留 member B（DB 已无关系）。缓解：① 当前单实例部署无此问题；② 残留数据 TTL 1 天自愈 + 回源以 DB 为准；③ 演进期若需多实例，改按 `aggregate_id` 一致性哈希拆分队列（保证同 key 同队列）。

### 6.4 多实例演进（当前不实施）

单实例 Relay 足够支撑当前量级（关注 QPS 远低于 1000/s 扫描能力）。多 API 实例部署时的演进：投递前原子抢占 `UPDATE outbox_event SET status=3(处理中) WHERE id IN (...) AND status=0`，检查 affected rows 后发布，并增加"处理中超时回收"任务（status=3 且超过 60s 未发布 → 重置为 0）。

## 七、Consumer 设计（缓存同步）

### 7.1 幂等性基础

缓存同步全部使用**天然幂等**的 Redis 命令（ZADD 同 member 同 score 覆盖、SADD/SREM/DEL/ZREM 重复执行结果不变），重复消费无需去重表；`message_id`（= outbox id）仅用于日志追踪。

### 7.2 各事件处理命令（redis.asyncio pipeline）

**follow_created**（A=follower_id，B=following_id，ts=payload.created_at_ms）：

```
MULTI:
  ZADD  follow:z:following:{A}  {ts} {B}     ← score 与读路径回源一致（同 created_at）
  ZADD  follow:z:followers:{B}  {ts} {A}
  SADD  follow:s:following:{A}  {B}
  SADD  follow:s:followers:{B}  {A}
  DEL   follow:empty:following:{A}           ← 闭环 B-5：空标记期内新关注立即可见
  DEL   follow:empty:followers:{B}
  EXPIRE follow:z:following:{A}  FOLLOW_CACHE_TTL    ← ZADD 已确保键存在，刷新滑动TTL
  EXPIRE follow:z:followers:{B}  FOLLOW_CACHE_TTL
  EXPIRE follow:s:following:{A}  FOLLOW_CACHE_TTL
  EXPIRE follow:s:followers:{B}  FOLLOW_CACHE_TTL
EXEC → 成功 ack
```

> ZSET 为部分回源（仅最近 1000 条）也无碍：ZADD 追加最新成员，zcard+1 仅影响 B-9 降级启发式判定（保守方向，安全）。

**follow_deleted**（A=follower_id，B=following_id）：

```
MULTI:
  ZREM  follow:z:following:{A}  {B}
  ZREM  follow:z:followers:{B}  {A}
  SREM  follow:s:following:{A}  {B}
  SREM  follow:s:followers:{B}  {A}
EXEC → 成功 ack
```

> 不写空标记、不删键（见 2.5）。若键本就不存在（未回源），命令空操作，无害。

**user_deactivated**（U=user_id，following_ids=U关注的人，follower_ids=U的粉丝）：

```
MULTI:
  DEL follow:z:following:{U} follow:z:followers:{U}
      follow:s:following:{U} follow:s:followers:{U}    ← 闭环 B-14：清自身4键
# 分批 pipeline（每500个ID一批，避免大pipeline阻塞）:
  对 X in following_ids:                               ← 从"U关注的人"的粉丝缓存中移除U
    ZREM follow:z:followers:{X} {U}
    SREM follow:s:followers:{X} {U}
  对 Y in follower_ids:                                ← 从"U的粉丝"的关注缓存中移除U
    ZREM follow:z:following:{Y} {U}
    SREM follow:s:following:{Y} {U}
全部批次成功 → ack（任一批失败 → 异常 → nack → DLQ）
```

### 7.3 失败与死信

- pipeline 抛异常（Redis 不可用等）→ `BaseConsumer` 既有策略 nack(requeue=False) → **进入 DLQ 存档**，同时该消息日志含 message_id 可回溯 outbox 行；
- DLQ 消息人工处理：排查 Redis 故障后，按 DLQ 消息头 x-death 原始 routing_key 重放（或等待 TTL 自愈——缓存最终以 DB 为准，1 天内全部修正）；
- 告警：DLQ 队列深度 > 0 时告警（运维监控项）。

---

## 八、异常场景与一致性保证汇总

| # | 故障点 | 行为 | 一致性影响 | 恢复机制 |
|---|--------|------|-----------|---------|
| 1 | DB 事务失败 | 业务与事件同回滚 | 无 | 客户端重试 |
| 2 | 事务提交后、Relay 轮询前宕机 | 事件滞留 status=0 | 秒~分钟级缓存滞后 | 进程重启后 Relay 补投 |
| 3 | MQ 发布失败/未 confirm | retry 退避重试 | 投递延迟增长 | 退避重试 + 死信告警 |
| 4 | Broker 落盘前宕机 | confirm 未回，status 仍 0 | 无丢失 | 重启后重投（可能重复，幂等消化） |
| 5 | Consumer 处理失败（Redis 故障） | nack → DLQ | 该事件对应缓存滞后 | 人工重放 或 TTL 自愈（≤1天） |
| 6 | 消费中 Consumer 崩溃 | 未 ack，Broker 重投 | 可能重复消费 | Redis 命令幂等，安全 |
| 7 | 乱序（多消费者实例，当前未启用） | 缓存残留脏 member | 关系判断误报 | TTL 自愈；演进按 aggregate 哈希分队列 |
| 8 | Relay 停摆数小时 | outbox 积压 | 缓存普遍滞后 | 读路径回源 DB 兜底（性能降级但正确）；恢复后顺序补投 |

**兜底原则**：Redis 任何状态损坏，读路径回源重建均以 DB 为准（singleflight + 空标记），Outbox/MQ 全链路故障最坏退化为"缓存滞后 1 天 TTL"，**永不产生错误数据**（只会短暂滞后）。

| 边界 | 读路径状态 | 本方案闭环方式 |
