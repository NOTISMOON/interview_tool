> 更新日期：2026-08-20

## 1. 功能模块概述

### 1.1 模块目标

实现社区帖子核心功能，包括：

* 帖子发布（含状态机：draft → published → hidden → deleted）
* 帖子删除（软删除，status=0）
* 帖子详情查询（Cache-Aside + 缓存三大防护）
* 评论互动（类抖音扁平模型，root_id 区分层级）
* 点赞互动（Redis SET 防重 + Outbox 异步落库）
* 收藏功能（Redis SET 防重 + Outbox 异步落库）
* 用户动态 Feed（Push-Pull 混合模型，大 V 降级拉取）
* 消息通知（复用现有 notification.created 事件）
* 热门帖子计算（定时任务 + Redis 分布式锁）

### 1.2 复用现有基础设施

| 基础设施 | 代码位置 | 帖子模块如何复用 |
|----------|---------|----------------|
| **Transactional Outbox** | `app/models/outbox_event.py` + `app/repositories/outbox_repository.py` + `app/mq/outbox_relay.py` | 发帖/点赞/评论等写操作在同一 MySQL 事务内写入 outbox_event，Relay 异步投递到 MQ |
| **Redis 同步分布式锁** | `app/redis/sync_lock.py` (`RedisLock`) | 热门帖子计算定时任务加锁，防止多实例重复执行 |
| **Redis 异步分布式锁** | `app/redis/async_lock.py` (`AsyncRedisLock`) | Agent 业务中需要互斥的异步操作 |
| **MQ 消费者基类** | `app/mq/consumer.py` (`BaseConsumer`) | 帖子/点赞/评论事件消费者继承 BaseConsumer，自动获得 ACK/Reject/DLQ 能力 |
| **MQ 生产者** | `app/mq/producer.py` (`MQProducer`) | Relay 投递时使用，消息自动持久化 + message_id 追踪 |
| **死信队列（DLQ）** | `app/mq/queues.py` (DLX 配置) | 帖子事件消费失败自动进入 DLQ 存档，人工重放 |
| **通知服务** | `app/services/notification_service.py` | 帖子的点赞/评论通知复用 notification.created Outbox 事件 |
| **关注缓存** | `app/cache/follow_cache.py` | Feed 推送时复用粉丝列表查询 |
| **Redis 客户端** | `app/redis/sync_client.py` + `app/redis/async_client.py` | 缓存读写、点赞 SET、Feed ZSET 等 |

## 2. 帖子状态机

### 2.1 状态定义

帖子采用软删除模型，通过 `status` 字段管理生命周期（与数据库设计文档 `post` 表一致）：

```
status = 0  → 已删除（软删除，数据保留）
status = 1  → 正常（已发布，公开可见）
```

> 当前阶段不引入草稿态和审核态，后续如需扩展可增加 status=2（草稿）、status=3（审核中）。

### 2.2 状态转换

```
用户创建帖子
      ↓
   status=1（正常）
      ↓
      ├── 用户删除 → status=0（已删除）
      └── 用户编辑 → 仍为 status=1（更新内容）
```

已删除的帖子：
- 详情接口返回 404
- 列表接口不展示
- 已有的评论/点赞保留（关联数据不物理删除）
- Feed 中移除引用

## 3. 帖子发布流程

### 3.1 写路径：Transactional Outbox（同步事务）

遵循现有关注/取关的写路径模式，**业务变更与事件写入共用同一个 MySQL 同步事务**：

```
用户发起发帖请求
      ↓
FastAPI 路由层（同步，Depends(get_db)）
      ↓
PostService.create_post()
      ↓
db.begin() 开启事务
      ↓
① INSERT post（状态=1，创建帖子记录）
      ↓
② 更新 user.posts_count +1
      ↓
③ INSERT user_activity（type=4，发帖动态）
      ↓
④ INSERT post_tag（标签关联）
      ↓
⑤ INSERT outbox_event（event_type="post.created"）
      ↓
⑥ INSERT outbox_event（event_type="notification.created"，通知粉丝用）
      ↓
db.commit() 事务提交
      ↓
返回帖子详情
```

**关键约束**：步骤 ①~⑥ 必须在同一个 `db` 会话内、同一个事务中完成，禁止拆分会话。事务提交即保证业务数据与事件同时落库，Outbox Relay 异步投递到 MQ。

### 3.2 Outbox 事件定义

**post.created**：

```json
{
  "event_type": "post.created",
  "aggregate_type": "post",
  "aggregate_id": "{post_id}",
  "payload": {
    "post_id": 123,
    "author_id": 456,
    "title": "帖子标题",
    "created_at": "2026-08-20T10:00:00",
    "created_at_ms": 1724140800000
  }
}
```

**notification.created**（通知粉丝，复用现有通知基础设施）：

```json
{
  "event_type": "notification.created",
  "aggregate_type": "message",
  "aggregate_id": "{粉丝user_id}",
  "payload": {
    "recipient_id": 789,
    "type": 2,
    "title": "新帖子",
    "content": "{作者昵称} 发布了新帖子《{帖子标题}》",
    "from_user_id": 456,
    "related_id": 123,
    "related_type": 1
  }
}
```

> 注意：如果作者粉丝量很大（如 >1000），通知粉丝不应在事务内逐条插入，而是由 MQ 消费端异步批量处理。事务内只插入一条 `post.created` 事件，消费端收到后查询粉丝列表并批量写入 notification.created 事件。

### 3.3 异步处理流程（MQ 消费端）

```
post.created 事件到达 SOCIAL Exchange
      ↓
PostFeedConsumer 消费
      ↓
① 查询作者粉丝列表（通过 follow_cache 或 DB）
      ↓
② 区分普通用户 vs 大 V（粉丝数 > FEED_PUSH_FAN_THRESHOLD）
      ↓
③ 普通用户：写入粉丝 Feed ZSET（PUSH 模式）
      ↓
④ 大 V：不写入 Feed，粉丝拉取时动态合并（PULL 模式）
      ↓
⑤ 为粉丝批量生成 notification.created 通知
```

## 4. 帖子查询流程

### 4.1 帖子详情查询（Cache-Aside + 三大防护）

**缓存 Key**：

```
post:detail:{post_id}
```

**缓存内容**（JSON 序列化）：

```json
{
  "id": 123,
  "author_id": 456,
  "title": "帖子标题",
  "content": "帖子内容",
  "tags": ["Python", "FastAPI"],
  "likes_count": 42,
  "comments_count": 15,
  "views_count": 1024,
  "is_pinned": false,
  "is_hot": false,
  "status": 1,
  "created_at": "2026-08-20T10:00:00",
  "updated_at": "2026-08-20T10:00:00"
}
```

**TTL**：`POST_DETAIL_CACHE_TTL = 1800`（30 分钟），写操作时主动删除缓存，靠下次读取回填。

### 4.2 缓存三大防护

| 场景 | 问题 | 方案 |
|------|------|------|
| **缓存穿透** | 恶意查询不存在的 post_id，每次穿透到 MySQL | ① 缓存空值：`post:detail:{id}` → `"NULL"`，TTL=60s；② 布隆过滤器（后续可选） |
| **缓存击穿** | 热点帖子缓存过期瞬间，大量请求打到 MySQL | ① Redis 分布式锁互斥回源（`RedisLock("post:rebuild:{post_id}", timeout=10)`）；② 逻辑过期方案（后续可选） |
| **缓存雪崩** | 大量缓存在同一时间过期 | ① TTL 加随机偏移：`TTL = 1800 + random(0, 300)`；② 预加载热门帖子（后续可选） |

### 4.3 缓存穿透防护流程

```
用户请求帖子详情
      ↓
查询 Redis post:detail:{post_id}
      ↓
    ┌─ 命中 "NULL" → 返回 404（不发 DB 查询）
    │
    ├─ 命中正常数据 → 返回数据
    │
    └─ 未命中（Key 不存在）
          ↓
      获取分布式锁 lock:post:rebuild:{post_id}
          ↓
      ┌─ 获取失败 → 等待 200ms 后重试读缓存
      │
      └─ 获取成功 → double-check 缓存
            ↓
        ┌─ 缓存已存在 → 释放锁，返回数据
        │
        └─ 缓存不存在
              ↓
          查询 MySQL
              ↓
          ┌─ 帖子存在 → 写 Redis（TTL + 随机偏移），释放锁，返回数据
          │
          └─ 帖子不存在/已删除 → 写 Redis "NULL"（TTL=60s），释放锁，返回 404
```

### 4.4 帖子列表查询

列表查询不走 Redis 缓存（变化频繁，缓存命中率低），直接查 MySQL 利用已有索引：

- **首页/最新**：`idx_created_at(status, created_at DESC)`
- **热门排序**：`idx_status_hot(status, is_hot DESC, likes_count DESC)`
- **用户帖子**：`idx_author_id(author_id)`

## 5. 帖子更新流程

### 5.1 帖子修改

```
用户修改帖子
      ↓
权限校验（仅作者本人）
      ↓
更新 MySQL（title、content、tags）
      ↓
更新 post_tag 表（先删后插）
      ↓
删除 Redis 缓存 post:detail:{post_id}
      ↓
下一次访问触发 Cache-Aside 回源
```

### 5.2 缓存策略

采用 **删除缓存** 而非更新缓存，原因：

```
MySQL 更新成功 → Redis 更新失败 → 数据不一致（脏缓存）
```

改为：

```
MySQL 更新成功 → 删除 Redis → 下次读取回源（总是正确的）
```

### 5.3 帖子编辑事件（可选）

当前阶段帖子编辑不需要推送 Feed 更新。如需支持"编辑后重新推送"，可增加 `post.updated` 事件。

## 6. 帖子删除流程

### 6.1 软删除

遵循数据库设计文档的软删除约定，`status=0` 而非物理删除：

```
用户删除帖子
      ↓
权限校验（仅作者本人）
      ↓
db.begin() 开启事务
      ↓
① UPDATE post SET status=0 WHERE id={post_id}
      ↓
② 更新 user.posts_count -1
      ↓
③ INSERT outbox_event（event_type="post.deleted"）
      ↓
db.commit() 事务提交
      ↓
④ 删除 Redis 缓存 post:detail:{post_id}
      ↓
⑤ 返回成功
```

### 6.2 post.deleted 事件

```json
{
  "event_type": "post.deleted",
  "aggregate_type": "post",
  "aggregate_id": "{post_id}",
  "payload": {
    "post_id": 123,
    "author_id": 456
  }
}
```

### 6.3 消费端处理

```
post.deleted 事件到达
      ↓
① 从所有粉丝 Feed ZSET 中移除 post_id（ZREM）
      ↓
② 从热门帖子 ZSET 中移除 post_id
      ↓
③ 删除帖子详情缓存
```

**注意**：评论和点赞数据保留不物理删除，但查询时通过 `post.status=0` 过滤，对用户不可见。

## 7. 评论功能流程

### 7.1 评论模型

采用数据库设计文档中已定义的**类抖音扁平模型**，`root_id` 区分层级：

```
一级评论: root_id IS NULL, reply_user_id IS NULL
回复:     root_id = 一级评论ID, reply_user_id = 被回复者ID
```

### 7.2 添加评论（写路径）

```
用户发起评论请求
      ↓
db.begin() 开启事务
      ↓
① 校验帖子存在且 status=1
      ↓
② 如果是回复：查询被回复评论，确定 root_id 和 reply_user_id
      ↓
③ INSERT comment
      ↓
④ 更新一级评论 reply_count +1（仅当 root_id IS NOT NULL）
      ↓
⑤ 更新 post.comments_count +1
      ↓
⑥ INSERT outbox_event（event_type="comment.created"）
      ↓
⑦ INSERT outbox_event（event_type="notification.created"，通知帖子作者）
      ↓
db.commit() 事务提交
      ↓
⑧ 删除帖子详情缓存 post:detail:{post_id}（comments_count 已变更）
      ↓
返回评论详情
```

### 7.3 comment.created 事件

```json
{
  "event_type": "comment.created",
  "aggregate_type": "comment",
  "aggregate_id": "{comment_id}",
  "payload": {
    "comment_id": 789,
    "post_id": 123,
    "root_id": null,
    "author_id": 456,
    "reply_user_id": null,
    "post_author_id": 999,
    "content_preview": "评论内容前50字",
    "created_at_ms": 1724140800000
  }
}
```

### 7.4 评论查询

评论不走 Redis 缓存，直接查 MySQL（利用 `idx_post_root` 索引）：

```sql
-- 一级评论分页
SELECT * FROM comment
WHERE post_id = ? AND root_id IS NULL AND status = 1
ORDER BY created_at DESC
LIMIT ? OFFSET ?;

-- 某条一级评论的回复
SELECT * FROM comment
WHERE root_id = ? AND status = 1
ORDER BY created_at ASC
LIMIT ?;
```

## 8. 点赞功能流程

### 8.1 点赞设计

**核心原则**：
- 写路径：先写 Redis SET（防重 + 实时判断），再通过 Outbox 异步落 MySQL
- 读路径：优先读 Redis SET（O(1) 判断是否已点赞），计数以 MySQL 为准
- 幂等：Redis SADD 天然幂等，MySQL 唯一索引 `uk_post_user` 兜底

### 8.2 点赞（写路径）

```
用户发起点赞请求
      ↓
Redis SADD post:likes:{post_id} {user_id}
      ↓
    ┌─ 返回 0 → 已点赞，直接返回成功（幂等）
    │
    └─ 返回 1 → 首次点赞
          ↓
      异步：通过 Outbox 投递 like.created 事件
          ↓
      实时：Redis INCR post:like:count:{post_id}（临时计数，用于快速展示）
          ↓
      返回成功
```

> **注意**：点赞操作不阻塞在 DB 事务上。Redis 写入成功后立即返回，Outbox 事件由 Relay 异步投递，消费端异步落 MySQL。这带来秒级的最终一致性，但用户体验是即时的。

### 8.3 取消点赞（写路径）

```
用户发起取消点赞请求
      ↓
Redis SREM post:likes:{post_id} {user_id}
      ↓
    ┌─ 返回 0 → 未点赞，直接返回成功（幂等）
    │
    └─ 返回 1 → 取消成功
          ↓
      异步：通过 Outbox 投递 like.deleted 事件
          ↓
      Redis DECR post:like:count:{post_id}
          ↓
      返回成功
```

### 8.4 点赞事件定义

**like.created**：

```json
{
  "event_type": "like.created",
  "aggregate_type": "post_like",
  "aggregate_id": "{post_id}:{user_id}",
  "payload": {
    "post_id": 123,
    "user_id": 456,
    "post_author_id": 999,
    "created_at_ms": 1724140800000
  }
}
```

**like.deleted**：

```json
{
  "event_type": "like.deleted",
  "aggregate_type": "post_like",
  "aggregate_id": "{post_id}:{user_id}",
  "payload": {
    "post_id": 123,
    "user_id": 456
  }
}
```

### 8.5 消费端处理（幂等）

```
like.created 事件到达
      ↓
① INSERT INTO post_like (post_id, user_id)（唯一索引 uk_post_user 兜底幂等）
      ↓
② UPDATE post SET likes_count = likes_count + 1
      ↓
③ 删除帖子详情缓存 post:detail:{post_id}
      ↓
④ 生成 notification.created 通知帖子作者
```

```
like.deleted 事件到达
      ↓
① DELETE FROM post_like WHERE post_id=? AND user_id=?
      ↓
② UPDATE post SET likes_count = GREATEST(likes_count - 1, 0)（防无符号溢出）
      ↓
③ 删除帖子详情缓存 post:detail:{post_id}
```

### 8.6 点赞状态查询

```
用户 A 查看帖子列表，需要判断是否已点赞
      ↓
批量查询 Redis：SMISMEMBER post:likes:{post_id} {user_id_1} {user_id_2} ...
      ↓
返回每个帖子的 is_liked 标记
```

### 8.7 点赞数据可靠性保障

| 风险 | 方案 |
|------|------|
| **Redis 宕机丢失点赞关系** | ① Redis AOF + RDB 持久化；② MySQL `post_like` 表有完整记录，Redis 重启后可通过 DB 回源重建 |
| **MQ 消息丢失** | Outbox Relay 使用 publisher confirm，收到 confirm 才标记已发布，保证 at-least-once |
| **MQ 消息重复** | 消费端使用 MySQL 唯一索引 `uk_post_user` 兜底幂等，`INSERT ... ON DUPLICATE KEY UPDATE` 或捕获 `IntegrityError` |
| **点赞计数不一致** | 以 MySQL `post.likes_count` 为准，Redis 计数仅用于快速展示，定时任务可对账修复 |
| **消息乱序（创建→删除→创建）** | 单队列 FIFO + 单消费者实例保证同一 post 内事件有序 |

## 10. 用户动态 Feed 功能

### 10.1 功能目标

用户查看"关注的人发布了什么内容"，按时间倒序分页。

### 10.2 Push-Pull 混合模型

**核心问题**：纯 Push 模式下，大 V（粉丝 >10 万）发一条帖子需要写 10 万次 Redis Feed ZSET，不可接受。

**方案**：Push-Pull 混合模型

```
粉丝数 <= FEED_PUSH_FAN_THRESHOLD（默认 1000）：
  → PUSH 模式：发帖后立即写入所有粉丝的 Feed ZSET

粉丝数 > FEED_PUSH_FAN_THRESHOLD：
  → PULL 模式：不写入粉丝 Feed，粉丝拉取时动态合并
```

### 10.3 Feed 缓存设计

**Redis Key**：

```
feed:user:{user_id}
```

**数据结构**：ZSET

```
score = 帖子发布时间（毫秒时间戳）
member = post_id
```

**示例**：

```
feed:user:1001

post1005  1724140800000
post1008  1724140900000
```

**容量限制**：每个 Feed ZSET 最多保留 `FEED_MAX_SIZE = 1000` 条，写入时检查：

```
ZADD feed:user:{user_id} {score} {post_id}
ZCARD feed:user:{user_id}
  → 如果 > 1000 → ZREMRANGEBYRANK feed:user:{user_id} 0 0（删除最旧一条）
```

### 10.4 消费端 Feed 推送

```
post.created 事件到达
      ↓
① 查询作者粉丝数
      ↓
    ┌─ 粉丝数 <= 1000（普通用户）
    │     ↓
    │  查询所有粉丝 ID
    │     ↓
    │  批量 ZADD feed:user:{粉丝ID} {score} {post_id}
    │     ↓
    │  批量 ZREMRANGEBYRANK（超出容量限制）
    │
    └─ 粉丝数 > 1000（大V）
          ↓
       不写入粉丝 Feed（标记为"大V发帖"即可）
```

### 10.5 Feed 查询（读路径）

```
用户请求 Feed 第一页
      ↓
① 从 Feed ZSET 获取 post_id 列表（ZREVRANGEBYSCORE，按时间倒序）
      ↓
② 从"大V关注列表"获取大V近期帖子（PULL 模式补充）
      ↓
③ 合并 + 去重 + 按时间倒序
      ↓
④ 批量查询 MySQL 获取帖子详情
      ↓
⑤ 批量查询 Redis SMISMEMBER 获取点赞状态
      ↓
返回帖子列表
```

### 10.6 Feed 空列表防穿透

与关注缓存保持一致，使用空标记：

```
feed:empty:{user_id}  →  TTL = 60s
```

新用户或关注列表为空时，缓存空标记避免每次都穿透到 DB。

### 11.1 复用现有通知基础设施

帖子模块的通知**完全复用现有 `notification.created` Outbox 事件**，无需新建通知通道。

## 12. 热门帖子功能

### 12.1 热度计算公式

```
score = 点赞数 × 3 + 评论数 × 5 + 浏览数 × 0.1 - 时间衰减

时间衰减 = (当前时间 - 发布时间) / 3600 × 衰减系数

衰减系数 = 1.5（每小时衰减 1.5 分）
```

### 12.2 浏览数收集

浏览数不实时写 MySQL（高并发下写压力大），采用 **Redis 计数器 + 定时同步** 方案：

```
用户浏览帖子
      ↓
Redis INCR post:views:{post_id}（当天）
      ↓
定时任务（每 5 分钟）
      ↓
读取所有 post:views:{post_id} 的值
      ↓
批量 UPDATE post SET views_count = views_count + ?
      ↓
DELETE post:views:{post_id}（重置当天计数）
```

### 12.3 热门帖子计算流程

定时任务 + **Redis 分布式锁**（防止多实例重复执行）：

```
定时任务触发（每 10 分钟）
      ↓
获取分布式锁 lock:hot:calc（timeout=120s，auto_renewal=True）
      ↓
    ┌─ 获取失败 → 退出（其他实例正在执行）
    │
    └─ 获取成功
          ↓
      ① 查询近 7 天发布的帖子（status=1）
          ↓
      ② 对每条帖子计算热度分
          ↓
      ③ 更新 post.is_hot 标记（热度 Top 100）
          ↓
      ④ 写入 Redis ZSET post:hot（score=热度分，member=post_id）
          ↓
      ⑤ 释放分布式锁
```

### 12.4 热门帖子查询

```python
# 查询热门 Top 20
redis.zrevrange("post:hot", 0, 19, withscores=True)

# 返回 [(post_id, score), ...]
# 批量查询 MySQL 获取帖子详情
```

### 12.5 分布式锁实现

使用项目已有的 `RedisLock`（`app/redis/sync_lock.py`）：

```python
from app.redis.sync_lock import RedisLock

def calc_hot_posts():
    """计算热门帖子（定时任务入口）。"""
    lock = RedisLock(
        name="hot:calc",
        timeout=120,       # 120 秒超时
        retry_count=0,     # 不重试，拿不到锁就跳过
        auto_renewal=True, # 自动续期，防止长任务锁过期
    )
    with lock:
        # 执行热度计算...
        pass
```

### 13.3 消息可靠性保障

| 机制 | 实现 |
|------|------|
| **消息持久化** | `delivery_mode=PERSISTENT`，Broker 重启不丢消息 |
| **Publisher Confirm** | Outbox Relay 使用独立 confirm 通道，收到确认才标记已发布 |
| **消费端 ACK** | BaseConsumer 自动处理：成功 ack，失败 reject(requeue=False) |
| **死信队列（DLQ）** | 消费失败消息经 DLX 进入 `*.dlq` 队列存档，人工重放 |
| **幂等性** | 点赞/收藏用 MySQL 唯一索引；Feed 操作用 Redis 幂等命令（ZADD/ZREM/SADD/SREM） |
| **消息顺序性** | 同一 aggregate 的事件路由到同一队列，FIFO 保证顺序 |
| **指数退避重试** | Outbox 投递失败按 `base_delay * 2^retry_count` 退避，超限置死信 |

## 15. 接口限流设计

| 接口 | 限流策略 | 限流 Key | 说明 |
|------|---------|---------|------|
| 发帖 | 每分钟 5 条 | `rate:post:create:{user_id}` | 防止刷帖 |
| 评论 | 每分钟 10 条 | `rate:comment:create:{user_id}` | 防止刷评论 |
| 点赞 | 每秒 5 次 | `rate:like:toggle:{user_id}` | 防止快速点赞/取消 |
| 收藏 | 每秒 5 次 | `rate:favorite:toggle:{user_id}` | 防止快速收藏/取消 |

限流实现使用 Redis 滑动窗口（可复用现有中间件或新增）：

```python
# 伪代码
def check_rate_limit(user_id: int, action: str, limit: int, window: int) -> bool:
    key = f"rate:{action}:{user_id}"
    now = time.time()
    # 移除窗口外的记录
    redis.zremrangebyscore(key, 0, now - window)
    # 统计当前窗口内请求数
    count = redis.zcard(key)
    if count >= limit:
        return False  # 触发限流
    # 添加当前请求
    redis.zadd(key, {str(now): now})
    redis.expire(key, window)
    return True
```

```
                       用户请求
                          |
                          ↓
                    FastAPI 服务
                          |
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                  ↓
      MySQL            Redis              RabbitMQ
   核心数据存储      缓存 + 状态        异步事件总线
        │                 │                  │
        │                 │                  ↓
        │                 │           ┌──────────────┐
        │                 │           │  Outbox Relay │
        │                 │           │  (独立进程)    │
        │                 │           └──────┬───────┘
        │                 │                  │
        │                 │     ┌────────────┼────────────┐
        │                 │     ↓            ↓            ↓
        │                 │  PostFeed   PostLike    Notification
        │                 │  Consumer   Consumer    Consumer
        │                 │     │            │            │
        │                 │     ↓            ↓            ↓
        │                 │  Feed ZSET   MySQL同步   消息推送
        │                 │  热门ZSET    计数更新      SSE
        │                 │
        │                 └──────────────┬──────────────┘
        │                                │
        ↓                                ↓
   ┌──────────────────────────────────────────┐
   │              定时任务服务                  │
   │                                          │
   │  ┌─────────────┐  ┌──────────────┐       │
   │  │ 热门帖子计算  │  │ 浏览数同步    │       │
   │  │ (分布式锁)   │  │ (Redis→MySQL) │       │
   │  └─────────────┘  └──────────────┘       │
   │                                          │
   │  ┌─────────────┐  ┌──────────────┐       │
   │  │ 缓存对账     │  │ 死信清理      │       │
   │  └─────────────┘  └──────────────┘       │
   └──────────────────────────────────────────┘
```

**关键设计决策汇总**：

| 决策 | 选择 | 原因 |
|------|------|------|
| 写路径一致性 | Transactional Outbox | 业务与事件原子落库，Relay 异步投递，与现有关注/取关一致 |
| 缓存模式 | Cache-Aside + 删除策略 | 避免更新缓存失败导致不一致 |
| 缓存穿透 | 空值缓存 + 分布式锁回源 | 防止恶意查询穿透到 DB |
| 缓存击穿 | 分布式锁互斥回源 | 热点过期时单线程回源，其余等待 |
| 缓存雪崩 | TTL 随机偏移 | 避免大量缓存同时过期 |
| Feed 模式 | Push-Pull 混合 | 大 V 粉丝量大时避免写扩散 |
| 点赞一致性 | Redis 先写 + Outbox 异步落 MySQL | 用户体验即时，最终一致 |
| 消息可靠性 | Publisher Confirm + DLQ + 幂等 | at-least-once 投递，消费端幂等兜底 |
| 帖子删除 | 软删除（status=0） | 数据可恢复，关联数据不丢失 |
| 定时任务互斥 | Redis 分布式锁 | 防止多实例重复执行热门计算 |
| 浏览数统计 | Redis 计数器 + 定时同步 | 避免高并发下频繁写 MySQL |
