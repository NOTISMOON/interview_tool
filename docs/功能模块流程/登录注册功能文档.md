## 一、需求概述

### 1.1 当前状态

| 维度 | 现状 |
|------|------|
| 登录方式 | 仅支持 GitHub OAuth 登录 |
| 令牌机制 | 双 Token：access_token（JWT，30min）+ refresh_token（不透明，7天），Redis 轮转 |
| 令牌存储 | HttpOnly Cookie（JS 不可读），refresh_token 限定 `Path=/api/v1/auth` 缩小暴露面 |
| 注册 | 无独立注册流程，首次 GitHub 登录即自动注册 |

### 1.2 本期目标

| 目标 | 说明 | 优先级 |
|------|------|--------|
| 双 Token 机制 | 短期 access token（JWT，30min）+ 长期 refresh token（7 天） | **必须** |
| HttpOnly Cookie 存储 | 双 Token 均通过 HttpOnly Cookie 下发，前端 JS 不可读，防 XSS 窃取 | **必须** |
| Token 自动刷新 | access token 过期时，前端自动用 refresh token 换取新 token | **必须** |
| 安全退出 | 退出时主动吊销 refresh token | **必须** |
| 改造 GitHub OAuth | 回调时统一签发双 token（access + refresh） | **必须** |

### 1.3 TODO（后续版本）

### 2.2 Token 生命周期

**GitHub OAuth 登录：**

1. 用户点击 GitHub 登录 → 跳转 GitHub 授权页
2. 授权完成 → 回调 `/auth/github/callback?code=xxx`
3. 后端用 code 换 GitHub access_token → 拉取用户信息
4. 查找/创建 user + user_auth 记录
5. 生成 access_token (JWT, 30min) + refresh_token (不透明, 7天)
6. refresh_token 存入 Redis：Key=`refresh_token:{sha256(token)}`，Value=`{user_id, login, created_at}`，TTL=7天
7. 双 Token 通过 `Set-Cookie`（HttpOnly; Secure; SameSite=Lax）下发，响应体仅返回 `{user}`

**正常 API 请求：**

1. 浏览器自动携带 Cookie: `access_token=...`（withCredentials）
2. 后端 `deps.get_current_user()` 从 Cookie 读取并验证 JWT 签名 + 过期时间
3. 验证通过 → 返回用户信息 → 业务处理

**Token 刷新：**

1. access_token 过期 → API 返回 401
2. 前端拦截器自动调用 `POST /auth/refresh`（无请求体，浏览器自动携带 refresh_token Cookie）
3. 后端计算 sha256(refresh_token) → 查 Redis
4. 存在 → 删除旧 refresh_token（轮转），生成新 token 对
5. 新 token 对通过 `Set-Cookie` 下发（旧 Cookie 被覆盖）
6. 前端重试原请求（新 Cookie 自动携带）

**退出登录：**

1. 前端调用 `POST /auth/logout`（Cookie 自动携带）
2. 后端删除 Redis 中的 refresh_token，并通过 Set-Cookie 清除客户端双 Cookie
3. 前端清除本地用户信息（auth_user）
4. 跳转登录页
```

### 2.3 Token 轮转策略（Refresh Token Rotation）

每次刷新 token 时，旧的 refresh token 立即失效，签发新的 refresh token：

```
刷新前:
  Redis: refresh_token:hash_A → {user_id: "1", ...}
  Browser Cookie: refresh_token = "A" (HttpOnly, JS不可读)

POST /auth/refresh （无请求体，浏览器自动携带 Cookie）
  → 验证 hash_A 存在
  → 删除 refresh_token:hash_A
  → 生成新 access_token + 新 refresh_token "B"
  → Redis: refresh_token:hash_B → {user_id: "1", ...}
  → Set-Cookie 下发新 token 对

刷新后:
  Redis: refresh_token:hash_B → {user_id: "1", ...}
  Browser Cookie: refresh_token = "B" (HttpOnly)
```

**轮转的意义**：如果攻击者窃取了某个 refresh token，一旦合法用户下次刷新，被窃取的 token 立即失效，攻击者无法继续使用。

```

  "message": "已退出登录"

## 四、数据存储设计

| Key 模式 | 类型 | 内容 | TTL | 说明 |
|----------|------|------|-----|------|
| `refresh_token:{sha256(token)}` | String(JSON) | `{"user_id":"1","login":"github-user","created_at":"..."}` | 7 天 | 有效 refresh token 索引 |

### 4.2 数据库表（沿用现有，无需变更）

**`user` 表**：

| 字段 | 用途 | 说明 |
|------|------|------|
| `id` | 用户唯一标识 | 主键 |
| `email` | GitHub 邮箱 | OAuth 拉取，可能为空 |
| `nickname` | 用户昵称 | OAuth 拉取 GitHub 用户名 |
| `avatar` | 头像 URL | OAuth 拉取 |
| `password_hash` | 密码哈希 | GitHub OAuth 用户为 NULL |

**`user_auth` 表**：

| provider | 含义 | 写入时机 |
|----------|------|----------|
| 2 | GitHub | GitHub OAuth 回调时 `INSERT (user_id, provider=2, provider_user_id=github_id)` |

### 4.3 配置项（新增）

在 `config.py` 的 `Settings` 类中新增：

```python
# Refresh Token 配置（新增）
REFRESH_TOKEN_EXPIRE_DAYS: int = 7          # refresh token 有效期（天）
REFRESH_TOKEN_BYTES: int = 32               # refresh token 随机字节数（32字节=256位）

# Cookie 与 CORS 配置（新增，HttpOnly Cookie 方案）
COOKIE_SECURE: bool = False                 # 是否仅HTTPS传输，生产环境必须为True
COOKIE_SAMESITE: str = "lax"                # SameSite策略，兼顾CSRF防护与OAuth跳转
COOKIE_DOMAIN: str | None = None            # Cookie作用域名，None表示当前域
COOKIE_ACCESS_PATH: str = "/"               # access_token Cookie路径（全部API）
COOKIE_REFRESH_PATH: str = "/api/v1/auth"   # refresh_token Cookie路径（仅认证端点）
CORS_ORIGINS: list[str] = ["http://localhost:5173"]  # 跨域白名单，credentials=True时禁止通配符
```

## 五、安全性设计

### 5.1 Token 安全

| 措施 | 说明 |
|------|------|
| JWT 签名 | HS256，密钥从环境变量 `SECRET_KEY` 读取 |
| Refresh Token 随机性 | 使用 `secrets.token_urlsafe(32)` 生成 256 位随机值 |
| Redis 存储 | 只存 refresh token 的 SHA256 哈希，不存明文 |
| 轮转 | 每次刷新签发新 token，旧 token 立即失效 |
| 过期控制 | access token 30 分钟，refresh token 7 天 |
| 前端存储 | HttpOnly Cookie（JS 不可读，XSS 无法窃取）；refresh_token 限定 `Path=/api/v1/auth` 缩小暴露面 |

### 5.2 防攻击措施

| 攻击类型 | 防御措施 |
|----------|----------|
| 重放攻击 | Refresh Token 轮转，每次刷新后旧 token 失效 |
| CSRF | SameSite=Lax 阻止跨站请求携带 Cookie；生产环境可追加 CSRF Token 双重提交校验 |
| XSS 窃取 | HttpOnly 使 JS 无法读取 token，XSS 攻击面降至最低 |
| Token 泄露 | 短期 access token（30min）限制攻击窗口；refresh token 轮转使泄露的旧 token 在合法用户下次刷新时失效 |

#### 前端 Token 存储

```
HttpOnly Cookie（JS 不可读，由后端 Set-Cookie 管理）:
  access_token     → JWT（Path=/，30分钟）
  refresh_token    → 不透明字符串（Path=/api/v1/auth，7天）

localStorage 键:
  auth_user        → 用户展示信息 JSON（非敏感，用于快速展示，不做权限校验）
```

#### 请求拦截器改造思路

```
当前逻辑:
  401 → 直接清除 token → 跳转登录页

改造后逻辑:
  401 → 尝试刷新会话:
    1. 检查是否正在刷新中（refreshPromise 单例防并发重复刷新）:
       - 正在刷新: 等待同一个 Promise 完成后重试
       - 未刷新: 发起 POST /auth/refresh（无请求体，Cookie 自动携带）
         - 成功: 浏览器自动写入新 Cookie，重试原请求（仅重试一次防死循环）
         - 失败: 清除 auth_user，跳转登录页
```

### 10.3 与现有 GitHub OAuth 的兼容

GitHub OAuth 回调目前返回旧的 `TokenResponse`（仅 `access_token`），改造后：

- 双 Token 通过 `Set-Cookie`（HttpOnly）下发，响应体仅返回 `{user}`
- refresh_token 存入 Redis（SHA256 哈希作 key）
- 前端 `CallbackPage` 仅存储用户信息（auth_user），token 由浏览器管理
- 退出时调用 `/auth/logout` 吊销 refresh_token 并清除 Cookie
