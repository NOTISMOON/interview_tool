# AI 面试功能流程文档

> **v2 变更（2026-08-23）**：面试链路已按《面试模块单LangGraph架构方案.md》演进。
> 原「同步单次合并 LLM 调用（分析+评分+追问预生成，5~15 秒）」已拆分为：
> ① 同步 **Fast Decision**（轻量 LLM，亚秒级）即时判定下一题（追问/下一基础/结束）；
> ② 全量分析评分改为**异步 MQ Worker**（`interview.analysis` 队列 + Outbox），
>    前端/同步 API 不再等待，报告页统一呈现。
> 本页保留 v1 交互细节；关键差异见下方标注。

## 1. 功能概述

AI 面试模块负责基于用户的**简历分析结果与面试配置**创建面试会话，创建时预生成基础题；面试中通过 **Fast Decision（即时判定下一题）** 与**异步全量分析 Worker**完成回答分析、评分与追问预生成，追问是否启用由 Fast Decision 判定并结合规则约束，最终生成面试报告。

整个面试流程与**简历上传、简历解析、简历 AI 分析**解耦。

简历相关能力由简历模块负责，面试模块只负责获取已经完成的 `Resume Analysis`，并将其作为 AI 面试的上下文。

整体关系：

```text
简历模块
    │
    │ Resume Analysis
    ▼
┌──────────────────────┐
│      AI 面试模块       │
└──────────┬───────────┘
           │
           ▼
    创建 Interview Session
           │
           ▼
    注册客户端租约（epoch）
           │
           ▼
     加载 Resume Context
           │
           ▼
      初始化面试状态
           │
           ▼
       AI 面试流程
```

# 3. 创建 Interview Session

## 3.1 创建流程

用户点击「开始面试」：

```text
用户
 │
 ▼
选择简历（resume_id）
 │
 ▼
选择面试类型（1-完整面试 / 2-快速面试）
 │
 ▼
POST /interviews
 │
 ▼
创建 interview 记录（status=0 进行中，id 即 session_id）
```

## 3.2 session_id 设计

`session_id` 直接使用 `interview` 表自增主键（数值），不新增列、不引入 UUID：

```text
interview:lock:42        # 操作锁
interview:checkpoint:42  # 面试状态 Checkpoint
interview:client:42      # 客户端租约
```

理由：

* 免数据库迁移，与全项目 BigInteger 主键风格一致；
* key 不可猜测性不是安全边界——越权由归属校验兜底（`interview.user_id == 当前用户`，与 `/resumes/{id}` 同款模式）。

操作锁、客户端租约、Checkpoint（Redis）与题目、报告（MySQL 外键）均以该 id 关联。

## 3.3 简历状态校验（创建时硬校验）

创建面试时同步校验简历状态，**不在面试流程内等待简历分析**（对齐《简历上传分析功能文档》§6.3 契约）：

| resume 状态 | 结果 |
| --- | --- |
| status=1（已就绪）且归属当前用户 | 正常创建 |
| status=0（分析中） | 409 `analyzing`，前端继续轮询简历状态 |
| status=2（分析失败） | 409 `analysis_failed`，提示重试/重新上传 |
| is_deleted=1 或非本人简历 | 404 |

## 3.4 API 契约

面试交互链路对延迟敏感（单次 LLM 调用 5~15 秒），采用**同步 HTTP 为主**，不经过 MQ；SSE 只做通知不承载数据（见 §16）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/interviews` | 创建面试：`{resume_id, type}`；校验归属与简历状态（§3.3）；预生成基础题并落库（§7）；返回面试 id + 首题 |
| GET | `/interviews/{id}` | 当前状态（question_index、phase、epoch）——刷新恢复 / 超时兜底轮询 |
| POST | `/interviews/{id}/answers` | 提交回答：`{question_index, answer, tab_epoch}`；幂等键 `(id, question_index)`；同步返回分析摘要 + 评分 + 下一题（或 summarizing） |
| GET | `/interviews/{id}/report` | 获取报告；未生成时返回 `generating` |
| POST | `/interviews/{id}/report/regenerate` | 报告生成失败后的手动重试 |
| POST | `/interviews/{id}/abort` | 主动放弃 → status=2（已中断） |

# 4. 获取简历上下文

## 4.1 Resume Context 来源

面试模块本身不负责重新分析简历。

根据 `resume_id` 获取已经生成的简历分析结果。

查询优先级：

```text
Interview
   │
   ▼
Redis Resume Analysis Cache
   │
   ├── 存在 ──────→ 直接使用
   │
   └── 不存在
        │
        ▼
     MySQL
        │
        ├── status=1 → 回写 Redis → 使用
        │
        └── status=0/2 → 创建接口已前置拦截（§3.3），此处仅防御性兜底
```

最终提供给 Interview Agent：

```text
Resume Context
    │
    ├── 基础信息
    ├── 技能
    ├── 工作经历
    ├── 项目经历
    ├── 教育经历
    └── 其他结构化信息
```

# 5. Interview Session 并发控制

## 5.1 问题场景

同一个面试不能同时由两个客户端推进。

典型场景：用户对正在面试的页面复制标签页，产生两个客户端同时操作同一场面试：

```text
客户端 A
    │
    └── 提交第 5 题回答

客户端 B（复制标签页产生）
    │
    └── 同时提交第 5 题回答
```

可能导致：

* 面试状态（Checkpoint）冲突
* 问题重复推进
* 回答重复分析
* 评分重复执行
* 当前问题索引错误

## 5.2 为什么不用会话级长锁

「创建 Session 时获取锁、面试结束时释放」的会话级长锁无法解决上述场景：

* **TTL 短**：面试持续几分钟到几十分钟，锁早已过期，互斥失效。
* **TTL 长 + 续期**：后台标签页的定时器会被浏览器节流，续期中断导致锁被误判过期，反而出现双客户端同时推进；标签页崩溃后僵尸锁还会阻塞恢复。

根本原因：复制标签页产生的两个客户端**属于同一个用户**，长锁回答不了「谁的写入算数」这个问题。

## 5.3 三层机制设计

| 层 | 机制 | 颗粒度 | 解决什么 |
| --- | --- | --- | --- |
| ① 操作锁 | `interview:lock:{session_id}`，SET NX EX + Lua compare-and-del | 单次状态推进 | 并发互斥：两个客户端同时提交，只有一个能推进 |
| ② 状态版本校验 | 请求携带 expected `question_index` + 阶段 | 每个写请求 | 过期写入：滞后客户端提交已被推进的状态被拒绝 |
| ③ 客户端租约 epoch | `interview:client:{session_id}` | 每个标签页 | 双开裁决：新客户端接管，旧客户端即时降级只读 |

**①② 保证数据正确性（必需），③ 负责双开时的体验裁决（推荐）。**

## 5.4 操作锁（①）

```text
interview:lock:{session_id}
```

* **获取时机**：每次状态推进请求开始时获取（提交回答→分析→评分→产出下一题，以及创建面试预生成题目、生成最终报告等），请求处理结束（含异常）在 `finally` 中释放。
* **Value**：唯一 `UUID`；释放时 Lua 脚本 compare-and-del，避免误删他人的锁。
* **TTL**：90 秒，覆盖最坏 LLM 处理窗口；生成最终报告等较长链路可增加续期。
* **实现**：复用简历分析锁模式（同步 + 异步双实现，参考 `app/redis/resume_lock.py`）。

不存在会话级长锁，因此也没有「面试结束时释放锁」的环节。

## 5.5 状态版本校验（②）

以 Checkpoint 中的 `question_index` + 当前阶段（如 `answering` / `analyzing` / `summarizing`）作为版本 token：

* 每次状态响应返回给前端；
* 前端下次写请求回带 expected 版本；
* 服务端比对不符 → 返回 409 + 最新状态，前端强制同步。

## 5.6 客户端租约 epoch（③）

```text
interview:client:{session_id}
```

存储 `{tab_id, epoch}`：

* 进入面试页时 activate：epoch + 1；
* 写请求携带 epoch，与 Redis 中不一致 → 409；
* epoch 变更时通过 SSE 推送 `taken_over` 事件（复用 `notify:push:{user_id}` 用户频道，事件体携带 `session_id`，各标签页自行过滤）；
* 旧客户端收到事件后提示「面试已在新标签页继续」并降级为只读；
* TTL 覆盖会话生命周期（如 24 小时），面试完成后随清理流程删除。

## 5.7 校验顺序

```text
epoch 租约 → 状态版本 → 操作锁
```

先做廉价的校验（Redis 读），最后才碰锁，减少无效锁竞争。

## 5.8 场景走查

```text
1. 客户端 A 进入面试        → activate(A, epoch=1) → SSE 连接
2. 用户复制标签页产生 B     → activate(B, epoch=2)
                             → 服务端推 taken_over 事件
                             → A 提示「面试已在新标签页继续」，降级只读
3. A 仍然发请求（异常情况） → epoch=1 ≠ 2 → 409（双保险）
4. 极端并发：A/B 同时提交   → 操作锁串行化
                             → 后到者 409 + 拿回最新状态自动同步
5. 客户端 B 整个浏览器被杀  → 无会话级长锁残留（操作锁均为短 TTL）
                             → 用户重开页面 epoch=3，从 Checkpoint 继续
6. 网络断在 LLM 推进中      → 操作锁 90s TTL 兜底
                             → 提交接口按 (session_id, question_index) 幂等，重试不重跑 LLM
```

第 5 条是对比会话级长锁最大的优势：**崩溃恢复不会被僵尸锁卡住**。

## 5.9 幂等性

提交回答接口以 `(session_id, question_index)` 为幂等键：

* 该题已分析过 → 直接返回已产出的下一题，不重复调用 LLM；
* 前端超时重试、网络抖动重发均安全。

# 6. 面试状态与 Checkpoint

## 6.1 设计决策：手写状态 JSON + Redis checkpointer

面试跨轮本质是**请求驱动的状态机**：每个写请求（提交回答 / 生成报告）推进一个确定性阶段，轮与轮之间由用户交互分隔，不存在长驻的图执行。

状态分层（两层职责不同）：

* **跨轮业务状态**：手写 Redis 状态 JSON（本节），TTL 24h，可从 MySQL 重建；
* **图内运行状态**：面试节奏控制图（单 LangGraph 图，thread_id = interview_id）使用 LangGraph checkpointer 持久化图内题目队列/计数值，后端为 `langgraph-checkpoint-redis`（Redis Stack 的 RedisJSON + RediSearch），多进程共享、不落本地磁盘文件；面试完成/中断时经 `invalidate_checkpoint()` 删除对应 thread。图状态可从 MySQL/Redis 业务数据重建，Redis 中仅作运行态冗余缓存。


## 6.2 状态结构

```text
interview:checkpoint:{id}
```

```json
{
    "phase": "answering",
    "question_index": 5,
    "current_question_id": 123,
    "current_question": "...",
    "current_answer": "...",
    "answered_count": 5,
    "follow_up_used": 1,
    "total_follow_up_used": 3,
    "started_at": "2026-08-22T10:00:00+08:00",
    "epoch": 2
}
```

`phase` 取值与流转：`answering`（等待/接收回答）→ `analyzing`（LLM 分析中）→ `summarizing`（报告生成中）→ `completed` / `aborted`。

## 6.3 版本 token

`question_index` + `phase` 组合即为 §5.5 的状态版本 token：每次状态响应返回给前端，前端下次写请求回带，服务端比对不符返回 409 + 最新状态。

## 6.4 TTL 与兜底

* TTL 24 小时（覆盖会话生命周期），每次写入刷新；
* 状态丢失（Redis 故障/淘汰）不影响数据正确性：题目、回答、评分均以 MySQL `interview_question` 为准（见 §14），Checkpoint 仅做**恢复加速**，可由 MySQL 重建。

# 7. 出题策略（Question Agent）

## 7.1 两种题目来源

| 题目类型 | 生成时机 | 方式 |
| --- | --- | --- |
| 基础题 | 创建面试时**一次性预生成** | LLM 按 Resume Context + 维度批量出题，逐题落库 `interview_question`（is_follow_up=0） |
| 追问 | 面试中随分析结果**预生成** | 分析评分合并调用顺带产出 `follow_up_question` 字段（见 §9），是否启用由规则判定（见 §10） |

面试进行中**不存在单独的「生成下一题」LLM 调用**——基础题已落库、追问已在分析时生成，下一题切换零等待。

## 7.2 基础题预生成

```text
Resume Context（技能/项目/工作经历/教育）
      +
面试类型（type=1 完整 8~10 题 / type=2 快速 4~5 题）
      │
      ▼
Question Agent（LangGraph 单轮，with_structured_output 批量出题）
      │
      ▼
按维度分配：技术基础/项目经验/综合素质/架构设计（category 1-4）
      │
      ▼
逐题落库 interview_question（question_no 顺序即面试顺序）
```

约束：

* 题目围绕简历**真实内容**生成（技能、项目细节），不出与简历无关的泛化题；
* 面试结束前用户**无法提前看到题目列表**（未完成面试不返回全量题目，仅返回当前题）。

# 8. 用户回答（语音作答）

## 8.1 语音转文字：浏览器原生能力

采用浏览器 Web Speech API（`SpeechRecognition`）在**前端**完成语音识别，后端只接收文本：

* 无第三方 ASR 服务、无音频上传链路，后端契约与文本输入完全一致；
* `interview_question.audio_url` 字段保留备用，当前流程不写。

前端要点：

* `webkitSpeechRecognition`（Chrome/Edge）持续识别，`lang=zh-CN`，识别文本实时上屏；
* 识别结果允许用户编辑修正后再提交；
* 麦克风权限检测（设备检测）为纯前端环节，不进入后端状态机；
* 浏览器兼容检测：进入面试前检测 `SpeechRecognition` 可用性，不支持（如 Firefox）直接提示用户更换 Chrome/Edge 浏览器；
* 本地开发（localhost 属于安全上下文）可直接使用，无需额外配置。

## 8.2 线上部署要求（零代码改动）

* 唯一硬性要求：页面通过 **HTTPS** 访问（SSL 证书 + Nginx/CDN，标准生产部署项，非本功能额外改造）；
* 前端页面与后端 API 均走 https，Nginx 同源反代 `/api` 到 FastAPI，避免 mixed content 拦截麦克风权限；
* 后端不涉及 ASR、前端无需条件逻辑，本地与线上行为一致。

## 8.3 识别失败处理

Chrome 的识别经 Google 云端处理（非本地离线识别），部分网络环境下会报 `network` 错误；Edge 走微软识别服务不受影响。前端需处理 `onerror`：

* `network` 错误 → 提示重试或更换浏览器（国内用户优先推荐 Edge）；
* `not-allowed` → 提示开启麦克风权限后重试；
* 连续识别失败 → 允许用户改用键盘输入完成本题（不作整场降级）。

## 8.4 提交流程

```text
用户提交回答（文本）
      │
      ▼
验证 Interview Session（归属 + status=0）
      │
      ▼
校验 epoch 租约 + 状态版本（§5.5 / §5.6）
      │
      ▼
获取操作锁（单次推进）
      │
      ▼
幂等检查：(id, question_index) 已分析 → 直接返回既有结果
      │
      ▼
读取 Checkpoint，写入 current_answer，phase=analyzing
      │
      ▼
分析+评分+追问预生成（§9，单次 LLM 调用）
      │
      ▼
同步返回：分析摘要 + 评分 + 下一题（或 summarizing）
```

请求体 `{question_index, answer, tab_epoch}`；前端请求超时（30 秒）后轮询 `GET /interviews/{id}` 兜底恢复。

---

# 9. 分析与评分（单次合并 LLM 调用）

## 9.1 为什么合并

若拆成「分析 → 评分 → 追问判断 → 生成下一题」四次串行调用，单轮延迟 20~80 秒，交互不可接受。合并为一次结构化输出调用后，**单轮仅 1 次 LLM 调用（5~15 秒）**。

## 9.2 合并输出 Schema

```text
AnswerAnalysisResult（with_structured_output）
├── correctness          是否切题、正确性
├── technical_depth      技术深度 1-5
├── completeness         完整性 1-5
├── logic                逻辑性 1-5
├── key_points           回答要点
├── weaknesses           薄弱点/缺失
├── score                综合评分 1-5（落库 ai_score）
├── comment              评价（落库 ai_comment）
└── follow_up_question   预生成追问（可为 null，启用与否由规则判定 §10）
```

## 9.3 执行

LangGraph 单轮编排（同 resume_parse 模式）：组装题目 + 回答 + 简历上下文（供追问贴合项目实际）→ 合并调用 → 逐题落库（§14.2）→ 更新 Checkpoint。

评分维度（技术能力/问题理解/准确性/深度/工程经验/表达能力）体现在 score 与 comment 中，不拆成多列。

---

# 10. 追问判定（规则化，不调 LLM）

分析结果中的 `technical_depth` / `weaknesses` / `follow_up_question` 已携带足够信号，是否追问由**规则**决定，不再消耗 LLM 调用：

```text
满足全部条件才追问：
├── follow_up_question 非空
├── technical_depth ≤ 2 或 weaknesses 非空
├── 当前基础题已追问次数 < 1（每道基础题最多追问 1 次）
└── 全场追问总数 < 基础题数（防无限连环追问）
```

任一条件不满足 → 直接进入下一题判断（§12）。

---

# 11. Follow-up 追问（预生成取用）

追问判定通过后，追问问题**直接取用分析输出中的 `follow_up_question`**：

```text
追问判定通过（§10）
      │
      ▼
追问题落库 interview_question
（is_follow_up=1，parent_question_id 指向当前题）
      │
      ▼
作为下一题展示（前端展示追问标签）
      │
      ▼
等待用户回答 → 回到 §8 提交流程
```

追问内容贴合用户回答动态生成（由 §9 的合并调用产出），而非固定题库。例如：

```text
问题：
Redis 为什么需要持久化？

用户：
因为 Redis 是内存数据库，所以需要持久化。

分析：
回答正确，但缺少具体机制（technical_depth=2，weaknesses 非空）。

追问（预生成）：
Redis 常见的持久化机制有哪些？
它们在性能和数据安全方面有什么区别？
```

---

# 12. 下一题判断与终止条件

```text
追问判定（§10）
      │
      ├── 追问 → 展示追问题（§11）
      │
      └── 不追问
           │
           ▼
      是否还有下一道基础题？
           │
       ┌───┴───┐
      是       否
       │       │
       ▼       ▼
   展示下一题  进入 Summary（§13）
```

## 12.1 终止条件

| 条件 | 规则 | 说明 |
| --- | --- | --- |
| 正常结束 | 预生成基础题全部问完且无待答追问 | 主路径 |
| 追问上限 | 每道基础题 ≤ 1 次追问；全场追问总数 ≤ 基础题数 | §10 规则内建，防无限连环 |
| 时长兜底 | 面试进行 > 60 分钟 → 当前题答完直接进入 Summary | 防挂机/异常驻留 |
| 题量 | type=1 完整面试 8~10 题；type=2 快速面试 4~5 题 | 预生成时确定（§7.2） |

满足终止条件后 phase=summarizing，异步触发报告生成（§13）。

# 13. Summary Agent 与报告生成

所有题目完成后进入最终总结。

```text
所有题目 + 回答 + 逐题评分（MySQL interview_question）
      │
      ▼
Summary Agent（LangGraph 单轮，with_structured_output）
      │
      ▼
最终面试报告 → 落库 interview_report（§14.3）
      │
      ▼
SSE 推送 report_ready 事件（§16）
```

报告内容与存储字段映射：

| 报告内容 | 存储字段（interview_report） |
| --- | --- |
| 总体评分 | total_score |
| 各维度得分 | dimension_scores (JSON) |
| 回答优点 | strengths |
| 知识薄弱点 | weaknesses |
| 能力画像 | capability_profile (JSON) |
| 改进建议 | suggestions |
| 总评 | summary |

## 13.1 报告生成时机与容错

* 最后一题分析完 → status=1（已完成）→ 异步生成报告（BackgroundTasks，操作锁保护）；
* LLM 失败重试 3 次 → 通知用户 + 暴露 `POST /report/regenerate` 手动重试；
* 题目与评分已全部落库，报告生成失败**不丢数据**；
* `GET /report` 未命中时惰性兜底触发一次生成，同时返回 `generating`。

# 14. 面试结果保存

## 14.1 持久化原则：逐题落库

**每题回答分析完即落库**，而非只在结束时一次性写 MySQL。Redis Checkpoint 丢失不影响已答数据（Checkpoint 仅做恢复加速，见 §6.4）。

## 14.2 逐题写入（每轮分析完成后，单事务）

```text
单事务：
├── interview_question：user_answer / ai_score / ai_comment / answer_duration
├── 追问题插入（若启用追问，is_follow_up=1）
└── interview：current_question_index / follow_up_count 冗余计数更新
```

## 14.3 报告落库（Summary 完成后）

新增 `interview_report` 表（与 interview 1:1）：

```sql
CREATE TABLE `interview_report` (
  `id` BIGINT NOT NULL AUTO_INCREMENT,
  `interview_id` BIGINT NOT NULL COMMENT '关联面试ID',
  `total_score` DECIMAL(5,2) DEFAULT NULL COMMENT '总评分',
  `dimension_scores` JSON DEFAULT NULL COMMENT '各维度得分',
  `strengths` TEXT COMMENT '回答优点',
  `weaknesses` TEXT COMMENT '知识薄弱点',
  `suggestions` TEXT COMMENT '改进建议',
  `capability_profile` JSON DEFAULT NULL COMMENT '能力画像',
  `summary` TEXT COMMENT '总评',
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_interview_id` (`interview_id`)
) COMMENT='面试报告表';
```

## 14.4 完成清理

```text
生成最终报告
      │
      ▼
interview：status=1，total_score 冗余回写，interview_time 记录
      │
      ▼
清理客户端租约；Checkpoint 保留供报告页回看（TTL 自然过期）
```

面试最终结果由 MySQL 作为持久化业务数据。

# 15. 面试异常恢复

如果发生：

* 浏览器刷新
* 网络断开
* SSE 断开
* 服务重启
* Agent 执行中断

不应该重新开始面试。

恢复流程：

```text
用户重新进入面试
        │
        ▼
获取 session_id
        │
        ▼
重新注册客户端租约（epoch + 1）
        │
        ▼
读取 Interview Checkpoint
        │
        ▼
恢复面试状态
        │
        ▼
确定 phase 与当前题目
        │
        ▼
继续执行
```

例如：

```text
原状态：

question_index = 5
phase = analyzing
```

用户刷新后：

```text
恢复：

question_index = 5
phase = analyzing
```

而不是重新生成前面的 1～4 题。

# 16. SSE 实时通信

面试过程中前端需要实时获得状态变化通知；**题目数据本身由 HTTP 响应携带，SSE 只做通知不承载数据**。

复用现有 `notify:push:{user_id}` 用户频道（sse_manager 订阅模式不变），事件体携带 `session_id`，各标签页自行过滤：

| 事件 | 触发时机 | 前端行为 |
| --- | --- | --- |
| `interview:taken_over` | epoch 变更（新标签页接管） | 旧标签页提示「面试已在新标签页继续」并降级只读 |
| `interview:completed` | 最后一题分析完成 | 提示进入报告等待 |
| `interview:report_ready` | 报告落库 | 报告页刷新/跳转 |

```text
Frontend ──SSE（只读）──► FastAPI ──Redis Pub/Sub──► notify:push:{user_id}
```

SSE 连接为只读，允许多个连接并存（各标签页按 `session_id` 过滤事件）；执行互斥由写路径的操作锁与 epoch 租约保证（见 §5）。

---

# 17. Redis 在面试模块中的职责

## 17.1 操作锁与客户端租约

```text
interview:lock:{session_id}      # 操作锁：单次状态推进互斥（短 TTL）
interview:client:{session_id}    # 客户端租约：双开场景裁决有效客户端
```

用途：

**操作锁保证同一个面试 Session 同一时间只有一个客户端在推进状态；客户端租约裁决复制标签页等双开场景下哪个客户端有效（详见 §5）。**

---

## 17.2 面试状态 Checkpoint

```text
interview:checkpoint:{id}    # id 即 interview 主键（见 §3.2）
```

用途：

**保存面试流程状态（phase / question_index / epoch 等，见 §6.2），实现中断恢复与状态版本校验。**

---

## 17.3 Resume Analysis Cache

虽然由简历模块维护，但面试模块可以读取：

```text
resume:analysis:{resume_id}
```

用途：

**快速获取简历分析结果。**

# 21. 失败与放弃处理矩阵

| 场景 | 阶段 | 处理 |
| --- | --- | --- |
| LLM 超时/失败 | 分析评分（§9） | 操作锁 TTL 兜底自动释放；Checkpoint 回退 phase=answering；幂等键保证重试不重跑 LLM；同题连续 2 次失败 → 跳过该题（ai_score=NULL，ai_comment=分析失败），继续下一题 |
| LLM 失败 | 基础题预生成（§7） | 创建接口返回 503 提示稍后重试；未生成题目则面试不可开始，无脏数据 |
| LLM 失败 | 报告生成（§13） | 题目已全部落库无数据丢失；后台重试 3 次 → 通知用户 + `POST /report/regenerate` 手动重试 |
| 用户主动放弃 | 任意 | `POST /abort` 或最后活动 > 30 分钟 → status=2（已中断）；已答题目与评分保留；清理租约；不生成报告 |
| SSE 断开 | 任意 | 不影响推进（SSE 只读只通知）；重连后 `GET /interviews/{id}` 全量同步 |
| 服务重启 | 任意 | 操作锁短 TTL 自然过期；逐题落库 + Checkpoint 兜底；走 §15 恢复流程 |
| Redis Checkpoint 丢失 | 任意 | 由 MySQL `interview_question` 重建（Checkpoint 仅恢复加速，见 §6.4） |
| 简历被删除 | 创建后 | 已创建面试继续有效（创建时已快照上下文）；再次创建该简历的面试返回 404 |

# 22. 里程碑规划

| 里程碑 | 范围 | 验收标准 |
| --- | --- | --- |
| M1 会话闭环 | `interview_report` 表迁移；创建面试（简历校验 + 基础题预生成）；三层并发控制（操作锁/状态版本/epoch 租约）；语音作答（前端 Web Speech API）+ 文本提交；分析评分追问合并调用；规则追问判定；逐题落库 | 复制标签页双开互斥正确；刷新可恢复；含语音作答的完整面试走通并落库 |
| M2 报告与容错 | Summary + 报告落库 + 报告 API；abort/超时中断；§21 失败矩阵全场景 | 报告可查询可重试；LLM 失败不丢数据；放弃后状态正确 |
| M3 实时与边界 | SSE 三事件（taken_over/completed/report_ready）；时长/追问上限；前端全面对接 | 双开即时提示；断线恢复；边界条件不失控 |

语音识别完全由前端浏览器能力承担（见 §8.1），后端无 ASR 依赖，不设独立语音里程碑。
